自研 RPC 框架架构设计

# 自研轻量级RPC框架 深度架构设计（对标Dubbo核心原理，面试天花板完整版）

整体沿用秒杀系统的交付结构：

  1. 业务背景 & 核心诉求 & 技术难点
  2. 框架整体模块拆分 + 每模块底层原理+代码伪实现
  3. 完整调用时序流程图解（文字版可直接画架构图）
  4. 高可用设计、容错、负载均衡、集群治理
  5. 序列化协议、自定义通信报文结构
  6. 可监控、可溯源、全链路埋点体系
  7. 生产级坑点与解决方案
  8. 30道高频深度面试追问 + 标准答案
  9. 三段背诵版面试总结话术

# 一、业务背景与核心需求

# 1. 使用场景

微服务架构下，服务A需要远程调用服务B的Java方法，原生HTTP协议存在冗余Header、短连接反复握手、序列化效率低等问题，无法满足高吞吐、低延迟的内部服务通信。 自研RPC框架目标：像调用本地方法一样调用远程服务，屏蔽网络通信、寻址、编解码、容错等底层细节。

# 2. 硬性设计要求（架构设计约束）

  1. 高性能：基于Netty Reactor模型长连接通信，自定义二进制协议，序列化占用体积小、速度快；
  2. 服务自动发现：服务提供者注册、消费者自动订阅，支持动态上下线无感感知；
  3. 丰富负载均衡：轮询、随机、加权轮询、一致性哈希、最小活跃数；
  4. 完整容错体系：超时重试、失败熔断、降级、故障隔离、请求重试防幂等；
  5. 高可用：注册中心集群、客户端连接池、服务多实例、自动断线重连、心跳保活；
  6. 可扩展：可插拔序列化器、可插拔负载均衡算法、可插拔注册中心；
  7. 可监控可溯源：全链路TraceId、调用耗时统计、QPS、异常率、服务健康度大盘、调用日志审计。

# 3. 核心技术难点（面试开篇必讲）

  1. 如何基于JDK动态代理实现本地方法无感调用；
  2. TCP粘包拆包问题如何解决；
  3. 自定义私有通信协议报文设计；
  4. 服务节点动态变更如何实时推送客户端；
  5. 分布式场景下服务雪崩如何通过熔断隔离防护；
  6. 如何保证请求唯一性，避免重试导致重复执行业务逻辑；
  7. 长连接空闲断开、服务下线后客户端快速剔除无效节点。

# 二、整体框架分层架构（6大核心模块，自上而下）

# 总架构层级

客户端调用层 → 代理层 → 路由负载均衡层 → 网络通信层 → 序列化编解码层 → 注册中心层 → 服务端业务反射执行层
附加：容错熔断模块 + 监控埋点模块 + 配置模块

# 模块1：注册中心模块（Registry）

# 核心职责

  1. 服务提供者启动时，将服务接口全限定名 + IP + 端口 + 权重 + 版本号注册到注册中心；
  2. 消费者启动时订阅指定服务，拉取全部可用服务节点列表，缓存在本地内存；
  3. 注册中心推送服务上下线变更事件，客户端自动更新本地节点缓存；
  4. 提供健康检测，剔除不健康宕机节点。

# 可选接入实现（可插拔）

  • Zookeeper：临时节点，服务断开自动销毁节点，天然适合服务注册；
  • Nacos：AP架构，支持持久化、权重配置、灰度分组，生产首选；
  • Redis：简易版基于Hash结构存储，适合演示Demo。

本地缓存+增量推送，消费者不会频繁轮询注册中心，降低注册中心压力，百万级服务集群也能稳定运行。

# 核心原理

UserResp resp = userService.getUserById(10001L);

# 代理拦截器执行逻辑伪代码

public class RpcInvocationHandler implements InvocationHandler {
    @Override
    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        // 1. 封装RPC请求对象
        RpcRequest request = new RpcRequest();
        request.setServiceName(method.getDeclaringClass().getName());
        request.setMethodName(method.getName());
        request.setParamTypes(method.getParameterTypes());
        request.setParams(args);
        request.setTraceId(TraceContext.getTraceId()); // 链路追踪ID
        // 2. 交给路由负载均衡模块选择服务节点
        ServiceNode targetNode = loadBalancer.select(serviceList);
        // 3. 网络模块发送TCP请求，阻塞等待响应
        RpcResponse response = nettyClient.sendRequest(targetNode, request);
        // 4. 解析返回结果，抛出远程异常
        if (response.getException() != null) {
            throw response.getException();
        }
        return response.getData();
    }
}

# 两种代理选型区别

  1. JDK动态代理：只支持接口代理，无依赖、性能高，RPC框架标准用法；
  2. CGLIB：支持普通类代理，依赖ASM字节码，Dubbo同时兼容两种。

# 模块3：路由与负载均衡模块（LoadBalance）

# 前置条件

消费者本地内存维护对应服务的可用节点列表List，节点属性：IP、Port、weight权重、activeCount活跃连接数、version版本。

# 内置5种负载均衡算法（可插拔策略工厂）

  1. Random 随机：简单粗暴，节点数量均衡时效果好；
  2. RoundRobin 轮询：按顺序逐个分发请求；
  3. WeightRoundRobin 加权轮询：性能好的机器配置更高权重，分配更多流量（生产最常用）；
  4. LeastActive 最小活跃数：优先发给当前正在处理请求最少的节点，解决慢节点拖累整体性能；
  5. ConsistentHash 一致性哈希：
    • 适用场景：有状态调用（如缓存、会话绑定）；
    • 优势：新增/下线节点只影响少量哈希映射，不会大面积路由漂移；
    • 虚拟节点优化：避免节点分布不均、哈希倾斜。

# 扩展点

支持按版本号分组路由（灰度发布）、按机房就近路由（异地多活架构）。

# 模块4：网络通信模块（Netty 核心）

# 架构模型：Netty 主从Reactor多线程模型

  1. Boss Group（主线程池）：只负责监听TCP端口，接受客户端连接；
  2. Worker Group（工作线程池）：处理已建立连接的IO读写、编解码、业务逻辑；
  3. 服务端启动绑定端口，客户端启动创建N个长连接连接池（默认单节点8条连接，复用TCP通道减少握手开销）。

# 三大网络可靠性保障机制

  1. 心跳保活机制 客户端定时发送PING心跳包，服务端返回PONG；N次未收到心跳判定连接失效，客户端关闭重连，解决TCP僵死连接问题。
  2. 自动断线重连 连接断开后客户端通过指数退避算法重试连接（1s、2s、4s、8s…上限32s），避免疯狂重试压垮服务端。
  3. 连接池复用 同一个服务节点复用多条长连接，不用每次调用新建TCP，降低三次握手四次挥手损耗。

# TCP粘包拆包解决方案（重中之重）

自定义协议头部携带数据包总长度，Netty内置LengthFieldBasedFrameDecoder解码器：

  1. 先读取固定长度协议头；
  2. 从头部解析出Body完整长度；
  3. 根据长度截取完整数据包，彻底解决TCP流无边界导致的拆包粘包。

# 模块5：自定义私有通信协议 + 序列化编解码层（Codec）

# 一、自定义二进制报文协议（固定16字节Header + Body）

| 魔数(4B) | 版本号(1B) | 序列化类型(1B) | 消息类型(1B) | 保留位(9B) | Body长度(4B) | Body内容(NB)
1

字段释义：

  1. 魔数（Magic）：固定 0xCAFEBABE，快速过滤非本框架非法数据包；
  2. 版本号：框架版本，兼容多版本升级；
  3. 序列化类型：0=Protostuff，1=Hessian2，2=JSON，3=Kryo；
  4. 消息类型：0=请求包，1=响应包，2=心跳PING，3=心跳PONG；
  5. Body长度：后续二进制数据字节长度，用于拆包；
  6. Body：序列化后的RpcRequest/RpcResponse对象二进制字节数组。

# 二、可插拔序列化器（策略模式）

序列化框架 优点 缺点 框架选用场景
Protostuff 二进制体积小、速度快、无依赖 可读性差 默认首选生产
Kryo Java专属极致性能 跨语言不兼容 纯Java微服务内部调用

# 编解码执行流程

客户端编码：Java对象 → 序列化二进制 → 拼装协议Header → 写入TCP通道 服务端解码：读取协议头校验魔数 → 截取Body字节 → 反序列化为Java对象

# 模块6：服务端请求处理 & 反射执行模块

服务端收到解码后的RpcRequest对象执行流程：

  1. 根据serviceName（接口全类名）从本地Spring容器/Bean工厂找到对应的实现类Bean；
  2. 通过反射Method.invoke()执行目标方法，传入请求参数；
  3. 捕获业务异常，封装返回RpcResponse对象（结果data/exception）；
  4. 按协议编码，通过Netty写回客户端；

# 优化点：反射性能优化

  1. 启动时预缓存所有接口Method反射对象，避免运行时重复查找；
  2. 使用MethodHandle替代原生反射，提升调用性能。

# 模块7：容错、熔断、降级集群治理模块（高可用核心）

# 1. 超时控制

客户端调用设置全局超时时间（默认1000ms），Netty超时直接抛出异常，避免线程池无限阻塞耗尽。

# 2. 失败重试机制（带幂等约束）

  • 重试策略：只对**读接口（查询）**开启重试，写操作默认关闭；
  • 重试次数、重试间隔可配置；
  • 幂等保障：请求携带全局唯一requestId，服务端Redis校验重复请求，防止重复下单、重复扣款。

# 3. 服务熔断（借鉴Sentinel/Hystrix滑动窗口）

核心：故障隔离，防止雪崩

  1. 统计单个服务节点一段时间内失败率；
  2. 失败率超过阈值（如50%）触发熔断，直接走降级逻辑；
  3. 半开状态：放行少量探测请求，恢复正常则关闭熔断。

# 4. 降级策略三种落地方式

  1. 本地Mock静态数据返回；
  2. 调用备用降级兜底接口；
  3. 返回统一错误提示，快速释放线程。

# 5. 故障剔除

连续多次调用失败的服务节点，临时从客户端本地列表剔除，隔一段时间自动探测恢复。

# 模块8：可监控、可溯源、全链路埋点体系（架构师加分项）

# 1. 全链路追踪

  • 调用入口生成全局唯一TraceId，跨客户端、服务端透传；
  • SpanId记录调用层级，嵌套调用完整串联；
  • 日志统一打印TraceId，接入ELK一键检索完整调用链路。

# 2. 核心监控指标（Prometheus+Grafana采集）

客户端指标：

  • 服务调用QPS、平均RT、最大耗时、超时率、异常率；
  • 连接池空闲连接数、重连次数、心跳失败次数； 服务端指标：
  • 每个接口调用量、执行耗时、异常堆栈；
  • Netty工作线程池活跃度、队列堆积长度。

# 3. 告警机制

服务熔断触发、调用失败率飙升、服务节点下线、连接大量断开自动钉钉/短信告警。

# 4. 调用日志审计

记录调用方IP、接口名、入参、出参、耗时、异常信息，留存用于问题溯源、安全审计。

# 三、完整一次RPC调用全时序（逐步骤拆解）

# 调用方（客户端）流程

  1. 业务代码调用代理对象 userService.getUserById()；
  2. JDK动态代理拦截方法，封装RpcRequest请求体，绑定TraceId；
  3. 从注册中心拉取并缓存的服务节点列表，通过负载均衡算法选中一台服务端节点；
  4. 从Netty连接池取出可用长连接；
  5. 序列化Request对象，拼装自定义私有协议二进制数据包；
  6. Netty异步发送TCP数据包，阻塞等待响应；
  7. 收到服务端返回数据包，解码反序列为RpcResponse；
  8. 解析结果，若有异常直接抛出，返回业务数据给上层。

# 被调用方（服务端）流程

  1. Netty Boss线程接受TCP连接，Worker线程处理数据；
  2. 通过长度解码器拆包，校验协议魔数合法性；
  3. 根据序列化类型反序列化得到RpcRequest；
  4. 根据接口名+方法名找到本地实现Bean，反射执行目标方法；
  5. 捕获异常封装RpcResponse；
  6. 编码成协议数据包写回客户端；
  7. 埋点记录调用耗时、状态，上报监控系统。

# 四、框架高可用全套设计汇总

  1. 注册中心高可用：Nacos/ZK集群部署，多节点防止注册中心单点故障；
  2. 服务集群高可用：服务提供者多实例部署，节点下线客户端自动剔除；
  3. 网络层高可用：Netty连接池、心跳保活、指数退避重连、TCP拆包安全解码器；
  4. 调用容错高可用：超时控制、失败重试、滑动窗口熔断、降级、故障节点临时隔离；
  5. 数据安全：请求唯一ID做幂等，防止重试重复执行业务；
  6. 扩展性高可用：所有组件采用SPI可插拔设计（注册中心、负载均衡、序列化器、容错策略均可自定义扩展）。

# 五、生产落地高频坑点 & 解决方案

# 坑1：TCP粘包拆包导致数据包解析错乱

解决方案：自定义协议头携带Body长度，使用Netty LengthFieldBasedFrameDecoder 按长度截取完整报文。

# 坑2：大量短连接频繁三次握手，性能低下

解决方案：客户端维护服务节点长连接池，复用TCP通道，配合心跳保活维持连接。

# 坑3：服务提供者下线后，客户端还在路由到无效节点报错

解决方案：注册中心推送Watcher变更事件，客户端实时更新本地节点缓存；增加失败自动剔除机制。

# 坑4：接口调用超时重试导致重复提交（如扣款、下单）

解决方案：1）写操作默认关闭重试；2）全局requestId做服务端幂等校验；3）数据库唯一索引兜底。

# 坑5：某个服务节点响应缓慢，拖垮整个调用集群（慢节点问题）

解决方案：负载均衡选用最小活跃数算法LeastActive，自动绕过高负载慢节点；熔断机制隔离故障实例。

# 坑6：反射调用性能损耗大

解决方案：服务端启动预热缓存Method对象，使用MethodHandle替代原生反射提升执行效率。

# 坑7：序列化漏洞、反序列化攻击风险

解决方案：白名单限制反序列化类，禁用危险序列化器（如默认Kryo需做安全校验）。

# 坑8：Netty线程池耗尽，请求堆积阻塞

解决方案：业务处理丢入独立业务线程池异步执行，不占用Netty Worker IO线程。

# 六、30道深度面试追问 + 满分标准答案

# 一、基础原理与架构模块（1-10）

# 1. RPC 和 HTTP 本质区别是什么，为什么微服务内部优先用RPC？

答：1）底层协议：RPC大多基于TCP自定义私有二进制协议，HTTP基于应用层协议，有大量冗余Header、Cookie；2）连接方式：RPC长连接复用，省去反复握手挥手，HTTP短连接开销大；3）序列化：RPC用二进制序列化体积更小、解析更快，HTTP多用JSON文本；4）能力封装：RPC内置注册发现、负载均衡、熔断重试、链路追踪等微服务治理能力，HTTP需要额外组件堆砌。内部服务追求低延迟高吞吐优先RPC，对外开放接口用HTTP。

# 2. JDK动态代理实现RPC代理对象的核心流程是什么？为什么不用CGLIB？

答：JDK动态代理要求目标必须是接口，框架生成接口的实现类字节码，调用时进入自定义InvocationHandler拦截器，封装请求参数发起远程调用。RPC场景下所有服务都以接口定义契约，JDK代理无第三方依赖、执行效率更高，是最优选择；CGLIB用于代理普通类，Dubbo为兼容做了双支持，自研框架没必要引入ASM字节码依赖。

# 3. Netty Reactor主从多线程模型讲清楚，BossGroup和WorkerGroup各自职责？

答：主Reactor（Boss Group）单线程负责端口监听、接受TCP连接请求，建立Socket通道后注册给从Reactor；从Reactor（Worker Group）一组N个线程，轮询处理已就绪连接的IO读/写、编解码事件，业务逻辑再丢到自定义业务线程池异步执行，保证IO线程不被阻塞。

# 4. TCP为什么会出现粘包拆包，你的RPC框架怎么解决？

答：TCP是流式协议，操作系统内核缓冲区会合并多个小包发送（粘包），或大数据拆分多个报文发送（拆包），应用层无法感知边界。解决方案自定义协议头部4字节存储Body总长度，使用Netty的LengthFieldBasedFrameDecoder，先读协议头拿到长度，再精准截取完整数据包，从底层彻底规避问题。

# 5. 自定义RPC协议每个字段设计的目的是什么，魔数Magic有什么作用？

答：魔数用于快速校验数据包合法性，过滤端口扫描、非法TCP报文、错误协议流量，直接丢弃不进入后续解码逻辑；版本号用于框架平滑升级兼容；序列化类型标识用哪一种序列化算法；消息类型区分请求、响应、心跳包；Body长度解决TCP拆包粘包。整套协议二进制紧凑，解析开销极低。

# 6. 注册中心Zookeeper为什么用临时节点存储服务实例？

答：ZK临时节点特性：客户端会话断开、进程宕机、网络中断时，服务端自动删除对应节点。服务提供者异常下线无需主动注销，注册中心数据自动干净；同时客户端注册Watcher监听器，节点变更立刻推送事件，消费者实时刷新本地服务列表，天然适配服务发现场景。

# 7. 消费者为什么要本地缓存服务节点列表，而不是每次调用都查注册中心？

答：如果每次RPC调用都查询注册中心，高并发下会给注册中心造成巨大压力，甚至压垮集群。启动时全量拉取一次，后续只接收增量变更推送，绝大部分请求直接读取本地内存列表，性能极高，这是服务发现标准优化方案。

# 8. 5种负载均衡算法各自适用什么业务场景？一致性哈希解决什么核心问题？

答：随机、轮询适合节点性能完全一致的无状态服务；加权轮询给配置高的机器分配更多流量，生产最通用；最小活跃数规避慢节点拖累整体性能；一致性哈希用于有状态绑定场景（如缓存分片），解决普通取模算法扩容时大量数据/请求路由漂移的痛点，新增节点只影响少量映射关系。

# 9. Netty心跳保活具体怎么实现，多久发一次，连续多少次断开重连？

答：客户端每30s发送PING心跳数据包，服务端收到返回PONG响应；客户端连续3次未收到PONG判定连接失效，关闭通道触发重连逻辑；重连采用指数退避算法（1s、2s、4s…最大32s），避免无限循环重试冲击服务端，解决TCP僵死连接无法感知的问题。

# 10. 服务端为什么要把业务逻辑放到独立线程池执行，不能直接在Netty Worker线程处理？

答：Netty Worker线程是IO核心线程，如果执行业务耗时操作（DB查询、复杂计算）会阻塞整个IO线程，导致该线程上所有连接无法收发数据，引发大面积超时。标准规范：IO线程只做编解码、数据包分发，所有业务逻辑丢入自定义ThreadPoolExecutor异步执行。

# 二、容错、一致性、高可用（11-20）

# 11. RPC调用超时重试怎么设计，哪些接口不能开启重试？如何保证重试幂等？

答：设置客户端全局调用超时时间，超时触发重试机制，可配置重试次数与间隔；写接口（新增、修改、删除、支付）一律关闭重试，仅查询类读接口开启。幂等方案：每个请求生成全局唯一requestId，传递到服务端，Redis记录已处理的requestId，重复请求直接返回上次结果，同时数据库唯一索引兜底防止重复落库。

# 12. 滑动窗口熔断降级完整执行逻辑，三个状态流转怎么切换？

答：三种状态：关闭→打开→半开。关闭状态统计一段时间内接口失败次数；失败率超过阈值进入打开状态，直接走降级逻辑不发起远程调用；半开状态定时放行少量探测请求，若探测全部成功则关闭熔断恢复正常，探测失败继续保持熔断，核心目的隔离故障节点防止服务雪崩。

# 13. 服务节点宕机后，客户端完整的故障感知与剔除流程？

答：1）注册中心感知服务实例下线，推送变更事件给消费者；2）消费者收到事件更新本地内存服务列表，移除宕机节点；3）已缓存的长连接因心跳检测失效关闭；4）负载均衡路由时自动跳过无效节点；5）兜底：调用连续失败N次临时剔除该节点，定时探测恢复。双重机制保证快速摘除故障实例。

# 14. 序列化为什么首选Protostuff，对比JSON和Kryo优缺点？

答：Protostuff二进制序列化，序列化后字节体积远小于JSON，解析速度快，跨语言兼容性优于Kryo，无安全漏洞风险；JSON调试打印方便但性能差、包体大；Kryo性能最优但仅兼容Java语言，存在反序列化安全漏洞，企业内部纯Java架构可选用，通用框架首选Protostuff。

# 15. 如何实现框架组件可插拔？SPI机制在RPC里用在哪些地方？

答：基于Java原生SPI或者自定义SPI工厂模式实现可扩展：可插拔注册中心（ZK/Nacos/Redis）、可插拔负载均衡算法、可插拔序列化器、可插拔容错策略。新增实现类无需修改框架核心代码，配置文件指定即可加载，开闭原则。

# 16. 长连接连接池为什么要每个服务节点维护多条TCP通道，单条不行吗？

答：单条TCP通道同一时间只能串行处理请求，高并发下形成队列排队，RT飙升；多连接池可以并行分发请求，充分利用网络IO，提升并发吞吐量，同时单连接断开不影响其他连接可用，容错性更好。

# 17. 服务版本灰度发布怎么在负载均衡层实现？

答：服务注册时携带version版本字段，消费者调用时指定目标版本，负载均衡过滤只路由对应版本的节点；也可按机房、分组做路由，实现灰度流量切分、蓝绿发布。

# 18. RpcRequest和RpcResponse里面必须携带哪些核心字段？

Request：服务接口名、方法名、参数类型数组、参数数组、traceId、requestId、超时时间； Response：返回结果数据、异常对象、耗时、状态码。

# 19. 如何解决反射调用性能低下问题，两种优化手段？

答：1）框架启动扫描所有暴露服务接口，提前解析并缓存Method反射对象，运行时直接取用，避免重复查找；2）使用Java 7+ MethodHandle方法句柄替代原生Method.invoke，底层绕过反射安全校验，调用性能接近直接调用。

# 20. 调用链路TraceId完整透传路径，服务嵌套调用如何串联？

答：客户端代理拦截器生成TraceId存入ThreadLocal，封装进RpcRequest请求体；服务端解码取出TraceId放入本地上下文，新生成SpanId标识子调用；如果服务继续发起下一级RPC调用，继续向下传递TraceId，整条调用链共用同一个全局ID，日志、监控全部绑定该ID，实现全链路溯源。

# 三、架构拔高、对比、生产优化（21-30）

# 21. 对比Dubbo，你自研的RPC框架缺失哪些核心能力？

答：自研极简版缺少：1）完整SPI扩展生态、多协议兼容（Dubbo协议、HTTP2、gRPC）；2）精细化流量治理（权重动态调整、限流、参数校验）；3）异步调用、泛化调用、隐式参数传递；4）完整配置中心动态推送规则；5）更细粒度的线程池隔离。但核心的RPC通信、注册发现、负载均衡、容错熔断、序列化整套原理完全一致。

# 22. gRPC和自研TCP RPC框架最大区别？

答：gRPC基于HTTP2协议+Protobuf序列化，跨语言极强，适合多语言异构系统；自研TCP私有协议纯Java栈深度优化，协议更轻量化、网络开销更低，只适合Java微服务集群内部调用。

# 23. 大规模集群下，注册中心压力过大怎么优化？

答：1）客户端本地全量缓存，只订阅增量变更，不轮询拉取；2）服务按业务模块拆分不同注册中心集群；3）Nacos开启集群分片、数据持久化；4）限制单服务实例最大注册数量，减少Watcher推送风暴。

# 24. 如何做异步RPC调用，不阻塞当前业务线程？

答：代理层返回CompletableFuture异步对象，Netty收到响应后回调Future完成方法，业务线程可以先执行其他逻辑，需要结果时再阻塞获取，提升整体服务吞吐量。

# 25. Netty内存泄漏怎么规避，框架层面做哪些防护？

答：1）使用Netty自带的内存池PooledByteBufAllocator；2）解码后手动释放ByteBuf缓冲区；3）使用try-finally结构保证资源释放；4）开启Netty内存泄漏检测日志，线上告警。

# 26. 服务启动时如何自动扫描所有需要对外暴露的RPC接口？

答：基于Spring的Bean后置处理器BeanPostProcessor，容器初始化完成后遍历所有Bean，判断是否带有自定义@RpcService注解，提取接口信息自动注册到注册中心，类似Dubbo的@DubboService注解扫描逻辑。

# 27. 跨机房异地多活场景，负载均衡怎么就近路由？

答：服务注册时上报机房、区域标签，客户端本地读取自身机房标识，负载均衡优先选择同机房节点调用，减少跨城网络延迟，只有同机房无可用节点才路由异地机房。

# 28. 监控系统采集哪些核心指标能快速定位RPC调用瓶颈？

答：客户端：调用QPS、P95/P99耗时、超时次数、异常率、连接重连次数；服务端：每个接口平均RT、业务线程池队列堆积、Netty IO线程利用率、GC频率。通过指标可以快速定位网络瓶颈、服务慢接口、线程池耗尽问题。

# 29. 如果注册中心整体宕机，RPC框架如何降级保证现有调用可用？

答：客户端已经在本地内存缓存了完整服务节点列表，注册中心宕机不影响存量请求继续路由；仅新启动的服务无法注册、新消费者无法拉取服务列表，存量集群完全可用，属于注册中心经典降级兜底方案。

# 30. 用一段话总结整套自研RPC框架的设计思想（面试收尾满分话术）

答：整体遵循分层解耦、可插拔扩展、可靠性优先、微服务闭环治理四大原则。底层基于Netty主从Reactor模型实现高性能TCP长连接通信，自定义二进制私有协议解决粘包拆包；通过注册中心实现服务自动发现与动态感知；上层使用JDK动态代理屏蔽远程调用细节，搭配多算法负载均衡完成流量分发；构建超时、重试、熔断、降级完整容错体系杜绝级联雪崩；最后嵌入全链路追踪、指标监控、日志审计实现可观测可溯源，同时所有核心组件基于SPI策略模式可灵活替换，是一套贴合Java微服务生产落地的轻量级RPC通信框架。

# 七、三段背诵版面试总结话术

# 30秒极简版

自研RPC框架核心分为八大模块，注册中心做服务自动注册发现，JDK动态代理实现本地无感调用，Netty长连接做底层TCP通信并自定义二进制协议解决粘包拆包，可插拔负载均衡分发流量，序列化层压缩传输报文，配套熔断降级重试容错机制保障高可用，最后全链路埋点实现监控与问题溯源。

# 1分钟标准版

自研RPC对标Dubbo核心原理，整体架构由注册中心、客户端代理、负载均衡、Netty网络通信、编解码序列化、服务端反射执行、容错治理、监控溯源八部分构成。服务启动自动注册到Nacos/ZK集群，消费者订阅节点本地缓存；通过JDK动态代理拦截方法调用封装请求，Netty基于Reactor模型建立长连接，自定义带长度字段的私有协议处理TCP拆包问题；内置多种负载均衡算法分发流量，Protostuff二进制序列化提升传输效率；增加超时重试、滑动窗口熔断降级防止服务雪崩，配合TraceId全链路追踪与Prometheus指标监控，整套框架高性能、高可用、可扩展、可运维。

# 架构师拔高版

整套RPC框架设计围绕性能极致化、故障自愈化、架构可扩展化、运维可观测化四大目标落地。通信层采用TCP长连接+私有二进制协议最大化降低网络开销，规避HTTP应用层协议冗余损耗；服务治理层面通过注册中心实现无状态服务自动扩缩容，多级负载均衡适配不同流量场景；稳定性上构建完整的故障闭环：超时控制、幂等重试、熔断隔离、节点自动摘除，阻断故障传导；架构上全部组件SPI可插拔，降低耦合方便迭代升级；最后端到端链路追踪、多维度指标告警、调用日志审计形成完整可观测体系，在高性能分布式服务通信场景下达成可靠性与扩展性平衡。
