## 1. MySQL 整体四层架构
### 1）连接层
负责TCP握手、身份账号密码校验、线程池管理，接收客户端请求。

磁盘持久化数据文件、日志文件、frm表结构文件、ibd数据文件。

## 2. InnoDB vs MyISAM 核心区别（必考题）
### MyISAM
1. 不支持事务、不支持外键；
2. 只支持**表级锁**，并发写性能极差；
3. 崩溃无法安全恢复，无redo log；
4. 有独立的索引文件.MYI、数据文件.MYD；
5. 全文索引支持，查询速度快，占用磁盘小；
6. 适合静态只读表、日志统计表、低频更新数据。

### InnoDB（生产唯一推荐）
1. **支持完整ACID事务**，支持外键；
2. 支持**行级锁+表级锁**，并发读写能力强；
3. redo+undo日志保证宕机数据安全，崩溃自动恢复；
4. 聚簇索引，数据和主键存在同一个ibd文件；
5. 支持MVCC多版本并发控制，读写不加锁；
6. 支持事务隔离级别、崩溃安全恢复；
7. 适用99%业务场景：订单、用户、库存、支付等需要事务的表。

### 一句话总结
只要涉及增删改、并发、事务，一律用InnoDB；MyISAM基本淘汰。

## 3. InnoDB 物理存储结构：页、区、段、表空间
1. **页 Page（最小IO单元）**
   默认16KB，磁盘一次读写最小单位，索引、数据、undo、change buffer都存在页中。
2. **区 Extent**
   连续64个页 = 1MB，分配存储空间的单位。
3. **段 Segment**
   一个索引对应一个段，叶子节点段、非叶子节点段，由多个区组成。
4. **表空间 Tablespace**
- 系统共享表空间 ibdata1
- 独立表空间 *.ibd（innodb_file_per_table=ON，每张表一个ibd文件）
5. Buffer Pool 缓冲池
   内存核心区域，缓存热点数据页、索引页，减少磁盘随机IO，MySQL性能核心。

## 4. 事务ACID四大特性原理
### A 原子性 Atomic
事务要么全部执行成功，要么全部回滚，依靠 **undo log 回滚日志**实现。
### C 一致性 Consistency
事务执行前后数据整体约束合法（主键唯一、外键、字段长度），最终由原子、隔离、持久共同保证。
### I 隔离性 Isolation
多个并发事务之间互相不可见，依靠 **MVCC + 锁机制** 实现。
### D 持久性 Durability
事务提交后数据永久落地磁盘，宕机不丢失，依靠 **redo log 重做日志** 刷盘保证。

### 极简记忆
Undo保证原子性，Redo保证持久性，锁+MVCC保证隔离性，三者共同达成一致性。

## 5. 事务4种隔离级别 + MVCC底层原理（重中之重）
### 5.1 三大并发问题
1. **脏读**：事务读到其他事务未提交的修改；
2. **不可重复读**：同一事务内，两次读取同一数据，中间被其他事务update提交，结果不一致；
3. **幻读**：同一事务内，多次范围查询，其他事务insert提交，导致数量不一致，像幻觉一样。

### 5.2 四个隔离级别（从上到下隔离性递增，性能递减）
1. **READ UNCOMMITTED 读未提交**
   允许脏读，生产绝不使用。
2. **READ COMMITTED RC 读已提交（Oracle默认，MySQL可配置）**
   解决脏读，存在不可重复读、幻读；MVCC每次读取最新快照。
3. **REPEATABLE READ RR 可重复读（MySQL InnoDB 默认）**
   解决脏读、不可重复读，**InnoDB通过临键锁机制解决了幻读**；MVCC在事务第一次快照后全程复用该版本。
4. **SERIALIZABLE 串行化**
   最高级别，全部加表锁，完全串行执行，性能极差，不用。

### 5.3 MVCC 多版本并发控制底层原理
全称 Multi-Version Concurrency Control，核心作用：**读不加锁，读写不冲突，提升并发性能**。
1. 每条InnoDB隐藏三个字段：
    - DB_TRX_ID：最后修改这条记录的事务ID；
    - DB_ROLL_PTR：指向undo log版本链表指针；
    - DB_ROW_ID：无主键时自动生成隐藏主键。
2. undo log 保存数据历史版本，形成版本链表；
3. Read View 视图规则判断当前事务可见哪个版本数据；
4. RR级别事务启动生成一次Read View，RC每次查询都生成新View。

### 5.4 MVCC 只能解决快照读，当前读仍要加锁
- 快照读：普通SELECT，走MVCC无锁；
- 当前读：SELECT ... FOR UPDATE / UPDATE / DELETE / INSERT，加行锁。

## 6. InnoDB 锁体系（行锁、表锁、意向锁、间隙锁、临键锁）
### 6.1 锁粒度划分
1. **表级锁**：锁定整张表，MyISAM只有表锁；InnoDB手动LOCK TABLE加表锁，并发差。
2. **行级锁 Record Lock**
   锁定索引上的某一条记录，只在命中唯一索引、精准等值查询时触发。
   **前提：SQL必须走索引，否则行锁退化成表锁！**

### 6.2 意向锁 Intention Lock（表级别辅助锁）
意向共享IS、意向排他IX，目的：快速判断整张表是否有行锁，避免遍历所有行，提升锁检测效率。
由InnoDB自动加，程序员不可手动操作。

### 6.3 间隙锁 Gap Lock（RR隔离级别特有）
锁定索引记录之间的间隙，**禁止其他事务在间隙插入数据，用来防止幻读**。只在RR级别生效。

### 6.4 临键锁 Next-Key Lock = Record Lock + Gap Lock
InnoDB RR默认算法，左开右闭区间，既锁当前行，又锁前后间隙，彻底杜绝幻读。
- 等值匹配命中唯一索引 → 降级为纯行锁；
- 范围查询/非唯一索引 → 保持临键锁。

### 6.5 共享锁S、排他锁X
- S锁：多个事务可同时加，读共享；
- X锁：排他，加了X锁其他事务不能加任何锁。

### 高频坑点
1. where条件字段无索引 → 行锁升级为表锁；
2. 字符串不加引号隐式转换导致索引失效，锁整张表；
3. RR级别范围查询会触发Gap间隙锁，容易引发死锁。

## 7. 索引底层：为什么用B+树，不用二叉树、B树、哈希
### 7.1 二叉平衡树（红黑树）
高度太高，千万级数据树高几十层，磁盘IO几十次，性能爆炸，排除。

### 7.2 B树（多路平衡查找树）
关键字和数据分散在所有节点，叶子节点不串联；范围查询需要中序遍历，多次IO，效率低。

### 7.3 B+树 InnoDB索引结构（最优）
1. 所有**数据只存在叶子节点**，非叶子节点只存主键索引值，内存可以缓存大量索引，减少IO；
2. 叶子节点用双向链表串联，**范围查询、排序、分页只需要遍历链表**，效率极高；
3. 树的高度极低（千万级数据树高3层），磁盘IO次数极少；
4. 叶子节点有序，完美适配数据库SQL场景。

### 7.4 Hash索引
等值查询极快，但无法范围查询、无法排序、存在哈希碰撞，InnoDB仅自适应哈希索引AHI内部使用，不对外。

### 一句话结论
数据库大量范围检索、排序、分页，B+树是综合最优解。

## 8. 聚簇索引（主键索引） vs 二级索引（普通索引）
### 8.1 聚簇索引 Clustered Index
1. InnoDB主键就是聚簇索引；
2. B+树叶子节点**直接存放完整一行所有字段数据**；
3. 一张表只能有一个聚簇索引。

### 8.2 二级索引 Secondary Index
普通索引、联合索引都属于二级索引；
叶子节点只存储**主键值**，查到主键后需要回到聚簇索引查找完整数据，这个过程叫**回表查询**。

### 8.3 覆盖索引（避免回表，优化核心）
查询字段全部包含在二级索引里，不需要回表，例如：
`CREATE INDEX idx_name ON user(name); SELECT name FROM user WHERE name='张三'`
explain中Extra显示 Using index 代表命中覆盖索引。

### 8.4 主键设计规范
1. 主键推荐自增bigint，有序插入，B+树页分裂最少；
2. 不要用UUID当主键，随机值导致频繁页分裂，性能差；
3. 必须设置主键，InnoDB无主键会自动生成隐藏row_id聚簇索引。

## 9. 联合索引最左前缀原则 & 索引失效全部场景
### 9.1 最左匹配原则
联合索引 `idx(a,b,c)`，查询条件要从最左前列开始连续匹配，中断后面索引失效。
✅ 有效：where a=? / a=? and b=? / a=? and b=? and c=?
❌ 失效：where b=? / c=? / b=? and c=?

### 9.2 索引失效高频场景（写SQL避坑）
1. 联合索引不满足最左前缀；
2. 索引列做运算、函数、类型转换：`where id+1=10`、`year(create_time)=2026`；
3. 隐式类型转换（字符串字段传数字，不加引号）；
4. 使用 `!=、<>、not in、is not null`；
5. like %前缀模糊查询 `like '%关键词'`，后置`'关键词%'`可以走索引；
6. or连接非索引字段，导致整体失效；
7. MySQL优化器判断全表扫描更快，主动放弃索引。

### 优化口诀
索引列不计算、不套函数、模糊只右配、or慎用、类型一致、遵守最左前缀。

## 10. 慢SQL优化全流程 + EXPLAIN执行计划关键字解析
### 10.1 完整优化步骤
1. 开启慢查询日志，定位耗时SQL；
2. EXPLAIN 分析执行计划；
3. 优化索引、改写SQL、拆分大事务；
4. 避免大分页、避免select *；
5. 关联查询小表驱动大表；
6. limit超大分页用主键偏移优化。

### 10.2 EXPLAIN 核心字段重点解释
1. **type（最重要）**
   性能等级：`system > const > eq_ref > ref > range > index > ALL`
   至少达到range级别，日常目标ref，ALL全表扫描必须优化。
2. **key**：实际最终使用的索引；
3. **rows**：扫描预估行数，越小越好；
4. **Extra**：
    - Using index：覆盖索引，优秀；
    - Using filesort：文件排序，需要优化order by索引；
    - Using temporary：创建临时表，GROUP BY无索引；
    - Using where：存储引擎层过滤，正常。

### 分页大坑优化
`limit 1000000,10` 偏移量极大，扫描百万行；
优化写法：`SELECT * FROM t WHERE id > 1000000 LIMIT 10`。

## 11. 三大日志 redo log / undo log / binlog 完整作用
### 11.1 redo log 重做日志（InnoDB崩溃恢复核心）
1. 解决磁盘随机IO慢的问题，先写redo log buffer，后台刷盘；
2. 事务提交持久化到磁盘redo log文件（ib_logfile0/1）；
3. 宕机重启后，根据redo log把已提交事务刷入数据页，保证持久性D；
4. 刷盘策略：innodb_flush_log_at_trx_commit
    - 1：每次提交刷磁盘，最安全，性能稍差（生产标配）；
    - 0：每秒刷一次；
    - 2：提交刷OS缓存，每秒落盘。

### 11.2 undo log 回滚日志
1. 保存数据修改前版本，用于事务回滚（原子性A）；
2. 构建MVCC版本链表，实现快照读；
3. 事务提交后undo log不会立即删除，由purge线程异步清理。

### 11.3 binlog 二进制日志（Server层，所有引擎共用）
1. 记录所有DDL/DML修改语句，用于**主从复制、数据备份恢复、审计**；
2. 三种格式：
    - statement：记录SQL语句，体积小，可能函数执行结果不一致；
    - row：记录行数据变更，精准无误差，体积大（生产推荐）；
    - mixed：混合模式。

### 三者协作崩溃恢复流程
1. 事务提交，先刷redo log（prepare），再写binlog；
2. binlog写入成功，redo log标记commit状态；
3. 宕机重启：扫描redo log，有commit标记直接落盘，无commit且binlog完整则提交，否则回滚。

## 12. MySQL 崩溃安全恢复 Crash-Safe 完整流程
1. 执行DML先写入redo log buffer；
2. 事务commit：redo log执行prepare刷盘；
3. 写入binlog并刷盘；
4. redo log写入commit标记；
5. 异常断电重启：
    - 检查redo log中prepare状态：
      a. 既有prepare又有commit：直接提交事务，刷新数据页；
      b. 只有prepare、binlog存在完整记录：提交；
      c. binlog不完整：回滚事务；
6. 后台线程将redo log里的数据刷回ibd磁盘文件。

## 13. MySQL 主从复制原理、三种复制模式、GTID
### 13.1 主从三线程核心原理
1. Master主库：Dump线程，读取binlog推送给从库；
2. Slave从库IO线程：拉取binlog写入relay log中继日志；
3. Slave从库SQL线程：重放relay log日志，同步数据。

### 13.2 三种复制模式
1. **异步复制（默认）**
   Master写完直接返回，不等待Slave，性能最高，主宕机可能丢失最后一小段binlog。
2. **半同步复制 Semi-Sync**
   Master至少等待一个Slave接收binlog回执再返回，数据安全性提升，性能略有损耗，生产推荐开启。
3. **并行复制**
   从库多个SQL线程并发重放relay log，解决单线程回放慢导致主从延迟。

### 13.3 GTID 全局事务ID
全局唯一事务编号，简化主从切换、故障转移，避免重复执行binlog，MGR集群依赖GTID。

### 主从架构用途
读写分离、数据热备份、高可用切换、分库分表前置。

## 14. 主从延迟产生原因与优化方案
### 产生原因
1. 主库写入压力过大，binlog生成速度远超从库回放速度；
2. 从库单SQL线程串行执行，大事务阻塞后续日志；
3. 从库硬件性能低于主库；
4. 大事务、大批量delete/update一次性生成海量binlog；
5. 网络带宽瓶颈。

### 优化方案
1. 开启从库并行复制；
2. 拆分大事务，禁止大批量一次性更新；
3. 半同步复制，缩小数据差；
4. 提升从库服务器配置；
5. binlog格式改为row，减少回放异常；
6. 读写分离规避实时强一致性查询。

## 15. 死锁产生条件、排查与解决
### 15.1 死锁四大必要条件
1. 互斥条件：行锁排他占用；
2. 请求保持：持有锁同时申请其他锁；
3. 不可剥夺：锁不能被强制释放；
4. 循环等待：两个事务互相等待对方资源，闭环等待。

### 15.2 复现场景
事务A锁id=1，申请id=2；事务B锁id=2，申请id=1，互相阻塞触发死锁。

### 15.3 解决与规避方案
1. **统一SQL加锁顺序**，所有事务按主键升序更新；
2. 缩小事务粒度，尽快提交释放锁；
3. 避免长事务、长时间持有行锁；
4. 减少Gap间隙锁范围（降低隔离级别到RC可消除间隙锁，但要评估幻读风险）；
5. 超时等待、死锁检测机制自动回滚代价小的事务。

### 排查命令
`show engine innodb status;` 查看LATEST DETECTED DEADLOCK死锁日志。

## 16. 大事务危害及优化手段
### 危害
1. 长时间占用行锁，并发阻塞、极易死锁；
2. undo log无法被purge清理，磁盘暴涨；
3. binlog文件过大，主从复制延迟飙升；
4. 崩溃恢复时间变长；
5. 锁等待超时概率大幅上升。

### 优化
1. 拆分循环批量操作为多次小事务；
2. 事务内剔除无关查询逻辑；
3. DML尽早执行，最后提交；
4. 避免一次性几万条批量更新。

## 17. 分库分表（垂直拆分、水平拆分、Sharding-JDBC）
### 17.1 垂直拆分（分库）
按业务模块拆库：user库、order库、goods库，解决单库表太多、关联复杂问题。

### 17.2 水平拆分（分表）
单表数据量过大（千万级以上），按规则拆成多张结构相同的子表：
拆分规则：取模、范围、日期、哈希、地区。
例：order_0 ~ order_31 按月分表。

### 17.3 中间件选型
1. Sharding-JDBC（客户端SDK，无中间件转发，性能好，SpringBoot无缝集成，首选）；
2. MyCat（服务端代理，独立进程，运维重）。

### 17.4 分表带来的痛点
1. 跨分片join关联查询困难；
2. 全局唯一主键生成（雪花算法、Redis自增、数据库号段模式）；
3. 分页、排序、聚合函数复杂度上升；
4. 分布式事务问题（Seata AT/TCC）；
5. 扩容重新分片数据迁移成本高。

### 最佳实践
优先优化索引、清理历史归档、分表，不到亿级数据不轻易分库。

---

## 18. 数据库三大范式 & 反范式设计
### 三大范式
1. 第一范式1NF：列不可再分；
2. 第二范式2NF：消除部分依赖，非主键字段完全依赖主键；
3. 第三范式3NF：消除传递依赖，非主键不能依赖其他非主键。

### 反范式（为查询性能冗余字段）
适当冗余字段，减少联表JOIN次数，以空间换时间。
例：订单表冗余商品名称、价格，下单后直接展示，不用关联商品表。
互联网业务大量使用反范式设计。

---

## 19. InnoDB 重要内存组件 Buffer Pool、Change Buffer、AHI
### 19.1 Buffer Pool（核心）
缓存数据页、索引页，LRU链表冷热数据淘汰，直接决定MySQL性能，通常设置服务器物理内存50%~70%。

### 19.2 Change Buffer 更改缓冲区
缓存二级索引的DML修改（INSERT/UPDATE/DELETE），延迟合并刷入磁盘，减少随机IO。主键聚簇索引有序插入，不使用Change Buffer。

### 19.3 Adaptive Hash Index 自适应哈希索引
InnoDB自动对热点页建立哈希索引，等值查询加速，可关闭。

# 面试极简背诵总结
1. InnoDB靠redo保证持久、undo保证原子、MVCC+锁保证隔离；
2. 索引B+树优势在于叶子有序链表，范围查询快，回表用覆盖索引优化；
3. RR默认隔离级别通过临键锁解决幻读，间隙锁是死锁高发点；
4. 慢SQL看EXPLAIN的type级别，杜绝索引失效九大场景；
5. 主从依赖binlog同步，半同步降低数据丢失风险，大事务是延迟和死锁元凶；
6. 千万级以上数据表考虑水平分表，Sharding-JDBC为首选中间件；
7. 架构遵循先索引优化、再SQL改写、最后分库分表的优化顺序。
