Java 后端面试高频场景题

# Java 后端面试高频场景题

整体分为 6 大模块：JVM 性能故障场景、并发多线程死锁 / 线程池场景、MySQL 数据库慢 SQL 与锁场景、Redis 缓存经典击穿 / 雪崩 / 穿透场景、Spring 框架循环依赖与事务失效场景、分布式微服务一致性场景，每题包含：面试场景描述→现象→解决方案→底层原理→深挖追问点，图文用结构化文字还原逻辑结构图（可自行手绘）。

# 重点 开场自我介绍

面试官您好，我叫XXX。 我从事java后端开发8年,主要做分布式高并发业务系统，在近期的工作中主要参与新项目从0到1、老服务迁移、服务架构改造、线上问题攻坚这方面工作。
在参与的XX项目中，经历过大促、节假日高峰流量场景，落地了接口性能优化、服务框架改造、流量压测、线上告警处理。
在以往的工作中,我还负责过团队的建设,带过团队，从人员招聘、新人培养、团队氛围建设到项目立项、工程交付、结项验收完整的项目生命周期都由我跟进推动 在承接业务需求时,我更习惯站在全局的角度业务希求与服务系统关系，兼顾迭代效率、稳定性与可扩展性；尽量把所有问题暴露在方案设计阶段。 希望今天能跟面试官多多学习。

# 一、JVM 高频故障场景（面试官最爱深挖资深经验）

# 场景 1：线上服务频繁 Full GC，CPU 打满，接口超时雪崩

# 1）现象

  1. GC 日志频繁 Full GC (Metadata GC Threshold) / Full GC (Ergonomics)
  2. CPU 使用率持续 95% 以上，业务线程被 STW 停顿阻塞
  3. 网关大量超时、请求堆积、服务熔断

# 2）常见根因（8 年工程师要分层回答）

# 根因 1：内存泄漏（最常见）
  • 静态集合类（static List/Map）无限存放对象，GC Roots 无法回收
  • 线程池核心线程常驻，任务持有大对象引用不释放
  • 第三方框架 IO 流、连接未关闭（文件流、数据库 Connection、Netty Buffer）
  • 循环引用、ThreadLocal 未手动remove()导致 Entry 内存泄漏
# 根因 2：堆内存参数不合理
  • Xmx 与 Xms 不一致，频繁扩容缩容触发 Full GC
  • 老年代过小，年轻代对象快速晋升老年代塞满
  • Metaspace 元空间上限过小，类加载过多触发元空间 Full GC
# 根因 3：大对象直接进入老年代

一次性加载几万条数据库数据到 List，绕过 Eden 区直接占满 Old 区

# 3）排查完整流程（面试标准答案）

  1. jps -l 找到进程 PID
  2. jstat -gc PID 1000 实时查看 YGC/FGC 次数、耗时
  3. jmap -dump:format=b,file=heap.hprof PID 导出堆快照
  4. MAT 工具分析：Leak Suspects 泄漏疑点、Histogram 大对象、GC Roots 引用链
  5. 查看 GC 日志 -Xlog:gc* 定位 Full GC 触发来源

# 4）底层原理深挖

  1. Full GC 会暂停所有用户线程（STW），新生代 + 老年代 + 元空间全部回收，代价远大于 Minor GC
  2. ThreadLocal 泄漏原理：ThreadLocalMap 的 Key 是弱引用，Value 是强引用，线程不销毁时 Value 永远无法被 GC，必须在finally中调用threadLocal.remove()
  3. 大对象判定阈值由-XX:PretenureSizeThreshold控制，超过阈值直接分配到老年代

# 5）优化落地方案

# JVM生产推荐参数（ZGC低停顿收集器，JDK17+）
-Xms8g -Xmx8g  # 堆固定大小，避免扩容
-XX:+UseZGC    # ZGC毫秒级STW，替代G1
-XX:MetaspaceSize=512m
-XX:MaxMetaspaceSize=512m
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/logs/heapdump.hprof

  1. G1 和 ZGC 底层回收差异？ZGC 的染色指针、读屏障原理？
  2. CMS 的浮动垃圾、并发失败（Concurrent Mode Failure）为什么会退化为 Serial Old？

# 场景 2：OOM 堆内存溢出，系统直接 Crash

核心区分 3 种 OOM 原理

  1. Java heap space：堆对象过多 / 泄漏，堆空间不足 → 排查堆快照
  2. Metaspace：动态代理、CGLIB 大量生成类，元空间溢出 → 调大 Metaspace 上限
  3. Direct buffer memory：NIO 直接缓冲区未释放，堆外内存溢出 → 手动调用cleaner释放 ByteBuffer

# 二、并发多线程经典场景（必考题）

# 场景 1：多线程操作共享变量，结果数据错乱（原子性问题）

# 场景描述

100 个线程循环累加int count = 0，每个线程累加 1000 次，最终结果远小于 100000

# 底层原理

count++ 不是原子操作，拆分为 3 步：

  1. 从主内存读取 count 到工作内存
  2. 工作内存 + 1 计算
  3. 写回主内存 多线程并发时指令重排、可见性丢失导致覆盖。

# 3 种解决方案 & 底层差异

  1. synchronized 同步方法 / 代码块 底层：对象监视器 Monitor，重量级锁，依赖操作系统内核态切换，锁升级（偏向锁→轻量级自旋锁→重量级锁）
  2. volatile 修饰变量 仅保证可见性 + 禁止指令重排，不保证原子性，不能解决本次累加问题（高频坑点）
  3. AtomicInteger CAS 自旋乐观锁 底层：Unsafe 类调用 CPU 硬件级cmpxchg指令，无内核切换，高并发下性能远优于 synchronized；缺点：长时间自旋消耗 CPU、只能单个变量原子操作

# 深挖延伸

  • LongAdder 为什么高并发比 AtomicInteger 更强？ 答：分段 CAS，将热点数据分散到多个 Cell 数组，最终汇总求和，降低单个 CAS 竞争概率。

# 场景 2：死锁场景（手写代码 + 排查 + 破坏四大条件）

# 死锁代码（面试直接默写）

public class DeadLockDemo {
    private static final Object lockA = new Object();
    private static final Object lockB = new Object();

    public static void main(String[] args) {
        new Thread(() -> {
            synchronized (lockA) {
                System.out.println("线程1拿到A锁，等待B锁");
                try {Thread.sleep(1000);} catch (Exception e) {}
                synchronized (lockB) {}
            }
        }).start();

        new Thread(() -> {
            synchronized (lockB) {
                System.out.println("线程2拿到B锁，等待A锁");
                try {Thread.sleep(1000);} catch (Exception e) {}
                synchronized (lockA) {}
            }
        }).start();
    }
}

# 死锁四大必要条件（必须背）

  1. 互斥条件：锁同一时间只能被一个线程持有
  2. 请求并持有：线程拿到一把锁，再去申请另一把
  3. 不可剥夺：锁只能持有者主动释放，外部无法抢占
  4. 循环等待：线程互相持有对方需要的锁，形成闭环

# 解决方案（破坏任一条件即可）

  1. 统一锁获取顺序：所有线程先拿 lockA 再拿 lockB（破坏循环等待，生产最常用）
  2. 设置锁超时：使用Lock.tryLock(time, unit)超时自动放弃，释放已持有锁（破坏不可剥夺）
  3. 减少嵌套锁，业务重构避免多锁嵌套

# 死锁排查命令

jstack PID 导出线程栈日志，搜索DEADLOCK关键字直接定位死锁线程。

# 场景 3：线程池使用不当导致服务卡死（资深高频）

# 故障场景

自定义无界队列new LinkedBlockingQueue<Runnable>()，大量异步任务涌入，队列无限膨胀，堆内存暴涨最终 OOM。

# 线程池核心原理

ThreadPoolExecutor七大参数：核心线程数、最大线程数、空闲存活时间、阻塞队列、拒绝策略、线程工厂、异常处理器 执行流程：

  1. 任务进来 → 核心线程未满 → 创建核心线程执行
  2. 核心线程满 → 放入阻塞队列排队
  3. 队列满 → 创建非核心线程直到达到最大线程数
  4. 总线程数达上限 → 触发拒绝策略

# 4 种拒绝策略深度解读（面试官深挖）

  1. AbortPolicy 默认：直接抛 RejectedExecutionException（接口直接报错）
  2. DiscardPolicy：丢弃当前新任务，无日志（风险极高，数据丢失）
  3. DiscardOldestPolicy：丢弃队列队头最老任务
  4. CallerRunsPolicy：让提交任务的主线程执行（降级保护，生产推荐）

# 生产规范约束

  1. 禁止使用Executors.newFixedThreadPool()等快捷方法，底层无界队列埋下 OOM 隐患
  2. IO 密集型线程池核心数 = 2*CPU 核心数 + 1；CPU 密集型 = CPU 核心数
  3. 必须自定义线程池名称、全局统一管理、捕获任务异常、监控队列堆积长度

# 三、MySQL 数据库高频故障场景（8 年后端核心分水岭）

# 场景 1：简单 SQL 百万级表查询全表扫描，接口耗时几秒甚至超时

# 现象

explain 查看 type=ALL，Extra=Using filesort/Using temporary，无索引或索引失效

# 索引失效 10 大底层原因（深度版）

  1. 索引列使用函数运算：where date(create_time) = '2026-08-11' → 改成范围查询create_time between xxx
  2. 隐式类型转换：varchar 字符串字段用数字查询phone=138xxxx，自动转数字导致索引失效
  3. 最左前缀原则违背：联合索引 (a,b,c)，where 只用 b/c 查询，不走索引
  4. 不等于!=、is not null、not in、like %xxx前缀模糊匹配
  5. MySQL 优化器判定走索引回表成本高于全表扫描，自动放弃索引

# 底层原理：B + 树索引结构

  1. 叶子节点有序链表，范围查询极强；非叶子节点只存索引键 + 页指针，高度极低（3 层可存千万级数据）
  2. 回表：二级索引只存主键 ID，查到后再去聚簇索引拉完整行数据；覆盖索引select id,name直接在二级索引拿到全部数据，避免回表（极大优化）

# 优化落地步骤

  1. explain 分析执行计划，重点看 type、key、rows、Extra 字段
  2. 建立联合索引遵循等值在前、范围在后原则
  3. 避免索引列运算，杜绝隐式转换
  4. 超大表做分区、分库分表、读写分离

# 场景 2：高并发下超卖问题（库存扣减经典场景）

# 场景描述

商品库存 10，100 个并发下单，最终库存变成负数，超卖。

# 逐层解决方案 & 优缺点

  1. 版本号乐观锁（数据库层面）
update goods set stock=stock-1,version=version+1 
where id=1 and stock>0 and version=旧版本号;
1

# 场景 3：MySQL 事务失效场景（资深必问）

高频失效场景：

  1. 方法非 public，Spring AOP 无法拦截，@Transactional 不生效
  2. 方法内部调用同类加事务方法，AOP 代理失效
  3. 事务方法内捕获了所有异常try-catch(Exception)，未抛出异常，Spring 无法触发回滚
  4. 数据库引擎是 MyISAM（不支持事务），必须 InnoDB
  5. 传播行为配置错误，如 REQUIRES_NEW、SUPPORTS 导致嵌套事务不回滚

# 四、Redis 三大缓存灾难场景（面试必考三件套）

# 1. 缓存穿透：查询数据库不存在的数据（如恶意 ID=-1）

现象：Redis 查不到 → 全部穿透打到 MySQL，DB 被打垮

  • 原理：空值无缓存，恶意高频请求直接击穿缓存层
  • 解决方案：
    1. 缓存空值（设置短期过期时间，避免大量无效 key）
    2. 布隆过滤器前置拦截：将所有有效主键存入布隆过滤器，不存在直接返回，不访问 Redis 和 DB
  • 底层：布隆过滤器二进制数组 + 多个哈希函数，空间极小，百万数据仅几 MB，存在极小误判率

# 2. 缓存击穿：热点 Key 过期瞬间，大量并发涌入数据库

场景：秒杀商品 key 30 分钟过期，过期一瞬间几千请求同时查 DB

  • 解决方案：
    1. 互斥锁（Redis 分布式锁，同一时间只放行一个请求更新缓存）
    2. 永不过期：后台异步线程定时刷新热点 Key，不依赖过期删除

# 3. 缓存雪崩：大量 Key 同时集中过期，批量失效压垮 DB

根因：批量设置相同过期时间、Redis 集群宕机

  • 解决方案：
    1. 过期时间加随机偏移值 expireTime = 30*60 + new Random().nextInt(600) 打散过期峰值
    2. Redis 集群高可用（主从 + 哨兵 / Cluster 集群）
    3. 多级降级：本地 Caffeine 二级缓存、服务熔断限流

# 深挖底层：Redis 过期删除策略

  1. 惰性删除：访问 key 时才判断是否过期（节省 CPU，浪费内存）
  2. 定期删除：后台线程抽样扫描过期 key
  3. 内存淘汰策略（maxmemory-policy）：生产常用volatile-lru，只淘汰带过期时间的 LRU 最少使用 key

# 五、Spring 框架深度场景题

# 场景 1：Spring Bean 循环依赖报错

# 场景

A 依赖 B，B 依赖 A，构造器注入直接启动报错，Setter 注入正常。

# 底层三级缓存原理（核心）

  1. 一级缓存 singletonObjects：完整初始化好的成品 Bean
  2. 二级缓存 earlySingletonObjects：实例化完成但未填充属性的半成品 Bean
  3. 三级缓存 singletonFactories：存放 Bean 工厂 ObjectFactory，用于生成 AOP 代理对象

执行流程： A 实例化→放入三级缓存→填充属性发现需要 B→实例化 B→B 填充属性需要 A→从三级缓存取出 A 的代理半成品放入二级缓存→B 完成初始化放入一级缓存→A 继续完成属性填充，解决循环依赖。

# 关键结论

  1. 构造器注入无法解决循环依赖：实例化阶段就需要对方对象，三级缓存还未创建；
  2. Setter / 字段注入可以依靠三级缓存解决；
  3. 原型 scope Bean 天生不支持循环依赖。

# 场景 2：Spring 事务传播行为混乱导致回滚异常

高频面试传播行为：

  1. REQUIRED（默认）：有事务加入当前，无则新建（最常用）
  2. REQUIRES_NEW：新开独立事务，外层回滚不影响内层已提交事务
  3. NESTED：嵌套事务，依赖外层事务，外层回滚嵌套一并回滚

# 六、分布式微服务一致性场景（架构师级别面试题）

# 场景：分布式事务，跨多个微服务、多个数据库要么全部成功要么全部回滚

# 四种方案逐层对比（讲出优缺点体现深度）

  1. 2PC 两段提交（Seata AT 模式） 原理：一阶段执行业务 SQL 记录 undo_log 回滚日志、锁定资源；二阶段提交删除日志 / 回滚释放锁 优点：侵入小，代码改动少；缺点：协调者阻塞，性能一般，长事务锁资源
  2. TCC 柔性事务 Try（预留资源）→Confirm（确认提交）→Cancel（撤销释放），完全手动编码 优点：性能最高，无锁阻塞；缺点：侵入极强，开发成本大
  3. SAGA 事务 正向执行 + 逆向补偿回滚，适合长流程、跨系统事务（订单 + 库存 + 支付）
  4. 本地消息表 + 可靠消息最终一致性（MQ） 本地事务操作业务表 + 消息表，MQ 投递消息，消费方执行失败不断重试，最终一致 生产最稳妥、使用最多的方案，解耦、高可用、无锁阻塞。
