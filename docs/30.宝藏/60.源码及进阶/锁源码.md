# 第一章 AbstractQueuedSynchronizer（AQS）完整源码深度剖析

## 1. 顶层结构与核心属性源码

```
public abstract class AbstractQueuedSynchronizer
    extends AbstractOwnableSynchronizer
    implements java.io.Serializable {

    // 1. 同步状态，核心变量，volatile保证可见性
    private volatile int state;

    // 2. CLH双向阻塞队列头尾节点
    private transient volatile Node head;
    private transient volatile Node tail;

    // 3. 内部等待队列Node静态内部类
    static final class Node {
        // 共享模式标记
        static final Node SHARED = new Node();
        // 独占模式标记
        static final Node EXCLUSIVE = null;

        // waitStatus 节点状态值
        static final int CANCELLED =  1;    // 线程取消，中断/超时，失效节点
        static final int SIGNAL    = -1;    // 后继节点需要被唤醒
        static final int CONDITION = -2;    // 在Condition条件队列等待
        static final int PROPAGATE = -3;    // 共享模式下状态向后传播

        volatile int waitStatus;
        volatile Node prev;    // 前驱指针
        volatile Node next;    // 后继指针
        volatile Thread thread; // 绑定阻塞线程
        Node nextWaiter;        // Condition条件队列下一个节点

        // 判断是否共享节点
        final boolean isShared() {
            return nextWaiter == SHARED;
        }
        // 获取有效前驱节点，跳过取消节点
        final Node predecessor() throws NullPointerException {
            Node p = prev;
            while (p.waitStatus == CANCELLED)
                p = p.prev;
            prev = p;
            return p;
        }
    }
}
```

### 源码关键点解读

1. **state 为什么是 volatile int**
    - volatile 保证多线程修改的内存可见性；
    - CAS（`Unsafe.compareAndSwapInt`）依赖 volatile 的内存屏障防止指令重排；
    - int 32 位可以被读写锁拆分为高低 16 位使用。
2. **Node 双向链表设计源码意图**`predecessor()` 方法是核心：当前驱节点被取消（CANCELLED=1）时，向前回溯找到有效前驱，并修正指针，单向链表无法完成回溯清理失效节点，这是双向链表唯一不可替代的价值。
3. waitStatus 5 种状态流转规则（源码死记）
    - 0：初始默认状态；
    - SIGNAL (-1)：前驱节点执行完必须唤醒我；
    - CANCELLED (1)：永久失效，队列中会被 GC 清理；
    - CONDITION (-2)：脱离主 AQS 队列，在 Condition 单向条件队列；
    - PROPAGATE (-3)：共享锁释放时唤醒多个后继。

## 2. AQS 独占模式获取锁 `acquire()` 完整源码逐行拆解

### 入口源码

```
public final void acquire(int arg) {

    if (!tryAcquire(arg) &&
        acquireQueued(addWaiter(Node.EXCLUSIVE), arg))
```

#### 第一层：`tryAcquire(arg)` 钩子方法（留给子类实现）

AQS 空实现，抛出异常，由 ReentrantLock 等子类重写：


#### 第二层：`addWaiter(Node mode)` 将线程封装 Node 并入队源码

```
private Node addWaiter(Node mode) {
    // 1. 新建Node绑定当前线程
    Node node = new Node(Thread.currentThread(), mode);
    // 快速尝试CAS插入队尾
    Node pred = tail;
    if (pred != null) {
        node.prev = pred;
        if (compareAndSetTail(pred, node)) {
            pred.next = node;
            return node;
        }
    }
    // CAS失败进入自旋死循环入队enq
    enq(node);
    return node;
}

// 自旋CAS插入队尾，无限循环直到成功
private Node enq(final Node node) {
    for (;;) {
        Node t = tail;
        if (t == null) {
            // 队列为空，初始化head虚拟头节点
            if (compareAndSetHead(new Node()))
                tail = head;
        } else {
            node.prev = t;
            if (compareAndSetTail(t, node)) {
                t.next = node;
                return t;
            }
        }
    }
}
```

**源码重点**：

- 头节点是**空虚拟节点**，不绑定任何线程，仅作为哨兵；
- 先快速一次 CAS，失败再无限自旋，减少循环次数提升性能。

#### 第三层：核心阻塞自旋方法 `acquireQueued` 超长源码

```
final boolean acquireQueued(final Node node, int arg) {
    boolean failed = true;
    try {
        boolean interrupted = false;
        for (;;) {
            // 获取有效前驱
            final Node p = node.predecessor();
            // 只有前驱是head头节点，才有资格尝试抢锁
            if (p == head && tryAcquire(arg)) {
                // 抢到锁，把自己设为新head，清空线程引用
                setHead(node);
                p.next = null; // 旧head脱离链表，帮助GC
                failed = false;
                return interrupted;
            }
            // 判断是否需要park阻塞
            if (shouldParkAfterFailedAcquire(p, node) &&
                parkAndCheckInterrupt())
                interrupted = true;
        }
    } finally {
        if (failed)
            cancelAcquire(node);
    }
}
```

##### 子方法 1：`shouldParkAfterFailedAcquire` 修改前驱状态为 SIGNAL

```
private static boolean shouldParkAfterFailedAcquire(Node pred, Node node) {
    int ws = pred.waitStatus;
    if (ws == Node.SIGNAL)
        // 前驱标记为SIGNAL，执行完会唤醒我，可以安心park
        return true;
    if (ws > 0) {
        // 前驱取消，持续向前删除所有取消节点
        do {
            node.prev = pred = pred.prev;
        } while (pred.waitStatus > 0);
        pred.next = node;
    } else {
        // ws=0/PROPAGATE，CAS把前驱改为SIGNAL
        compareAndSetWaitStatus(pred, ws, Node.SIGNAL);
    }
    return false;
}
```

##### 子方法 2：`parkAndCheckInterrupt` 阻塞线程

```
private final boolean parkAndCheckInterrupt() {
    LockSupport.park(this);
    // 返回是否被中断唤醒
    return Thread.interrupted();
}
```

**acquireQueued 完整执行逻辑总结（源码背诵版）**

1. 死循环获取前驱节点；
2. 只有前驱是 head 才允许调用 tryAcquire 抢锁；
3. 抢不到就把前驱状态改为 SIGNAL，调用 LockSupport.park 阻塞；
4. 被 unpark 唤醒后再次循环竞争；
5. 抢到锁后替换 head，断开旧节点引用，GC 回收；
6. 如果中途线程被中断，记录中断标记，最终上层`selfInterrupt()`补上中断。

#### 第四层：`selfInterrupt()` 补充中断

```
private static void selfInterrupt() {
    Thread.currentThread().interrupt();
}
```

原因：park 唤醒时会清除中断标记，必须手动恢复中断状态。

## 3. AQS 独占锁释放 `release()` 源码解析

```
public final boolean release(int arg) {
    // 子类执行释放逻辑
    if (tryRelease(arg)) {
        Node h = head;
        // head不为空且状态不是初始0，唤醒后继节点
        if (h != null && h.waitStatus != 0)
            unparkSuccessor(h);
        return true;
    }
    return false;
}

// 唤醒头节点后继有效节点
private void unparkSuccessor(Node node) {
    int ws = node.waitStatus;
    // 先把head状态归零
    if (ws < 0)
        compareAndSetWaitStatus(node, ws, 0);

    Node s = node.next;
    // 后继为空或者被取消，从tail倒着找最前面有效节点
    if (s == null || s.waitStatus > 0) {
        s = null;
        for (Node t = tail; t != null && t != node; t = t.prev)
            if (t.waitStatus <= 0)
                s = t;
    }
    if (s != null)
        LockSupport.unpark(s.thread);
}
```

**源码亮点**：
释放唤醒时**从尾部向前遍历**找有效节点，因为 next 指针在并发入队时可能未完成赋值，prev 指针永远可靠，避免漏唤醒。

## 4. AQS 共享模式 acquireShared /releaseShared 简要源码

```
public final void acquireShared(int arg) {
    // tryAcquireShared 返回负数代表获取失败
    if (tryAcquireShared(arg) < 0)
        doAcquireShared(arg);
}
```

共享模式核心差异：

1. 获取成功后会执行`setHeadAndPropagate`，向后传播唤醒多个读线程；
2. ReentrantReadWriteLock 读锁、Semaphore、CountDownLatch 全部走这套共享逻辑。

# 第二章 ReentrantLock 完整源码逐行深度解析

## 1. ReentrantLock 外层类结构源码

```
public class ReentrantLock implements Lock, java.io.Serializable {
    // 核心同步器对象，多态指向公平/非公平内部类
    private final Sync sync;

    // 默认构造：非公平锁
    public ReentrantLock() {
        sync = new NonfairSync();
    }
    // 传入boolean选择公平/非公平
    public ReentrantLock(boolean fair) {
        sync = fair ? new FairSync() : new NonfairSync();
    }

    // 委托给sync调用AQS模板方法
    public void lock() {
        sync.acquire(1);
    }
    public void unlock() {
        sync.release(1);
    }
    public Condition newCondition() {
        return sync.newCondition();
    }

    // 抽象内部Sync，继承AQS
    abstract static class Sync extends AbstractQueuedSynchronizer {
        // 模板：释放锁逻辑，公平非公平共用
        protected final boolean tryRelease(int releases) {
            int c = getState() - releases;
            // 非持有线程释放直接抛异常
            if (Thread.currentThread() != getExclusiveOwnerThread())
                throw new IllegalMonitorStateException();
            boolean free = false;
            if (c == 0) {
                free = true;
                setExclusiveOwnerThread(null);
            }
            setState(c);
            return free;
        }
        // 判断是否当前线程持有锁
        final boolean isHeldExclusively() {
            return getExclusiveOwnerThread() == Thread.currentThread();
        }
        final ConditionObject newCondition() {
            return new ConditionObject();
        }
    }
}
```

## 2. 非公平锁 NonfairSync 内部类源码（重点）

```
static final class NonfairSync extends Sync {
    // 重写AQS独占获取钩子
    protected final boolean tryAcquire(int acquires) {
        final Thread current = Thread.currentThread();
        int c = getState();
        if (c == 0) {
            // 【非公平核心】不判断队列，直接CAS抢占
            if (compareAndSetState(0, acquires)) {
                setExclusiveOwnerThread(current);
                return true;
            }
        }
        // 可重入逻辑：当前线程已经持有锁，state累加
        else if (current == getExclusiveOwnerThread()) {
            int nextc = c + acquires;
            if (nextc < 0) // int溢出
                throw new Error("Maximum lock count exceeded");
            setState(nextc);
            return true;
        }
        return false;
    }
}
```

### 源码核心差异一句话

非公平锁`c==0`时**直接 CAS 插队**，无视 CLH 队列中排队的线程。

## 3. 公平锁 FairSync 内部类源码

```
static final class FairSync extends Sync {
    protected final boolean tryAcquire(int acquires) {
        final Thread current = Thread.currentThread();
        int c = getState();
        if (c == 0) {
            // 【公平锁核心】先判断队列是否有前驱排队
            if (!hasQueuedPredecessors() &&
                compareAndSetState(0, acquires)) {
                setExclusiveOwnerThread(current);
                return true;
            }
        }
        // 可重入逻辑和非公平完全一致
        else if (current == getExclusiveOwnerThread()) {
            int nextc = c + acquires;
            if (nextc < 0)
                throw new Error("Maximum lock count exceeded");
            setState(nextc);
            return true;
        }
        return false;
    }
}
```

### 关键方法 `hasQueuedPredecessors()` 源码

```
public final boolean hasQueuedPredecessors() {
    Node t = tail;
    Node h = head;
    Node s;
    return h != t &&
        ((s = h.next) == null || s.thread != Thread.currentThread());
}
```

逻辑翻译：
队列不为空，并且头节点下一个有效节点不是当前线程 → 返回 true，代表有线程排队，放弃 CAS 抢锁。

## 4. ReentrantLock 可重入源码实现总结

1. `tryAcquire` 中判断 `current == getExclusiveOwnerThread()`；
2. `state = state + 1` 累加计数；
3. `tryRelease` 中每次`state -1`，只有减到 0 才算完全释放；
4. **加锁 n 次必须解锁 n 次**，否则 state 不为 0 死锁。

## 5. LockSupport.park 底层补充源码原理

`LockSupport`底层调用`Unsafe.park(boolean isAbsolute, long time)`，依赖操作系统内核：

- Linux：pthread_mutex + pthread_cond 条件变量；
- Windows：WaitForSingleObject；  

优势：

1. 不需要 synchronized 监视器包裹；
2. unpark 可以先执行，持有许可，后续 park 直接放行；
3. 精准阻塞指定线程，而 Object.wait 只能随机唤醒。


### LockSupport.park() 大白话彻底拆解（用法+场景+代码示例+和wait区别）

#### 一、先建立最简单模型：每个线程自带一张「通行证」

JVM 给每一个 Java 线程内部维护了一个**只有 0 和 1 的标记（permit 许可）**

- 0 = 没有通行证
- 1 = 有一张通行证
  **通行证规则死记：最多只能存 1 张，发多少次都只算1张**

##### 两个核心方法就是操作这张通行证

1. `LockSupport.park()`
   检查自己线程的通行证：
    - 有通行证（1）：直接把通行证销毁（变成0），方法立刻结束，线程继续往下跑
    - 无通行证（0）：线程直接卡住、休眠、放弃CPU，进入 WAITING 等待状态
2. `LockSupport.unpark(Thread t)`
   给指定线程 t 发一张通行证：
    - 如果t当前通行证是0 → 变成1
    - 如果t已经是1 → 啥事不做（不会叠加成2）

### 二、4个最直观运行案例，一看就懂

#### 案例1：先park，后unpark（常规阻塞唤醒）

```
public class ParkDemo1 {
    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(() -> {
            System.out.println("线程t1开始执行，准备park阻塞");
            LockSupport.park(); // 没有通行证，卡住
            System.out.println("线程t1被唤醒，继续执行");
        });

        t1.start();
        Thread.sleep(2000); // 主线程等2秒
        System.out.println("主线程准备给t1发通行证unpark");
        LockSupport.unpark(t1);
    }
}
```

执行流程：

1. t1 执行 park，通行证0 → 阻塞
2. 2秒后主线程 unpark(t1)，通行证变为1
3. t1 被唤醒，park消耗通行证变回0，继续打印

### 案例2：先 unpark 发通行证，后 park（重点：顺序无关）

```
public class ParkDemo2 {
    public static void main(String[] args) {
        Thread t1 = new Thread(() -> {
            System.out.println("t1 马上执行park");
            LockSupport.park();
            System.out.println("t1 直接通过，没有阻塞");
        });

        // 先提前发通行证
        LockSupport.unpark(t1);
        t1.start();
    }
}
```

结果：**t1 完全不会阻塞**
原因：
unpark 提前给t1通行证置为1，后面调用park直接消耗掉，一秒都不卡。
👉 这是和 `wait/notify` 最大的分水岭：wait必须先等待再通知，反过来永久死等。

### 三、park 三个重载方法完整用法

```
// 1. 无限阻塞，直到 unpark 或者被中断
LockSupport.park();

// 2. 最多阻塞多少纳秒，超时自动唤醒
LockSupport.parkNanos(1000000000);

// 3. 阻塞到某个绝对时间戳（毫秒）

LockSupport.parkUntil(deadline);
```

### 四、park() 与 Object.wait() 核心区别（彻底分清）

| 特性 | LockSupport.park() | synchronized + wait() |
| --- | --- | --- |
| 是否需要锁 | 不需要任何同步锁，随便调用 | 必须先拿到对象监视器，否则直接报错 |
| 执行顺序 | unpark先发后park也生效 | 必须先wait再notify，顺序颠倒死锁 |
| 唤醒粒度 | unpark精准唤醒**指定单个线程** | notify随机唤醒一个，notifyAll全部唤醒 |
| 中断响应 | 唤醒不抛异常，仅清除中断标记 | 抛出 InterruptedException |
| 锁释放 | park 完全不释放synchronized锁 | wait 执行瞬间释放监视器锁 |

#### 举个反例：wait 顺序颠倒直接死锁

```
Object lock = new Object();
new Thread(()->{
    try {
        Thread.sleep(1000);
        synchronized (lock){
            lock.wait();
        }
    } catch (InterruptedException e) {
    }
}).start();

// 先notify，后wait，永久卡死
synchronized (lock){
    lock.notify();
}
```

### 五、LockSupport 到底用来干什么？（实际业务&底层用途）

#### 用途1：JUC AQS 并发包底层唯一阻塞工具（最重要）

ReentrantLock、读写锁、CountDownLatch、Semaphore 所有锁排队阻塞线程，全部依赖它：

1. 多个线程抢锁失败，进入AQS双向CLH队列排队
2. 排队的线程调用 `LockSupport.park()` 挂起，不占用CPU空转
3. 上一个线程释放锁时，调用 `LockSupport.unpark(下一个线程)` 精准唤醒
   为什么不用 wait/notify？

- AQS队列是自己实现的，不想绑定synchronized监视器锁
- 需要精准唤醒某一个后继节点，notify做不到
- 需要处理中断、超时获取锁（tryLock(time)），park重载天然支持

#### 用途2：手写简单阻塞队列、自定义同步器

自己实现一个简易生产者消费者，不用synchronized的Condition，用LockSupport手动控制线程启停。

示例简易生产者消费者：

```
public class SimpleQueue {
    private Queue<String> queue = new LinkedList<>();
    private int maxSize = 5;
    private Thread consumer;

    public void produce(String msg) {
        if (queue.size() >= maxSize) {
            LockSupport.park(); // 满了，生产者阻塞
        }
        queue.add(msg);
        System.out.println("生产：" + msg);
        LockSupport.unpark(consumer); // 唤醒消费者
    }

    public void consume() {
        consumer = Thread.currentThread();
        while (true) {
            if (queue.isEmpty()) {
                LockSupport.park(); // 空了，消费者阻塞
            }
            String poll = queue.poll();
            System.out.println("消费：" + poll);
        }
    }
}
```

#### 用途3：线程休眠可控工具（业务开发极少用，框架底层多）

比如定时任务框架、线程池空闲线程挂起、自定义自旋锁的阻塞逻辑。

## 六、极简总结背诵版

1. 本质：**基于线程内部1张唯一许可（permit）的阻塞工具**
2. `park()`：有许可就消耗放行，无许可就阻塞线程；
3. `unpark(线程)`：给目标线程发放许可，最多1张，重复调用无效；
4. 优点：无需同步锁、唤醒顺序不限、精准单线程唤醒、支持超时阻塞；
5. 核心价值：JDK AQS 并发锁体系底层依赖的线程挂起原语，普通业务几乎不用，面试+看JUC源码必须吃透。

# 第三章 ReentrantReadWriteLock 读写锁源码深度拆解

## 1. 外层类结构与 state 拆分源码

```
public class ReentrantReadWriteLock
        implements ReadWriteLock, java.io.Serializable {
    private final ReadLock readerLock;
    private final WriteLock writerLock;
    final Sync sync;

    public ReentrantReadWriteLock() {
        this(false);
    }
    public ReentrantReadWriteLock(boolean fair) {
        sync = fair ? new FairSync() : new NonfairSync();
        readerLock = new ReadLock(this);
        writerLock = new WriteLock(this);
    }

    // 读写锁视图，内部直接委托sync
    public ReadLock readLock()  { return readerLock; }
    public WriteLock writeLock(){ return writerLock; }

    // 核心Sync继承AQS
    abstract static class Sync extends AbstractQueuedSynchronizer {
        // 移位常量：16位
        static final int SHARED_SHIFT   = 16;
        // 读锁单位增量 65536
        static final int SHARED_UNIT    = (1 << SHARED_SHIFT);
        // 最大读锁计数 65535
        static final int MAX_COUNT      = (1 << SHARED_SHIFT) - 1;
        // 写锁掩码，取低16位
        static final int EXCLUSIVE_MASK = (1 << SHARED_SHIFT) - 1;

        // 取低16位 = 写锁重入次数
        static int countOfWrite(int c) {
            return c & EXCLUSIVE_MASK;
        }
        // 右移16位 = 读锁持有线程总数
        static int countOfRead(int c) {
            return c >>> SHARED_SHIFT;
        }
    }
}
```

### state 32 位拆分源码规则（死记）

- 高 16 位：读锁共享计数，每次读锁 +`SHARED_UNIT(65536)`；
- 低 16 位：写锁独占重入次数，每次写锁 + 1；
  计算公式：

```
写锁状态 = state & 0x0000FFFF
读锁状态 = state >>> 16
```

## 2. WriteLock 写锁独占模式 tryAcquire 源码

```
protected final boolean tryAcquire(int acquires) {
    Thread current = Thread.currentThread();
    int c = getState();
    int w = countOfWrite(c);

    // 分支1：已有读锁占用 或者 其他线程持有写锁，直接失败
    if (countOfRead(c) != 0 || w != 0 && current != getExclusiveOwnerThread())
        return false;

    // 分支2：写锁重入溢出校验
    if (w + acquires > MAX_COUNT)
        throw new Error("Write lock count overflow");

    // CAS修改state，低16位+1
    if (compareAndSetState(c, c + acquires)) {
        setExclusiveOwnerThread(current);
        return true;
    }
    return false;
}
```

核心约束源码体现：
只要**读锁计数 > 0**，写锁永远获取失败，保证读写互斥。

## 3. ReadLock 读锁共享模式 tryAcquireShared 源码

```
protected final int tryAcquireShared(int unused) {
    Thread current = Thread.currentThread();
    int c = getState();
    // 存在写锁且不是自己持有，直接返回-1获取失败
    if (countOfWrite(c) != 0 && getExclusiveOwnerThread() != current)
        return -1;

    int r = countOfRead(c);
    // 读锁计数溢出判断
    if (r >= MAX_COUNT)
        throw new Error("Read lock overflow");

    // CAS高16位+65536
    if (compareAndSetState(c, c + SHARED_UNIT)) {
        return 1; // 共享获取成功，返回正数
    }
    // CAS自旋重试逻辑省略...
}
```

## 4. 锁降级源码官方标准实现（源码级原理）

### 降级定义源码逻辑

1. 当前线程持有**写锁（独占）**；
2. 在写锁未释放时调用`readLock.lock()`获取读锁；
3. 执行`writeLock.unlock()`释放写锁；
4. 此时线程仅持有读锁，完成降级。

```
// 锁降级标准源码模板
rwLock.writeLock().lock();
try {
    // 关键：持有写锁期间先获取读锁
    rwLock.readLock().lock();
    // 修改共享数据
} finally {
    // 先释放写锁，读锁仍持有
    rwLock.writeLock().unlock();
}
// 后续读操作
try {
} finally {
    rwLock.readLock().unlock();
}
```

### 源码层面为什么不支持锁升级？

读锁是共享模式，多个线程同时持有读锁，写锁`tryAcquire`判断读计数≠0 直接返回 false，永远无法 CAS 成功，死循环阻塞。

## 5. 读写锁源码遗留缺陷：写饥饿

大量读线程持续占用高 16 位读计数，写锁线程在 AQS 队列长期阻塞，JDK 官方解决方案：`StampedLock`乐观读，底层 CAS 版本戳校验，放弃可重入换取高并发性能。

# 第四章 Condition 条件队列完整源码解析（AQS 第二套队列）

## 1. ConditionObject 内部类核心结构

```
public class ConditionObject implements Condition, java.io.Serializable {
    // 条件队列单向链表首尾
    private transient Node firstWaiter;
    private transient Node lastWaiter;

    // await() 释放锁进入条件队列阻塞
    public final void await() throws InterruptedException {
        if (Thread.interrupted())
            throw new InterruptedException();
        // 1. 将当前线程封装Node加入Condition单向队列
        Node node = addConditionWaiter();
        // 2. 完全释放AQS独占锁，state归零
        int savedState = fullyRelease(node);
        int interruptMode = 0;
        // 3. 自旋判断是否被转移回AQS主队列
        while (!isOnSyncQueue(node)) {
            LockSupport.park(this);
            // 处理中断
            if ((interruptMode = checkInterruptWhileWaiting(node)) != 0)
                break;
        }
        // 4. 重新竞争AQS主锁
        if (acquireQueued(node, savedState) && interruptMode != THROW_IE)
            interruptMode = REINTERRUPT;
        // 清理条件队列取消节点
        if (node.nextWaiter != null)
            unlinkCancelledWaiters();
        // 抛出中断或自中断
        if (interruptMode != 0)
            reportInterruptAfterWait(interruptMode);
    }

    // signal 唤醒条件队列头节点
    public final void signal() {
        // 必须持有独占锁才能调用signal
        if (!isHeldExclusively())
            throw new IllegalMonitorStateException();
        Node first = firstWaiter;
        if (first != null)
            doSignal(first);
    }
}
```

### Condition 完整流转源码流程

1. `await()`：调用`fullyRelease`释放 AQS 锁，Node.waitStatus 改为 CONDITION (-2)，进入 Condition**单向等待队列**；
2. `signal()`：将 Condition 队首 Node 的 waitStatus 改为 0，转移到 AQS**主 CLH 双向队列**尾部排队；
3. 被 AQS 队列前驱 unpark 唤醒后，重新竞争锁；

### 和 Object.wait/notify 源码本质区别

- synchronized 监视器只有**1 个等待集合**，notifyAll 全部唤醒；
- 一个 Lock 可以 new 多个 Condition，每个独立单向队列，`signal()`精准唤醒某一组线程，粒度更细。

缺陷源码层面：

2. 同一线程多次加锁无法识别，不可重入；

## 1. Redisson RLock 可重入锁 **加锁 Lua 完整源码**

```
-- ARGV[1] = 过期时间毫秒
-- ARGV[2] = 线程唯一标识（UUID:ThreadId）
if redis.call('exists', KEYS[1]) == 0 then
    -- 锁不存在，Hash结构存入，重入计数=1
    redis.call('hset', KEYS[1], ARGV[2], 1)
    redis.call('pexpire', KEYS[1], ARGV[1])
    return nil
end
-- 锁已存在，判断是否当前持有线程
if redis.call('hexists', KEYS[1], ARGV[2]) == 1 then
    -- 重入计数+1
    redis.call('hincrby', KEYS[1], ARGV[2], 1)
    redis.call('pexpire', KEYS[1], ARGV[1])

end
```

- Hash 结构`key:{线程标识:重入次数}`天然实现可重入；
- 整段 Lua 在 Redis 单线程原子执行，无并发竞态。

## 3. WatchDog 看门狗后台续期任务源码逻辑（Java 层）

```
private void scheduleExpirationRenewal(long threadId) {
    ExpirationEntry entry = new ExpirationEntry();
    ExpirationEntry old = EXPIRATION_RENEWAL_MAP.putIfAbsent(getEntryName(), entry);
    if (old != null) {
        old.addThreadId(threadId);
    } else {
        // 定时任务，默认3秒执行一次（锁默认10s，1/3时间）
        renewExpiration();
    }
}

private void renewExpiration() {
    Timeout task = commandExecutor.getServiceManager().newTimeout(new TimerTask() {
        @Override
        public void run(Timeout timeout) throws Exception {
            ExpirationEntry ent = EXPIRATION_RENEWAL_MAP.get(getEntryName());
            if (ent == null) return;
            Long threadId = ent.getFirstThreadId();
            if (threadId == null) return;

            // 执行续期Lua脚本
            RFuture<Boolean> future = renewExpirationAsync(threadId);
            future.onComplete((res, e) -> {
                if (res) {
                    // 递归再次调度，循环续期
                    renewExpiration();
                }
            });
        }
    }, internalLockLeaseTime / 3, TimeUnit.MILLISECONDS);
}
```

### 看门狗源码规则

1. 只有调用无参`lock()`才启动自动续期；
2. 手动传入`leaseTime`过期时间，**直接禁用看门狗**，业务自己处理续期；
3. `unlock()`时删除`EXPIRATION_RENEWAL_MAP`中的任务，终止递归定时。

## 4. Redisson 红锁 RedLock 源码核心思想（解决主从锁丢失）

1. 传入 N 个独立 Redis 主节点；
2. 循环向每个节点执行加锁 Lua；

4. 释放时遍历所有节点统一删除 key；
   牺牲性能换取集群分布式锁强可靠性。

# 第六章 AQS 衍生工具类极简源码拆解（CountDownLatch / Semaphore / CyclicBarrier）

## 1. CountDownLatch 源码（AQS 共享模式）

```
public class CountDownLatch {
    private final Sync sync;
    private static final class Sync extends AQS {
        Sync(int count) {
            setState(count);
        }
        // 共享获取：state>0 返回-1阻塞
        protected int tryAcquireShared(int acquires) {
            return (getState() == 0) ? 1 : -1;
        }
        // 共享释放：state自减1
        protected boolean tryReleaseShared(int releases) {
            for (;;) {
                int c = getState();
                if (c == 0) return false;
                int next = c - 1;
                if (compareAndSetState(c, next))
                    return next == 0;
            }
        }
    }
}
```

要点：一次性计数器，state 归 0 永久放行，无法 reset。

## 2. Semaphore 信号量源码（AQS 共享）

state = 许可总数，`acquire()` state-1，`release()` state+1，支持公平 / 非公平，用于接口限流、池化资源控制。

## 3. CyclicBarrier 源码（**不基于 AQS**）

底层组合：`ReentrantLock + Condition`

```
private final ReentrantLock lock = new ReentrantLock();
private final Condition trip = lock.newCondition();
```

逻辑：

1. 每调用`await()`计数器 - 1；
2. 计数器为 0 时`trip.signalAll()`批量唤醒；
3. 自动重置计数器，循环使用。

# 第七章 高频源码面试追问（直接背答案）

1. **AQS 为什么 CLH 队列要用双向链表？**
   源码`predecessor()`方法需要向前回溯清理 CANCELLED 失效节点，单向链表无法反向遍历。
2. **ReentrantLock 非公平锁吞吐量更高源码原因？**`tryAcquire`中`c==0`直接 CAS 插队，跳过`hasQueuedPredecessors()`队列判断，减少上下文切换。
3. **读写锁 state 拆高低 16 位源码为什么用 int 不用 long？**
   32 位 int 足够拆分，JDK8 中 CAS 操作 int 比 long 更轻量，满足最大 65535 读锁并发上限。
4. **Condition await 为什么必须先 fullyRelease 释放全部 state？**
   当前线程持有 n 次可重入锁，必须一次性清空 state，否则其他线程无法获取锁，源码`fullyRelease`循环递减到 0。
5. **Redisson 看门狗为什么 1/3 时间续一次？**
   预留网络延迟、Redis 执行耗时，避免刚好到期才续期导致锁过期失效。
