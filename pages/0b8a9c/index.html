高并发短链接系统设计

# 自研高并发短链接系统完整架构设计（生产级落地版）

# 一、需求分析与业务痛点

# 1. 核心功能

  1. 长URL压缩生成唯一短链接（如https://xxx.cn/s/Abc123）
  2. 访问短链接302/301重定向跳转原长地址
  3. 访问数据统计：UV、PV、访问设备、IP、浏览器、访问时间、地域
  4. 短链接有效期设置、过期自动失效、批量管理、黑名单拦截恶意网址
  5. 防刷限流、重复生成去重、高并发大流量跳转不雪崩

# 2. 现有方案痛点

  • 纯自增ID转62进制简单方案：ID泄露、可遍历猜解所有短链、不安全；
  • 数据库单表存储：海量数据分库分表困难，查询慢；
  • 无缓存层：每次跳转都查DB，高并发下数据库直接打垮；
  • 缺少过期清理、访问统计、风控拦截等企业级能力。

# 3. 非功能设计目标

  1. 超高并发：跳转QPS支撑10w+/s，核心路径不走DB；
  2. 唯一性：全局不重复短码，不可逆、不可遍历猜测；
  3. 高性能：Redis全量缓存热点数据，毫秒级响应；
  4. 海量存储：支持亿级短链接存储，MySQL分库分表平滑扩容；
  5. 安全可控：恶意URL黑名单、访问限流、过期自动失效；
  6. 可观测：完整访问日志、数据分析、告警机制。

# 4. 核心技术难点

  1. 全局唯一短码生成，分布式多实例下无重复、无冲突；
  2. 高并发跳转请求避免穿透数据库，缓存雪崩/击穿/穿透防护；
  3. 亿级短链接数据MySQL分库分表路由规则设计；
  4. 访问量统计异步化，避免主链路阻塞；
  5. 过期短链接自动清理、无效数据定时回收；
  6. 分布式ID生成器高性能、高可用落地。

# 二、整体分层架构（自上而下全链路）

客户端请求 → Nginx负载均衡层
    ↓
网关层（限流、黑名单、请求校验）
    ↓
两大核心业务模块：
1. 短链接生成服务（写链路，低频）
2. 短链接跳转解析服务（读链路，超高并发）
    ↓
缓存层（Redis集群，热点短码全量缓存）
    ↓
持久化存储层（MySQL分库分表 + 定时归档）
    ↓
异步统计模块（MQ+ClickHouse存储访问日志）
    ↓
后台管理系统（规则配置、数据看板、过期清理）

# 模块1：Nginx接入层（性能第一道关卡）

# 核心能力

  1. 静态拦截：非法参数、超长URL、恶意User-Agent直接拦截；
  2. 负载均衡：多应用服务器轮询分发跳转请求；
  3. 二级缓存优化：Nginx本地内存缓存高频短链接，直接返回302，不转发后端；
  4. 协议优化：开启HTTP2、gzip压缩，降低网络耗时。

# 拆分路由

  • /create 短链接生成接口 → 路由到写服务集群
  • /s/* 短链接跳转接口 → 路由到读解析服务集群

# 模块2：网关风控与限流模块（复用前面自研分布式限流组件）

  1. 黑名单校验 内置恶意域名库（钓鱼、涉黄、非法网站），生成短链时直接拦截；跳转时校验目标地址防止跳转风险。
  2. 多层限流防护
  • IP粒度限流：单IP每秒最多生成N条短链，防止恶意批量刷库；
  • 接口粒度限流：生成接口低阈值，跳转接口放开高阈值；
  • Redis分布式滑动窗口算法全局计数。
  1. 请求参数校验 校验URL格式合法性、长度上限、是否内网地址（防止内网渗透扫描）。

# 模块3：核心模块一：短链接生成服务（写操作，低并发）

# 3.1 短码编码规则设计

字符集：62进制（0-9,a-z,A-Z）

chars = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"
1
  • 6位短码：62⁶ = 568亿+ 容量，满足绝大多数业务体量；
  • 7位短码：62⁷ 近3.5万亿，超大体量预留扩展。

# 3.2 三种分布式唯一ID生成方案（选型对比）

# 方案1：数据库自增主键 + 62进制转换（最简单）

缺点：ID连续递增，攻击者可遍历000001、000002猜解全部短链接，安全性差，仅内部系统使用。

# 方案2：Redis自增Incr全局ID（推荐中小体量）

Redis设置全局计数器short_link:global_id，每次生成执行INCR拿到唯一数字，转62进制得到短码。 优点：实现简单、性能高； 缺点：Redis宕机重启会重复，需持久化RDB/AOF兜底。

# 方案3：雪花算法SnowFlake（生产最终选型）

自研分布式雪花ID：时间戳+机器ID+序列号，生成64位长整型数字，再转为62进制短码。 优势：

  1. 分布式多节点完全不重复；
  2. ID无序，无法遍历猜解，安全性最高；
  3. 不依赖Redis/DB，单机也可生成，高可用极强。

雪花ID转62进制伪代码

// 雪花算法获取唯一数字ID
long uniqueId = snowflake.nextId();
// 十进制数字转为62进制字符串（6位短码）
String shortCode = Base62.encode(uniqueId);
// 不足6位补前缀字符，固定长度
shortCode = String.format("%6s", shortCode).replace(' ', '0');

# 3.3 生成完整业务流程

  1. 校验长URL合法性、是否在黑名单；
  2. 开启布隆过滤器判断该长URL是否已生成过短链（去重）；
  3. 雪花算法生成全局唯一ID，转换为62进制6位短码；
  4. 组装存储对象：短码、原始URL、创建时间、过期时间、创建人、状态（有效/过期/禁用）；
  5. 写入MySQL分库分表持久化；
  6. 同步写入Redis缓存：key=short:code:xxx value=原始长链接 + 过期时间；
  7. 返回拼接完成的短链接域名+短码。

# 3.4 布隆过滤器去重优化

问题：相同长URL多次调用生成接口，会产出多条重复短链，浪费存储。 解决：Redis布隆过滤器存储已处理过的长URL，生成前先判断：

  • 不存在 → 正常生成；
  • 已存在 → 直接返回历史已生成的短链接。

# 模块4：核心模块二：短链接跳转解析服务（读操作，超高QPS核心）

99%流量集中在此，极致性能优化重点

# 完整跳转执行时序（从上到下逐级穿透，越早拦截越好）

  1. Nginx层优先本地缓存命中 → 直接302重定向，不进Java服务；
  2. 请求到达后端，截取URL中的6位短码code；
  3. 查询Redis缓存：short:code:Abc123
    • 缓存命中：拿到原URL，执行302临时重定向；异步发送MQ记录访问日志；
    • 缓存未命中（缓存穿透）：穿透查询MySQL数据库；
  4. MySQL查询分库分表路由定位记录：
    • 查询到有效未过期数据：回写Redis，再302跳转；
    • 查询为空/已过期/已禁用：返回404页面；
  5. 异步投递消息到MQ，记录本次访问行为，主线程立刻返回响应。

# 301 vs 302 重定向选型

  • 302 临时重定向（业务首选） 浏览器不缓存跳转结果，后台修改原URL、禁用短链后立刻生效，灵活可控；
  • 301 永久重定向 浏览器长期缓存，后台修改无法实时生效，仅固定不变的静态短链使用。

# 2. 三大缓存问题防护（重中之重）

# （1）缓存穿透：查询不存在的短码大量打穿到DB

解决方案：

  1. 布隆过滤器存储所有有效短码，无效短码直接拦截；
  2. MySQL查询为空时，Redis写入空值缓存，设置短期TTL（5分钟）。
# （2）缓存击穿：热点爆款短链过期瞬间大量请求查DB

解决方案：

  1. 互斥锁（Redis SETNX）同一时间只放行一个请求去更新缓存；
  2. 后台定时主动刷新热点Key，永不过期。
# （3）缓存雪崩：大量短链接同时过期批量查库

解决方案： 给Redis过期时间增加随机偏移量，例如有效期天数*86400 + Random(0,3600)，打散过期时间。

# 3. Redis集群部署

主从+哨兵集群，开启RDB+AOF持久化，防止宕机丢失映射关系；热点短链开启本地二级缓存（Caffeine）进一步降低Redis压力。

# 模块6：MySQL分库分表持久化存储层

# 1. 存储单表字段设计

CREATE TABLE `short_link` (
  id BIGINT PRIMARY KEY COMMENT '雪花算法主键',
  short_code VARCHAR(10) NOT NULL COMMENT '6位短码',
  long_url VARCHAR(1024) NOT NULL COMMENT '原始长链接',
  expire_time DATETIME COMMENT '过期时间，NULL永久有效',
  create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
  update_time DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  creator VARCHAR(64) COMMENT '创建人/渠道',
  status TINYINT DEFAULT 1 COMMENT '1有效 0过期 2禁用',
  INDEX idx_short_code (short_code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

# 2. 分库分表路由规则（Sharding-JDBC）

分片键：short_code 短码字符串

  1. 先对shortCode做Hash取模拆分分库；
  2. 再二次Hash取模拆分分表； 示例：2库×32表 = 64张物理表，单表控制500w以内数据，查询极快。 优点：短码均匀分散，查询路由计算简单，热点数据自动打散。

# 3. 过期数据自动清理

  1. 定时任务每日凌晨扫描，将status=0过期数据迁移至历史归档表；
  2. 归档表按月分区，可冷备份至对象存储OSS，减少主表数据量；
  3. Redis中过期Key依靠TTL自动淘汰。

# 模块7：异步访问统计与大数据分析模块

# 架构链路

跳转请求 → 异步发送MQ（RocketMQ/Kafka） → 消费服务解析日志 → 写入ClickHouse

# 统计维度

  • 基础：PV总访问量、UV独立访客；
  • 客户端：操作系统、浏览器类型、设备移动端/PC；
  • 网络：访问IP、归属地省市、运营商；
  • 时间：小时/日/周/月访问趋势。

# 为什么不用MySQL统计？

亿级访问日志写入MySQL会产生海量IO压力，ClickHouse列式存储专为海量日志聚合查询设计，百万级数据秒级聚合，做数据看板、报表导出性能碾压MySQL。

# 模块8：后台管理与运维模块

  1. 短链接管理：新增、编辑目标URL、手动禁用、批量删除、设置有效期；
  2. 黑名单管理：录入恶意域名、自动拦截生成与跳转；
  3. 数据大盘：可视化图表展示访问趋势、TOP热门短链接；
  4. 定时任务
    • 过期短链接自动标记失效；
    • 归档历史冷数据；
    • Redis布隆过滤器定期重建；
  5. 告警机制
    • 生成接口限流突增告警（疑似刷量）；
    • MySQL慢查询、缓存命中率过低告警；
    • 短链接过期大批量失效通知。

# 三、一条短链接完整生命周期全流程

# 流程1：创建短链接（写流程）

  1. 用户提交长URL到/create接口；
  2. 网关校验URL格式、黑名单拦截、IP限流；
  3. Redis布隆过滤器判断是否已存在该长链接，存在直接返回旧短链；
  4. 雪花算法生成唯一ID，转为6位6位短码；
  5. 写入MySQL分库分表持久化；
  6. 写入Redis缓存，同步设置过期时间；
  7. 返回https://short.domain.cn/s/xxxxxx。

# 流程2：访问跳转（超高并发读流程）

  1. 浏览器访问https://short.domain.cn/s/Abc123；
  2. Nginx优先本地缓存命中，直接302重定向；
  3. 未命中转发后端服务，截取短码；
  4. 查询Redis缓存获取原URL：
    • 命中：异步发MQ记录访问日志，返回302跳转；
    • 未命中：路由查询MySQL，有效则回写Redis再跳转，无效返回404；
  5. 消费端异步汇总访问数据到ClickHouse做统计。

# 流程3：过期销毁

  1. Redis Key到期自动删除缓存；
  2. 定时任务扫描MySQL，更新状态为过期；
  3. 管理后台可查看失效列表，支持重新启用或删除。

# 四、高可用与可靠性闭环

  1. 接入层高可用：Nginx集群多机部署，LVS四层负载兜底；
  2. 应用层高可用：生成服务、跳转服务无状态，水平无限扩容；
  3. 缓存高可用：Redis主从哨兵集群，持久化防止数据丢失；
  4. 存储高可用：MySQL一主多从，分库分表规避单表瓶颈；
  5. 故障降级：Redis宕机降级直接查询MySQL（限流保护）；MQ宕机日志落本地文件后续补发；
  6. 安全闭环：黑名单、访问限流、内网地址拦截、ID不可遍历防爬虫。

# 五、生产落地踩坑点&解决方案

# 坑1：雪花算法多机器出现重复ID

解决：机器ID通过配置中心/Nacos动态分配，保证每台实例workerId唯一，避免重复。

# 坑2：大量无效短码请求击穿Redis打到MySQL

解决：布隆过滤器前置拦截+空值缓存双重防护。

# 坑3：短链接集中过期引发Redis雪崩

解决：TTL增加随机偏移量，打散过期时间。

# 坑4：分库分表查询跨库关联，性能变差

解决：仅用short_code单字段哈希分片，查询只走单库单表，无跨库查询。

# 坑5：访问统计同步阻塞主链路，接口RT拉高

解决：完全异步MQ解耦，主线程只做跳转，统计完全后置。

# 坑6：攻击者暴力遍历6位短码爬取全部链接

解决：1.雪花ID无序短码无法遍历；2.IP高频访问限流拦截扫描行为；3.敏感短链接后台加密管控。

# 坑7：布隆过滤器误判导致重复生成短链

解决：布隆过滤器判断存在后二次查Redis/DB二次校验，极低概率兜底。

# 六、25道高频面试题+标准答案

# 一、短码生成与ID设计（1-8）

  1. 为什么不用数据库自增ID做短码？ 答：自增ID连续可预测，黑客可以按顺序遍历所有短链接，数据泄露风险极高；雪花算法生成无序ID，无法猜解，安全性更强。

  2. 62进制字符集为什么大小写字母+数字，不用Base64？ 答：Base64包含+ / =等特殊字符，放在URL中需要URL编码，会导致短链接变长、可读性变差，62进制全部使用URL安全字符。

  3. 雪花算法结构简单说一下，如何保证分布式不重复？ 答：由时间戳（毫秒级）+机器ID+序列号组成；同一毫秒同一机器下序列号自增，不同机器workerId不同，全局保证唯一性。

  4. 布隆过滤器在短链接系统的作用？有什么缺点？ 答：作用是对长URL去重，避免同一地址重复生成短链；缺点存在极小概率误判，只能判断“一定不存在”，不能判断“一定存在”，需要二次校验。

  5. Redis自增ID和雪花算法各自适用场景？ 答：Redis自增适合单体、中小并发内部系统；雪花算法适合分布式集群、高并发、对外公网服务，不依赖中间件更健壮。

  6. 固定6位短码容量怎么计算？ 答：62的6次方，约56.8亿条，足以支撑绝大多数业务，不够直接升级7位短码。

  7. 短链接为什么设置过期时间？ 答：清理无效冷数据，减少Redis内存占用和MySQL存储压力，同时管控营销活动有效期。

  8. 生成时如何防止重复短码？ 答：底层依赖全局唯一ID源（雪花/Redis Incr），ID唯一则转出来的62进制短码天然唯一，不会碰撞。

# 二、缓存、高并发、数据库（9-18）

  1. 跳转接口QPS极高，如何做多层缓存优化？ 答：三层缓存：Nginx本地缓存 → 应用Caffeine本地缓存 → Redis分布式缓存，层层拦截，尽量不碰数据库。

  2. 短链接系统如何解决缓存穿透、击穿、雪崩？

  • 穿透：布隆过滤器+空值缓存；
  • 击穿：热点Key互斥锁/定时主动刷新；
  • 雪崩：过期时间随机偏移、Redis集群高可用。

  1. MySQL分库分表用什么字段做分片键，为什么？ 答：用short_code短码Hash分片，查询时直接根据短码路由到唯一一张表，没有跨库查询，性能最优。

  2. 301和302重定向区别，项目为什么选302？ 答：301永久重定向浏览器会缓存跳转地址，后台修改失效规则无法实时生效；302临时跳转每次都请求后端，后台禁用、改地址立刻生效，业务灵活性更高。

  3. 为什么访问日志不存MySQL，要用ClickHouse？ 答：跳转访问是海量流水日志，MySQL写入压力大、聚合统计慢；ClickHouse列式存储对大数据量聚合查询做了深度优化，适合做PV/UV分析。

  4. Redis宕机后短链接系统怎么降级？ 答：缓存失效后直接走MySQL分库分表查询，同时开启接口限流，保护数据库不被打垮，告警通知运维修复Redis。

  5. 大量过期短链接怎么清理不影响线上性能？ 答：凌晨低峰期定时任务批量更新状态，迁移至归档历史表，避免高峰期大量UPDATE锁表。

  6. 跳转请求为什么要用MQ异步记录访问日志？ 答：同步写入日志会增加接口响应耗时，高并发下阻塞主线程；MQ异步解耦，跳转立刻返回，日志消费后置处理，RT极致压低。

  7. Redis Key为什么要和短链接过期时间一致？ 答：短链接失效后Redis自动淘汰Key，不占用无效内存，不用手动清理缓存。

  8. Nginx在整个架构中承担了哪些性能工作？ 答：请求拦截、负载均衡、静态缓存、协议压缩、限流前置，大量请求直接在Nginx层消化，不抵达应用服务器。

# 三、安全、架构拔高（19-25）

  1. 如何防止恶意人员批量扫描遍历所有短链接？ 答：①雪花算法无序短码无法顺序猜解；②IP粒度分布式限流，高频扫描直接拦截；③异常访问告警；④后台敏感链接加密管控。

  2. 短链接生成接口为什么要做严格黑名单校验？ 答：防止生成钓鱼网站、恶意跳转链接，规避公司合规与法律风险。

  3. 系统整体压力瓶颈在哪，如何扩容？ 答：瓶颈在跳转读请求；扩容方式：水平扩容跳转服务实例、扩容Redis集群分片、Nginx多节点负载、MySQL分更多库表。

  4. 如果短链接被大量恶意刷生成接口怎么防护？ 答：网关层IP+接口分布式限流，滑动窗口算法限制频次，触发后钉钉告警。

  5. 布隆过滤器放在Redis还是应用内存？优缺点？ Redis全局共享，多实例数据一致；本地内存性能更高但多实例数据不同步，生产优先Redis布隆过滤器。

  6. 如何保证短链接跳转的幂等性？ 跳转本身是查询操作天然幂等，只需保证多次访问不会重复扣减业务资源即可。

  7. 一句话总结整套短链接架构设计核心思想？ 整体以读多写少为核心做架构倾斜，写链路依靠雪花分布式ID生成62进制安全短码，MySQL分库分表承载亿级数据存储；超高并发跳转链路搭建Nginx+本地缓存+Redis三级缓存体系，全方位解决缓存三大问题；访问统计通过MQ异步解耦落地ClickHouse海量日志分析，叠加网关限流、域名黑名单、过期自动归档、故障自动降级形成高可用、高安全、高性能的完整短链接服务。

# 七、三段背诵版面试总结话术

# 30秒极简版

自研高并发短链接系统采用雪花算法生成无序全局ID转为62进制6位短码，MySQL分库分表持久化存储；跳转链路搭建Nginx、本地内存、Redis三级缓存扛住超高QPS，异步MQ投递访问日志写入ClickHouse做UV/PV统计，配套限流、黑名单、过期自动清理保障安全与稳定性。

# 1分钟标准版

整套短链接系统分为低并发写链路和超高并发读跳转链路两大模块。写链路使用雪花分布式ID生成全局唯一无序数字，转换为62进制URL安全短码，通过Redis布隆过滤器实现长URL去重，数据落地MySQL分库分表提升海量存储能力；读跳转链路构建Nginx前置缓存、应用Caffeine二级缓存、Redis分布式缓存三层架构，彻底规避缓存穿透、击穿、雪崩问题；所有访问行为经RocketMQ异步消费存入ClickHouse做大数据访问分析，同时叠加网关分布式限流、恶意域名黑名单、短链接过期自动归档、中间件故障降级等机制，构建生产级高并发、高安全、可运维的短链接服务。

# 架构师拔高版

设计核心遵循写轻量化、读极致性能、数据可扩展、风险全闭环四大原则。编码层摒弃自增连续ID，采用雪花算法生成不可逆无序ID映射62进制短码，从根源杜绝爬虫遍历风险；存储层通过Sharding-JDBC对短码Hash路由分库分表，支撑亿级数据平滑扩容；并发层针对99%流量的跳转请求搭建三级缓存防御体系，系统化解决Redis缓存三大经典问题，并依托异步消息队列削峰解耦，将海量访问日志离线存入列式数据库完成多维数据分析；可靠性上落地IP接口多层限流、恶意网址黑名单、过期冷数据自动归档、Redis/MySQL故障自动降级等运维策略，最终在并发吞吐、数据安全、存储扩展性、系统容错四个维度达成平衡。
