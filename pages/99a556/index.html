分布式秒杀系统设计

# 分布式秒杀系统

# 一、业务背景 & 核心难点（面试开篇必说）

# 真实场景

电商限时秒杀：活动商品短时间涌入几十万 QPS，瞬时流量是日常的 100 倍以上。

# 秒杀四大核心痛点（面试核心）

  1. 流量洪峰：瞬间高并发打垮数据库、服务、网关
  2. 超卖问题：并发扣库存导致负数库存、资损事故
  3. 黄牛刷单：脚本批量请求，普通用户抢不到
  4. 数据不一致：扣了库存没下单、下了单没支付、库存回滚错乱

# 系统硬性要求（架构设计依据）

  • 高性能：支撑瞬时 10w+ QPS
  • 高可用：不能雪崩、支持降级限流
  • 数据准确：绝对不能超卖、库存最终一致
  • 安全防刷：拦截黄牛脚本
  • 可监控、可溯源、可对账、可自愈

# 三、架构演进史（面试超级加分：4代架构迭代）

# V1 原始架构（新手写法，必死架构）

# 流程

前端请求 → 直接查DB库存 → 判断库存 → 扣库存 → 创建订单

# 致命问题

  1. MySQL 扛不住高并发，单库 QPS 只有 1000 左右
  2. 并发超卖
  3. 流量直接打垮数据库 结论：线上绝对不能用

# V2 缓存架构（Redis优化，解决并发）

# 流程

请求 → 查询Redis库存 → 扣库存 → 落库

# 问题

  1. Redis与DB数据不一致
  2. 瞬时流量依然打垮后端接口
  3. 无法防刷

# V3 MQ削峰架构（主流半成品架构）

# 流程

请求 → Redis预扣 → MQ异步落库

# 遗留问题

  1. MQ消息丢失导致库存卡死
  2. 无完整限流防刷体系
  3. 无监控、无降级、无兜底

# V4 最终生产架构（我下面讲的完整版）

五层流量拦截 + 双层防超卖 + 异步削峰 + 最终一致性 + 全链路监控溯源

# 四、最终生产架构【五层拦截 从上到下完整深度解析】

# 第一层：前端拦截（第一道流量过滤）

# 1. 页面静态化 + CDN

秒杀页面纯静态 HTML 放 CDN，不经过后端服务

  • 减轻源站压力
  • 毫秒级响应

# 2. 按钮防抖 + 限时置灰

  • 点击后立刻置灰 1s，禁止重复点击
  • 防止用户手动频繁点击刷接口

# 3. 动态URL加盐（防脚本提前刷）

秒杀开始前接口地址动态生成，不是固定URL 黄牛脚本无法提前构造请求

作用：拦截初级脚本黄牛

# 第二层：Nginx + 网关层限流（第二道拦截）

# 1. Nginx IP 限流

限制单IP每秒请求次数，封禁高频恶意IP

# 2. Gateway 网关限流

  • 基于 Redis + Lua 分布式限流
  • 维度：IP、用户ID、设备指纹
  • 令牌桶算法限流，应对突发流量

# 3. 黑名单拦截

对接风控系统，拉黑：

  • 高频IP
  • 批量异常设备
  • 异地异常登录账号

作用：拦截中级黄牛、爬虫、恶意刷量

# 第三层：Redis 预扣库存层【系统核心心脏】

# 核心设计（源码级）

所有秒杀核心逻辑全部下沉到 Redis + Lua 原子脚本 为什么必须 Lua？

  • 保证 库存判断、库存扣减、限购判断、下单标记 四步原子不可分割
  • 彻底杜绝并发超卖

# Redis 存储结构设计

  1. seckill:stock:{goodsId} 剩余库存
  2. seckill:user:{goodsId} Set集合：已下单用户（保证一人一单）

# Lua 完整源码（生产直接可用）

-- 1.获取参数
local goodsId = ARGV[1]
local userId = ARGV[2]

-- 2.key定义
local stockKey = "seckill:stock:" .. goodsId
local userKey = "seckill:user:" .. goodsId

-- 3.判断是否已秒杀过（一人一单）
if redis.call('sismember',userKey,userId) == 1 then
    return 0 -- 重复秒杀，拒绝
end

-- 4.判断库存
local stock = tonumber(redis.call('get',stockKey) or 0)
if stock <= 0 then
    return 0 -- 库存不足
end

-- 5.扣减库存
redis.call('decr',stockKey)
-- 6.标记用户已秒杀
redis.call('sadd',userKey,userId)

return 1 -- 秒杀成功

# 这一层解决的核心问题

  1. 彻底杜绝超卖（原子执行）
  2. 一人一单限购
  3. 百万级并发扛压（Redis 单机 10w+ QPS）
  4. 快速失败，不穿透后端

# 第四层：RocketMQ 事务消息削峰（最终一致性核心）

# 为什么必须 MQ？

  1. 瞬时流量削峰：10w QPS 瞬间打入服务直接崩，MQ 排队匀速消费
  2. 异步解耦：秒杀成功立刻返回，不阻塞用户
  3. 保证最终一致性：防止Redis扣库存、DB没落库导致数据不一致

# 事务消息完整流程（源码级）

  1. 秒杀服务执行 Redis预扣成功
  2. 发送 RocketMQ半消息（对消费者不可见）
  3. 执行本地事务：创建临时秒杀订单
  4. 本地事务成功 → 提交消息，消费者开始消费
  5. 本地事务失败 → 回滚Redis库存、回滚本地事务、消息回滚

# MQ 兜底机制

  1. 消息重试机制
  2. 死信队列兜底异常订单
  3. 定时任务对账补偿

解决：消息丢失、库存不一致、订单丢失 三大生产事故

# 第五层：数据库最终落地 & 兜底防超卖

# 数据库两大兜底方案

# 1. 唯一索引防重复

user_id + goods_id 唯一索引 杜绝同一用户重复下单落库

# 2. 数据库乐观锁兜底防超卖

update seckill_goods 
set stock = stock - 1 
where goods_id = ? and stock > 0;

哪怕Redis层出问题，数据库绝对不会超卖

# 订单表分库分表

秒杀订单流量极大，单表爆炸

  • 按 user_id 分表
  • 按月分区
  • 冷热数据分离

# 五、超时未支付库存回滚机制（高频深挖考点）

# 业务规则

秒杀订单 15分钟未支付自动过期，释放库存

# 实现方案（最优方案）

RocketMQ 延迟消息

  1. 创建订单时发送 15分钟延迟消息
  2. 消费者监听消息
  3. 判断订单状态：待支付 → 关闭订单 + 回滚Redis库存 + 回滚DB库存

# 分布式秒杀系统30道深度面试追问+满分标准答案

# 一、基础架构层（1-10题）

# 1. 为什么秒杀请求不能直接操作MySQL数据库？

答：MySQL InnoDB引擎基于行锁、事务MVCC实现并发，单库TPM上限大概1000~2000，秒杀瞬时几万甚至十几万QPS会造成大量锁竞争、事务排队、CPU打满、连接池耗尽，直接数据库雪崩。同时大量同步IO会拖垮整个订单服务，所以必须把压力前置到Redis做内存级预扣，数据库只做最终落地。

# 2. Redis扣库存为什么非要用Lua脚本，Pipeline或者多次Redis调用不行吗？

答：Pipeline只能批量打包网络IO，无法保证多命令原子性。秒杀需要连续执行4个操作：判断用户是否已下单、校验库存、扣减库存、写入已下单用户集合。如果拆成多条命令，高并发下会出现指令穿插，导致超卖、一人多单。Lua脚本在Redis服务端单线程完整执行，中间不会被其他请求打断，天然保证原子性，这是杜绝超卖最核心的手段。

# 3. MQ在秒杀里核心作用是什么，只做削峰吗？

答：三大核心作用：

  1. 削峰填谷：把瞬时洪峰流量转为匀速消费，保护下游数据库；
  2. 异步解耦：Redis预扣成功直接返回给用户，创建订单、库存落库、支付通知等异步执行，缩短用户等待RT；
  3. 分布式事务兜底：借助RocketMQ事务消息，保证Redis库存扣减和数据库订单落库的最终一致性，解决缓存与DB双写不一致问题。不只是削峰，一致性兜底是更关键的价值。

# 4. 简单说下RocketMQ事务消息（半消息）完整执行流程？

答：

  1. 生产者发送半事务消息到Broker，消息对消费者不可见；
  2. 执行本地事务（创建数据库秒杀订单）；
  3. 本地事务执行成功：发送Commit指令，Broker投递消息给消费者；本地事务失败：发送Rollback指令，Broker删除半消息；
  4. 如果生产者宕机、网络中断，Broker会定时回查生产者事务状态，根据回查结果决定提交或回滚；
  5. 消费者消费消息，执行数据库库存最终扣减。 闭环保证Redis预扣和DB订单落地要么同时成功，要么同时回滚。

# 5. 架构里设计了Redis+DB双层防超卖，两层分别承担什么职责？

答：

  1. Redis层：高并发下快速拦截绝大部分请求，Lua原子预扣从源头避免并发超卖，承担流量扛压、前置校验；
  2. DB层兜底：通过update ... where stock>0乐观锁做最终校验，防止Redis集群故障、Lua执行异常、脏数据导致的超卖，属于最后一道数据安全屏障。两层组合实现零资损。

# 6. 为什么用Redis Set存储已下单用户，不用Hash、String？

答：核心需求是快速判断用户是否已抢购、抢购结束后统计抢购人数。Set天然提供SISMEMBER O(1)成员判断、SCARD统计总数，结构极简。Hash会冗余多余field，String需要拼接拼接用户ID做分隔符，查询和统计复杂度更高，Set是最优选型。

# 7. 秒杀订单为什么要做分库分表，直接单表加索引不行吗？

答：大促期间单次秒杀可能产生几十万甚至百万条订单，单表数据量超过千万后，索引层级变深、分页查询、统计对账SQL性能急剧下降。按user_id做哈希分库分表，分散单表数据压力，同时后续归档、冷热分离、按月分区都更方便，保证订单库长期可维护。

# 8. 前端静态化+CDN能解决什么问题，只做按钮置灰够吗？

答：按钮置灰只能防止用户重复点击，挡不住爬虫脚本。CDN存放纯静态秒杀页面，不回源业务服务器，大幅降低源站带宽和请求量；配合动态签名URL、验证码校验，拦截批量刷接口的机器流量，是最廉价有效的第一层流量防护。

# 9. 网关层用什么算法做分布式限流，为什么选这个？

答：优先Redis+Lua实现令牌桶算法。令牌桶可以预热桶内令牌，应对秒杀瞬间流量突刺；Lua保证限流计数原子性，避免分布式集群多实例计数不准。漏桶只能匀速流出，无法应对突发峰值；固定窗口临界有流量毛刺，滑动窗口实现复杂度更高，令牌桶最适配秒杀场景。

# 10. 一人一单做了Redis Set和数据库唯一索引双重校验，重复了吗？

答：不重复，各司其职。Redis拦截绝大多数并发请求，避免大量重复请求穿透到DB；数据库goods_id+user_id联合唯一索引做兜底，防止Redis数据丢失、过期、逻辑bug导致重复落库，遵循缓存校验、数据库最终兜底的设计原则。

# 二、一致性、库存回滚与数据兜底（11-20题）

# 11. 15分钟未支付自动释放库存，为什么用MQ延迟消息，不用定时任务轮库？

答：定时任务每分钟全表扫描大量秒杀订单，数据库压力极高，订单越多性能越差；延迟消息是点对点触发，只在订单过期那一刻执行，精准触发、无无效轮询、DB压力极小。唯一缺点依赖MQ组件可用性，可加定时任务二次巡检做降级兜底。

# 12. 延迟消息执行关闭订单时，Redis库存和DB库存分别怎么回滚？

答：

  1. 查询DB订单状态为「待支付、已过期」；
  2. DB执行update更新订单为已取消，并给商品库存+1；
  3. Redis执行Lua脚本：stockKey自增+从user集合移除该用户；
  4. 操作失败进入死信队列，定时对账任务补偿修复。保证Redis和DB库存同步回滚。

# 13. Redis宕机/主从切换，已经预扣的库存数据丢失怎么处理？

答：三层兜底：

  1. Redis开启RDB+AOF混合持久化，哨兵自动故障转移，最大程度避免丢数据；
  2. 后台定时对账任务，每分钟对比Redis库存和DB真实库存差值，自动修复偏差；
  3. Redis不可用时开启降级，流量直接导流到数据库乐观锁兜底模式，牺牲并发换取数据安全。

# 14. MQ消息丢失、重复消费如何解决？

答：

# 消息丢失

生产者开启重试+事务消息机制；Broker开启同步刷盘、多副本存储；消费者手动ACK确认消费完成再提交offset。

# 重复消费

消费逻辑做幂等：以order_no唯一订单号作为幂等键，数据库唯一索引+Redis消费记录去重，重复调用不会生成多条订单。

# 15. 什么是热点Key击穿，秒杀商品怎么规避？

答：同一个秒杀商品的stock Key被几万请求并发访问，压垮Redis节点就是热点Key击穿。 优化方案：

  1. Redis内部对同一个商品拆分多个虚拟库存key，请求随机路由分摊压力；
  2. 网关层本地Caffeine缓存短时库存状态，减少穿透Redis次数；
  3. 对热点商品单独Redis分片部署，隔离资源。

# 16. Redis库存和MySQL库存出现不一致，定时对账逻辑怎么写？

答：

  1. 遍历所有进行中的秒杀商品；
  2. 获取Redis剩余库存、DB原始总库存-DB已售出库存=理论剩余库存；
  3. 两者差值不为0则记录异常日志，自动修正Redis库存；
  4. 统计Redis已下单用户数量和DB有效订单数量做二次校验，产出对账报表推送告警。

# 17. 数据库乐观锁如果并发更新失败，业务上怎么重试？

答：MQ消费者收到消息后执行update乐观锁，受行锁影响返回影响行数0，直接抛出异常触发MQ自带重试机制；重试达到阈值转入死信队列，人工介入排查，避免无限重试占用资源。

# 18. 秒杀服务多实例集群部署，会产生并发问题吗？哪些环节要做分布式控制？

答：纯Redis Lua、MQ、DB自带的原子机制天然支持集群，业务服务无状态可水平扩容。需要分布式控制的点：

  1. Redis限流计数（分布式Lua）；
  2. 定时对账任务（Redis分布式锁保证单机执行）；
  3. MQ消费负载均衡由Broker自行管理。

# 19. 为什么不直接用分布式锁扣库存，反而用Lua脚本？

答：Redisson分布式锁有加锁、释放锁、看门狗续期多次网络往返，并发越高Redis网络开销越大。Lua脚本单条网络请求完成全部逻辑，性能远高于分布式锁，秒杀追求极致QPS必须优先Lua原子操作。

# 20. 秒杀系统怎么保证幂等性，哪些节点容易重复请求？

答：

  1. 前端防重复点击；
  2. 网关层基于用户ID+请求参数生成唯一requestId，Redis过滤重复请求；
  3. MQ消费端基于订单号幂等；
  4. DB唯一索引兜底。 重复高发点：网络超时重试、MQ重复投递、定时任务重复执行。

# 三、高可用、降级熔断、运维监控溯源（21-25题）

# 21. 系统峰值压力过大时，Sentinel如何做降级熔断？哪些功能可以关闭？

答：

  1. 限流熔断：秒杀核心接口设置QPS阈值，超出直接返回“活动火爆，请稍后重试”；
  2. 功能降级：关闭商品详情查询、积分抵扣、优惠券叠加、消息推送等非核心附属逻辑；
  3. 服务熔断：下游支付、物流服务超时比例过高直接熔断，避免级联故障。核心只保留库存校验+下单落库。

# 22. Redis集群高可用完整部署方案怎么设计？

答：采用主从架构+哨兵集群：

  1. 每个主节点配置1~2台从节点做数据备份；
  2. 3个哨兵节点监控所有主从，主节点宕机自动选从节点升级为主；
  3. 开启AOF持久化+每秒刷盘，RDB定时快照；
  4. 热点商品单独分片，避免单个分片压力过大。

# 23. MQ Broker集群高可用配置要点？

答：

  1. NameServer集群3节点保证注册中心可用；
  2. Topic多副本同步刷盘，Broker宕机副本自动接管；
  3. 开启消息重试队列、死信队列，堆积超限触发告警；
  4. 生产者负载均衡发送，消费者集群负载均衡消费。

# 24. 整套秒杀系统需要监控哪些核心指标，用什么组件采集？

答：基于Prometheus + Grafana采集，SkyWalking做全链路追踪：

  1. 网关层：总QPS、限流拒绝数、IP黑名单拦截量；
  2. Redis：命令耗时、Key命中率、CPU、内存、主从延迟；
  3. MQ：消息生产TPS、堆积量、消费延迟、死信数量；
  4. 应用服务：接口RT、异常率、线程池占用；
  5. 数据库：慢SQL、锁等待、事务回滚次数。 异常指标对接钉钉短信告警。

# 25. 可溯源体系怎么落地，出问题如何快速定位哪一步异常？

答：

  1. 全局透传TraceId，从Nginx→Gateway→秒杀服务→Redis→MQ→MySQL全程打印日志；
  2. ELK统一收集所有日志，根据TraceId一键串联完整调用链路；
  3. 对账日志入库留存，库存偏差、订单失效、死信消息均可溯源操作人、操作时间、原始请求参数；
  4. SkyWalking可视化查看每一段调用耗时、报错堆栈，快速定位瓶颈点。

# 四、黄牛风控、架构迭代与拔高开放性问题（26-30题）

# 26. 完整的防黄牛风控体系分哪几层？

答：

  1. 前端层：滑块/点选验证码、设备指纹采集、请求时间间隔校验；
  2. 网关层：IP频次限流、异常IP黑名单、批量账号拦截；
  3. 业务层：新注册账号限购、异地登录风控、同一设备多账号拦截；
  4. 后端校验：请求动态签名校验，防止脚本伪造请求参数；
  5. 事后复盘：抓取高频抢购IP，同步至风控系统永久拉黑。

# 27. 如果预估秒杀流量达到百万QPS，现有架构怎么二次扩容？

答：

  1. Redis：拆分库存虚拟key、独立Redis集群、增加分片；
  2. MQ：Topic多分队列，消费者水平扩容；
  3. 应用服务：K8s弹性扩缩容，峰值自动增加Pod；
  4. 数据库：订单表进一步水平分库分表，读写分离增加从库分担查询；
  5. 前置层：接入WAF防护，清洗恶意爬虫流量。

# 28. 说说秒杀架构4个版本迭代思路（面试加分项）

答： V1 直连DB：最简但并发极低，直接雪崩； V2 加Redis缓存：解决并发，但缓存DB一致性无法保障； V3 引入MQ异步削峰：解决流量洪峰，但缺少完整风控、兜底、监控； V4 最终生产架构：五层流量拦截+Lua原子防超卖+事务消息一致性+延迟回滚+全链路监控对账+多级降级风控，可支撑大促生产落地。

# 29. 除了RocketMQ事务消息，还有哪些方案保证Redis和DB库存一致性？各自优缺点？

答：

  1. 本地消息表：业务库建一张消息表，定时任务扫描发送MQ，实现简单但数据库多一张表，大促压力大；
  2. Seata AT分布式事务：对多服务多库友好，但秒杀单场景过重，性能损耗高于MQ事务消息；
  3. 定时任务兜底对账：只能做事后修复，无法实时保证一致性，只能作为辅助兜底。 最优依旧是RocketMQ半事务消息。

# 30. 总结一下你设计这套秒杀系统的核心设计思想，面试官收尾口述版？

答：整套秒杀系统核心围绕四大目标设计：扛住流量洪峰、绝对不超卖、保证数据最终一致性、系统高可用可运维。整体采用多层流量漏斗逐级削峰，前端CDN、网关限流、Redis内存预扣三层拦截流量，把压力和并发计算前置到高性能中间件；通过Lua原子脚本+数据库乐观锁双层兜底杜绝超卖；RocketMQ事务消息解决缓存与数据库双写一致性，延迟消息自动回收超时未支付库存；配套服务集群、Redis哨兵、MQ多副本、数据库分库分表保障全链路高可用；最后通过全链路追踪、指标监控、定时数据对账实现可监控、可溯源、可自愈，同时叠加多层风控策略拦截黄牛刷单，是一套完整可落地的生产级秒杀架构。

# 附加：可以直接背诵的3段精简面试话术

# 版本1（30秒极简口述）

秒杀核心是多级流量拦截，前端CDN静态页面、网关分布式限流过滤无效流量，核心用Redis+Lua原子脚本预扣库存防止超卖，RocketMQ事务消息异步削峰保证Redis和数据库库存最终一致，数据库乐观锁兜底，延迟消息自动释放超时订单库存，配套集群高可用、全链路监控和定时对账，同时多层风控抵御黄牛，整套架构支撑高并发且零资损。

# 版本2（1分钟完整版）

首先梳理秒杀四大痛点：流量洪峰、并发超卖、黄牛刷单、数据不一致。架构分为五层流量拦截：前端CDN+验证码做第一层防护；Nginx+网关做IP、用户维度分布式限流拦截恶意请求；Redis作为核心层用Lua脚本原子完成库存扣减、用户限购，承接绝大部分并发；RocketMQ事务消息异步削峰，同步保证缓存与数据库一致性；最后数据库乐观锁+唯一索引做最终兜底防超卖。额外通过延迟消息回滚过期库存、服务中间件集群实现高可用，全链路监控+定时对账完成可观测与数据自愈，完整解决大促秒杀所有生产问题。

# 版本3（架构师拔高版）

整体遵循压力前置、异步解耦、多层兜底、最终一致的架构原则。将高并发计算下沉至Redis内存层，利用单线程Lua保证操作原子性从源头规避超卖；引入消息队列实现流量削峰与分布式事务闭环，弱化数据库瞬时压力；所有核心数据均设计双重校验机制，缓存做性能、数据库做可靠；配套熔断降级、故障转移、死信重试、定时对账形成闭环自愈体系，同时构建端到端风控体系对抗黑产，在高性能、高可用、数据可靠性三者之间做最优平衡。
