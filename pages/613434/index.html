# 1. 单体架构、SOA、微服务架构区别、优缺点

# 1.1 单体架构

# 定义

所有模块（用户、订单、商品、支付）打包成一个War/Jar包，部署在一台服务器，数据库共用一个。

# 优点

开发简单、测试简单、部署简单、无分布式问题、事务天然ACID。

# 缺点

  1. 代码耦合严重，牵一发而动全身；
  2. 无法单独扩容某个压力大的模块；
  3. 技术栈统一，不能针对服务选型；
  4. 迭代速度随项目增大急剧变慢。

# 1.2 SOA 面向服务架构

# 定义

引入ESB企业服务总线，将单体拆分为多个粗粒度服务，通过ESB做协议转换、路由、数据透传，服务间通过WebService调用。

# 优点

完成初步解耦，可独立部署部分服务。

# 缺点

ESB总线性能瓶颈，粗粒度拆分，架构笨重，耦合依然很高，基本被微服务淘汰。

# 1.3 微服务架构

# 定义

将系统按照业务能力拆分成细粒度、高度自治的小型独立服务，每个服务独立数据库、独立部署、独立迭代、独立扩容，通过轻量级HTTP/RPC通信，去中心化，无总线。

# 三者核心区别总结

  1. 单体：一个包、一个库、一个DB、中心化；
  2. SOA：粗粒度拆分 + ESB重总线；
  3. 微服务：细粒度按业务域拆分、去中心化、轻量RPC/HTTP、每个服务独立数据源。

# 2. 微服务架构优点 & 落地带来的痛点

# 优点

  1. 服务解耦：单个服务修改不影响整体系统；
  2. 独立弹性扩容：订单、秒杀等压力大的服务单独多实例部署；
  3. 技术栈异构：存储用MySQL、Redis、MongoDB、Elasticsearch自由选择；
  4. 团队自治：小团队维护单个微服务，并行开发迭代；
  5. 故障隔离：一个服务宕机不会导致整个系统崩溃。

# 微服务落地带来的巨大挑战（面试重点）

  1. 分布式复杂性陡增：分布式事务、分布式锁、分布式Session、接口幂等；
  2. 运维成本指数级上升：几十上百个服务部署、版本管理、日志收集；
  3. 服务调用链路复杂：服务A调用B，B调用C，链路排查困难，需要链路追踪；
  4. 网络问题增多：网络超时、丢包、重试、端口占用；
  5. 服务雪崩风险：下游服务宕机导致上游线程耗尽拖垮自身，必须熔断降级；
  6. 数据一致性难以保证：多服务多数据库无法使用本地事务ACID；
  7. 重复开发、接口规范统一、文档管理、统一鉴权、统一参数校验难度大。

# 3. 微服务拆分原则（DDD领域驱动设计）

# 核心拆分原则

  1. 按业务能力拆分（高内聚低耦合） 一个微服务对应一个完整业务域：用户服务、商品服务、订单服务、支付服务、库存服务、优惠券服务。

  2. 单一职责原则 一个服务只做一件事，订单服务只负责创建订单、取消订单、查询订单，不插手库存扣减。

  3. 数据库独立原则（最重要） 微服务尽量一服务一数据库，禁止多个微服务共用一张表，否则等于伪微服务，无法彻底解耦。

  4. 限界上下文（DDD核心） 用限界上下文划分业务边界，上下文之间通过接口通信，内部实体不对外暴露。

  5. 拆分粒度宁粗勿细 避免过度拆分（比如把订单创建、订单取消拆两个服务），拆分过细会导致调用链路爆炸，维护成本极高。

  6. 独立团队负责 一个微服务对应一个小团队，谁维护谁发布，责任闭环。

# DDD核心名词简述

  • 限界上下文：业务边界；
  • 聚合根：聚合的入口实体（Order订单为聚合根，包含订单项、收货地址）；
  • 值对象：无唯一ID的对象，如地址、金额；
  • 领域事件：订单创建完成发布事件通知库存、支付。

# 5. 服务注册中心 Nacos/Eureka/Zookeeper/Consul 对比与CAP

# CAP理论回顾

  • C一致性：所有节点数据同一时刻完全一致；
  • A可用性：任何请求都能正常响应；
  • P分区容错：网络故障节点断开，系统仍可运行； 分布式系统P必须保证，只能在C和A之间取舍。

# 各个注册中心CAP特性

  1. Eureka AP架构，舍弃强一致性，保证高可用； 集群节点互相独立，某个节点宕机不影响整体； 自我保护机制：短时间大量服务下线，Eureka不剔除实例，防止网络抖动误删； 缺点：2018年停止维护，不推荐新项目。

  2. Zookeeper CP架构，保证强一致性，牺牲可用性； 采用ZAB一致性协议，主节点宕机要重新选举，选举期间整个注册中心不可用； 适合做分布式锁、配置中心，不适合做服务注册发现。

  3. Consul CP架构，自带健康检查、KV存储、多数据中心，部署复杂，国内使用率低。

  4. Nacos（阿里生产首选） AP架构，兼顾可用性与最终一致性； 同时集成注册中心 + 配置中心二合一，简化架构； 支持持久化、权重负载、灰度发布、健康检查、临时实例/持久实例； Spring Cloud Alibaba主推，企业微服务标配。

# 面试一句话选型结论

新项目直接使用Nacos；老项目Eureka维护；Zookeeper不做服务注册。

# 6. API网关 Spring Cloud Gateway vs Zuul 底层原理

# 6.1 Zuul 1.x（淘汰）

  1. 基于Servlet同步阻塞IO模型；
  2. 每一个请求占用一个Tomcat线程，高并发下线程池耗尽性能差；
  3. 代码维护停止，Spring官方不再更新。

# 6.2 Spring Cloud Gateway（官方新一代网关）

# 底层核心原理

  1. 基于Spring5、Reactor、Netty实现异步非阻塞IO，高并发吞吐量远超Zuul；
  2. 三大核心组件：
    • Route路由：定义请求转发规则；
    • Predicate断言：匹配请求路径、参数、Header；
    • Filter过滤器：前置/后置逻辑（鉴权、限流、跨域、日志、修改响应）；
  3. 支持动态路由、负载均衡、全局异常处理、灰度发布、限流熔断。

# 网关核心落地作用

  1. 统一入口，隐藏后端服务地址；
  2. 全局身份认证、权限校验、Token校验；
  3. 请求限流、防刷、跨域处理；
  4. 日志记录、请求参数打印、全局异常捕获；
  5. 灰度发布、蓝绿发布、版本路由；
  6. 协议转发、请求加解密。

# 7. 远程调用 OpenFeign、RestTemplate、Dubbo 区别

# 1）RestTemplate

原生Spring封装HTTP工具，手动拼接URL、参数，代码冗余，无负载均衡，极少直接使用。

# 2）OpenFeign（Spring Cloud HTTP调用标准）

  1. 声明式接口编程，像调用本地接口一样调用远程服务；
  2. 内置负载均衡（整合Ribbon）；
  3. 可集成Sentinel做熔断降级；
  4. 底层依然是HTTP协议，通用性强，调试方便。

# 3）Dubbo（阿里RPC高性能框架）

  1. 私有二进制RPC协议，TCP长连接，序列化效率极高，QPS远高于HTTP；
  2. 内置注册中心、负载均衡、重试、超时、熔断；
  3. 适合内部服务高频次密集调用；
  4. 缺点：协议封闭，外部系统无法直接调用。

# 选型总结

  1. 跨部门、对外开放接口、需要调试：OpenFeign HTTP；
  2. 内部微服务高频调用追求极致性能：Dubbo RPC；
  3. Spring Cloud Alibaba体系推荐Dubbo + Nacos组合。

# 8. 服务雪崩、熔断、降级、限流、线程隔离（Sentinel重点）

# 8.1 服务雪崩原理

微服务调用链路：A → B → C → D。 如果D服务宕机或者响应极慢，大量请求堆积在C的请求线程池中，线程被耗尽，C服务无法处理其他请求，接着拖垮B，最终整个链路全部瘫痪，这就是服务雪崩。

# 8.2 核心四个保护手段

# （1）线程/信号量隔离

把调用下游服务的请求放到独立线程池，下游故障只耗尽隔离池，不影响本服务其他业务，Sentinel、Hystrix底层核心机制。

# （2）熔断（Circuit Breaker）

统计下游调用失败率，失败比例超过阈值直接打开熔断器，快速失败，不再发起远程调用，一段时间后半开试探恢复。 三个状态：关闭→打开→半开→关闭。

# （3）降级（Fallback）

熔断触发后，不走真实业务逻辑，返回兜底默认数据。 例如：商品详情服务异常，返回缓存静态商品信息，避免抛出500错误。 降级类型：接口降级、非核心业务直接关闭（关闭商品推荐、关闭日志统计）。

# （4）限流

限制单位时间内请求总量，保护自身服务不被打垮。 Sentinel支持：QPS限流、并发线程数限流、热点参数限流、网关限流。

# 8.3 Sentinel vs Hystrix

  1. Hystrix：Netflix开源，已停止迭代，功能单一；
  2. Sentinel：阿里开源，轻量级、控制台可视化、规则动态推送、热点限流、网关限流、系统自适应保护，生产环境统一使用Sentinel。

# 9. 分布式配置中心 Nacos / Apollo / Spring Cloud Config

# 1）Spring Cloud Config

Spring官方，基于Git仓库存储配置，无可视化控制台，配置刷新需要手动POST接口，无集群高可用，仅适合简单测试项目。

# 2）Apollo（携程）

功能强大，权限细致、灰度发布、环境隔离、版本回滚； 缺点：部署重，依赖MySQL，架构复杂，中小型项目太重。

# 3）Nacos（最优）

  1. 注册中心+配置中心二合一，减少中间件部署；
  2. Web可视化控制台，修改配置实时推送到微服务，自动刷新@Value/@ConfigurationProperties；
  3. 支持配置分组、命名空间隔离多环境（dev/test/prod）；
  4. 持久化到MySQL，集群高可用，Spring Cloud Alibaba生态无缝集成。

# 核心原理

微服务启动时拉取远端配置存入内存；Nacos长连接监听配置变更，一旦修改通过推送机制通知客户端重新加载配置，无需重启应用。

# 10. 分布式链路追踪 SkyWalking、Zipkin、Pinpoint

# 核心作用

微服务多层调用，出现超时、报错、慢SQL无法定位是哪一层的问题，链路追踪记录每一次调用耗时、服务名、异常堆栈、请求参数，可视化展示调用链。

# 理论基础：OpenTracing 规范

三个核心概念：

  1. Trace：一次完整请求全局唯一ID；
  2. Span：调用过程中的一个单元（一次接口调用、一次SQL查询）；
  3. Context：透传TraceId在所有微服务Header中传递。

# 三款工具对比

  1. SkyWalking（国产首选） 字节码探针无侵入、部署简单、性能损耗低、UI友好、支持Java/Go/PHP、自动监控JVM指标、服务拓扑图，企业微服务标配。

  2. Zipkin Spring Cloud官方集成，功能简陋，仅基础链路存储，无深度分析。

  3. Pinpoint 基于字节码注入，采集粒度极细，占用资源偏高，部署较重。

# 面试一句话答案

生产环境优先使用SkyWalking做全链路监控。

# 11. 微服务跨域解决方案

# 跨域产生原因

浏览器同源策略（协议、域名、端口任一不同即为跨域），前端Vue/React访问后端网关或微服务出现CORS报错。

# 四层解决方案（从上到下优先级）

  1. 网关层统一配置跨域（最佳实践） 在Spring Cloud Gateway全局CORS配置，所有微服务统一生效，不用每个服务重复配置。

  2. Nginx反向代理 前端和后端统一域名，规避浏览器跨域校验。

  3. 单个微服务添加@CrossOrigin注解 简单测试使用，微服务多了维护麻烦。

  4. 后端添加全局CORS过滤器 WebMvcConfigurer重写addCorsMappings方法配置允许源、Header、请求方法。

# 12. 微服务分布式事务6种解决方案（Seata为核心）

# 背景

微服务跨多个数据库，无法使用本地MySQL事务ACID，需要保证最终数据一致性。

# 方案1：2PC XA 强一致性（数据库层面）

  • 原理：协调器、参与者两段提交，准备阶段全部锁定资源，第二阶段统一提交/回滚；
  • 优点：强一致性；缺点：阻塞性能极差，数据库锁长时间持有，生产几乎不用。

# 方案2：TCC 侵入式补偿事务（Try-Confirm-Cancel）

  • Try：检查资源、锁定预留；
  • Confirm：确认执行业务；
  • Cancel：释放资源回滚；
  • 优点：性能好；缺点：代码侵入极强，每个接口写三套逻辑，复杂度高，核心支付场景使用。

# 方案3：Seata AT模式（自动事务，生产最常用）

无侵入框架方案 原理：

  1. 执行业务SQL前记录undo_log回滚快照；
  2. 全局事务ID传递到所有分支；
  3. 全部分支执行成功删除undo_log；任意分支失败，根据undo_log自动生成补偿SQL回滚；
  4. 全局锁保证写隔离，防止脏写。 优点：零业务侵入，一行注解@GlobalTransactional开启；缺点：只支持关系型数据库。

# 方案4：本地消息表 + MQ 可靠消息最终一致性（高并发场景）

  1. 本地事务：业务操作 + 插入一条待发送消息到消息表；
  2. 定时任务轮询消息表发送RocketMQ；
  3. 下游消费成功ACK，上游修改消息状态；消费失败重试、死信队列兜底。 优点：高并发、解耦、性能最高；适合订单库存最终一致性场景。

# 方案5：SAGA 长事务模式

把大事务拆分成多个本地小事务，每个事务对应一个补偿回滚操作，失败反向执行补偿，适合长流程业务、第三方外部接口调用。

# 方案6：最大努力通知

对账兜底方案，比如短信通知、积分发放，多次重试，最终人工对账修正。

# 面试总结

  1. 简单内部系统：Seata AT无侵入模式；
  2. 高并发订单库存：RocketMQ可靠消息最终一致性；
  3. 金融核心支付：TCC；
  4. 长流程审批：SAGA。

# 13. CAP、BASE、最终一致性（分布式理论基础）

# CAP

  1. C 一致性：多节点数据实时完全一致；
  2. A 可用性：服务随时可访问响应；
  3. P 分区容错：网络断裂分区故障，系统依然可用； 分布式系统P无法避免，只能在C和A做取舍。
  • CP：放弃可用性，保证强一致（Zookeeper）；
  • AP：放弃强一致，保证高可用（Nacos、Eureka）。

# BASE理论（CAP的落地妥协）

  1. BA 基本可用：故障时损失部分功能，核心可用；
  2. S 柔性状态：允许系统中间状态，数据不一致；
  3. E 最终一致性：经过一段时间同步，所有节点数据达成一致。 微服务分布式系统几乎全部遵循BASE理论，追求最终一致性而非强一致性。

# 14. 微服务分布式Session共享方案

# 场景

登录后网关路由到不同微服务，默认Tomcat Session隔离，登录状态丢失。

# 解决方案

  1. Redis统一存储Session（主流） Spring Session整合Redis，所有服务登录信息存入Redis，共享登录态，过期自动销毁，网关统一校验Token。

  2. JWT无状态Token（前后端分离首选） 登录签发JWT令牌，携带用户信息，服务解密校验，不需要服务端存储Session，扩展性更强。

  3. Nginx IP哈希负载均衡 固定用户访问同一台实例，不推荐，失去负载均衡意义。

# 企业最终方案

前后端分离项目：网关签发JWT + Redis黑名单（注销失效）；传统服务：Spring Session Redis共享。

# 15. 灰度发布、蓝绿发布、金丝雀发布、滚动发布

# 1）蓝绿发布

两套完整环境：蓝（旧版本）、绿（新版本）；先部署绿环境测试，全部没问题网关切流量到绿，风险极低，但双倍服务器资源占用。

# 2）滚动发布

一台一台停止旧实例，启动新版本实例，逐步替换，节省资源，缺点中间版本混合运行，回滚复杂。

# 3）金丝雀发布（灰度发布，微服务最常用）

  1. 启动少量新版本实例；
  2. 按比例/按用户/按请求Header分流一小部分流量到新版本；
  3. 监控日志、异常、指标无问题，全量放量；出现异常立刻切回旧版本。 Spring Cloud Gateway + Nacos权重配置完美实现灰度。

# 4）A/B测试

针对不同用户群体推送不同版本，用于产品功能效果对比，属于灰度的子集。

# 16. 微服务统一安全认证 OAuth2.0 + JWT + 网关鉴权

# 架构方案（标准落地）

  1. 独立认证授权中心：基于Spring Security + OAuth2.0；
  2. 四种授权模式：密码模式（后台管理）、客户端模式（第三方对接）、授权码模式（网页登录）、简化模式；
  3. 登录成功颁发JWT令牌；
  4. 网关层统一拦截校验JWT，解析出用户ID、权限放入请求头向下游微服务透传；
  5. 各个微服务只做接口权限判断，不重复校验Token。

# JWT结构

Header头部、Payload载荷（用户信息、过期时间）、Signature签名加密； 优点：无状态、可扩展；缺点：无法主动作废，搭配Redis黑名单处理退出登录。

# 为什么要在网关统一鉴权？

避免每个微服务重复写Token解析、验签逻辑，统一收口，简化业务代码。

# 17. 微服务接口幂等性（防止重复请求）

# 问题来源

网络超时重试、前端重复点击、MQ重复投递、负载均衡重试导致业务重复执行（重复下单、重复扣款）。

# 通用5种解决方案

  1. 唯一业务流水号（最优） 前端/网关生成全局唯一单号，Redis或数据库唯一索引约束，执行前判断是否已处理。

  2. 数据库唯一索引 订单号、支付流水建立唯一键，重复插入直接数据库报错拦截。

  3. 状态机控制 订单只有待支付可以执行支付，已支付状态直接返回成功。

  4. Redis分布式锁 执行业务前加锁，锁定本次请求唯一标识，处理完成释放。

  5. MQ消费端幂等 使用消息MessageId作为幂等Key存入Redis，消费前校验。

# 18. Docker + K8s 微服务容器化简述（架构师加分题）

  1. Docker：将微服务Jar包、JVM、依赖、环境打包成镜像，一次打包到处运行，解决环境不一致问题；
  2. Kubernetes(K8s)：容器编排平台，自动扩缩容、滚动发布、自愈重启、负载均衡、资源限制、日志管理；
  3. CI/CD流水线：Jenkins/GitLab自动拉取代码→编译→构建Docker镜像→推送仓库→K8s滚动更新发布。

# 19. 微服务监控体系 Prometheus + Grafana

  1. Prometheus时序数据库：采集JVM指标、接口QPS、异常数、CPU、内存、磁盘、线程池、GC频率；
  2. Grafana可视化大屏：绘制监控图表；

# 最终面试口述精简总结（背诵版）

  1. 微服务核心是按业务域细粒度拆分，一服务一库，去中心化，带来解耦扩容优势，但引入分布式事务、服务雪崩、链路排查、运维复杂度四大难题；
  2. 注册中心选Nacos（AP架构，注册配置二合一），网关用Spring Cloud Gateway非阻塞异步模型；
  3. 流量防护靠Sentinel做熔断、降级、限流、线程隔离，防止服务雪崩；
  4. 分布式事务优先Seata AT无侵入方案，高并发订单场景用RocketMQ可靠消息最终一致性；
  5. 分布式遵循CAP、BASE理论，追求最终一致性；
  6. 链路追踪用SkyWalking排查调用链瓶颈，网关统一做跨域、鉴权、灰度发布；
  7. 整体容器化Docker+K8s部署，Prometheus监控告警闭环。

# 2. 完整四大核心流程

# 流程 1：服务注册（生产者启动）

  1. 微服务启动时，Nacos 客户端 SDK 加载@EnableDiscoveryClient注解；
  2. 封装服务名称、IP、端口、权重、实例类型（临时 / 持久）、元数据；
  3. 向 Nacos Server 发送RegisterService HTTP 请求；
  4. Nacos Server 收到请求后：
    • 判断实例类型：临时实例（AP） 存入内存，依靠心跳保活；持久实例（CP） 写入 MySQL 持久化；
    • 将实例挂载到对应服务名的服务列表下；
    • 通过 Raft 一致性协议同步该数据到 Nacos 集群所有节点，保证集群数据一致；
  5. Server 返回注册成功，客户端开启定时心跳线程（默认 5 秒）。

# 流程 2：心跳保活 & 健康剔除（核心自愈能力）

  1. 临时实例客户端每 5 秒上报心跳包；
  2. Nacos Server 开启后台健康检查线程，默认 15 秒未收到心跳 → 标记不健康；30 秒未上报 → 自动剔除该实例；
  3. 持久实例不依赖心跳，手动下线才会删除，多用于数据库、定时任务等常驻中间件服务。

# 流程 3：服务发现（消费者拉取服务列表）

两种模式结合：定时轮询 + 增量长连接推送

  1. 消费者启动时，向 Nacos 订阅目标服务（比如订单服务 order-service）；
  2. 第一次全量拉取该服务所有可用实例列表，缓存到本地内存 Map；
  3. 客户端建立TCP 长连接订阅通道，阻塞等待 Nacos Server 推送变更；
  4. 当生产者扩容、缩容、宕机下线，Nacos Server 立刻通过长连接增量推送变更后的实例列表；
  5. 消费者更新本地缓存，后续远程调用直接走本地负载均衡，不会每次都请求 Nacos 服务端，性能极高。

# 流程 4：负载均衡内置规则

Nacos 客户端内置 5 种负载均衡策略：

  1. 随机轮询（默认）
  2. 权重加权轮询（灰度发布核心，给新版本实例调高权重分流）
  3. 最小活跃数（避开卡顿、高耗时实例）
  4. 一致性哈希（固定用户路由到同一实例）
  5. 就近机房优先（多集群部署）

# 3. Nacos CAP 架构底层取舍（为什么选 AP）

  1. 分布式必须保证 P（网络分区容错）；
  2. Nacos 服务注册模块采用AP 架构：
    • 集群节点之间异步同步服务列表，牺牲瞬间强一致性；
    • 某一台 Nacos 节点宕机，其他节点依然独立提供注册发现，可用性拉满；
  3. 配置中心模块采用CP 架构：配置修改必须 Raft 同步集群过半节点才生效，保证配置强一致。

# 4. 对比 Eureka 补充原理（加深理解）

Eureka 核心也是 AP，依靠自我保护机制：短时间大量实例掉线，不剔除列表，防止网络抖动误删可用服务；缺点是 2018 年停止维护，无配置中心一体化能力，无灰度权重，所以被 Nacos 替代。

# 步骤 1：项目启动优先级加载配置

SpringBoot 启动时，Bootstrap 上下文优先于 Application 上下文加载 Nacos 配置：

  1. 读取bootstrap.yml中的 nacos 地址、命名空间 namespace、分组 group、DataId 配置文件名；

# 步骤 2：动态配置实时推送核心（长连接订阅机制）

  1. 客户端拉取完初始配置后，立刻向 Nacos Server 建立HTTP 长轮询长连接（Nacos 自研的订阅通道）；

    • Raft 协议同步到 Nacos 集群所有节点；
    • 遍历所有订阅该配置的客户端长连接，推送变更通知；
  4. 客户端收到变更通知后，重新拉取最新完整配置，调用 Spring 上下文刷新接口ContextRefresher.refresh()；
  5. Spring 重新绑定所有配置类，@ConfigurationProperties自动刷新，服务零重启生效。

# 3. 三维环境隔离模型（生产落地核心）

Nacos 用三层维度彻底隔离多环境、多项目、多模块配置：

  1. Namespace 命名空间：最高层级，隔离 dev/test/prod 三个环境；
  2. Group 分组：同一环境下区分项目组，比如 order_group、user_group；
  3. DataId 配置文件 ID：具体微服务的配置文件，order-service-dev.yml。

# 4. 配置版本回滚、灰度发布原理

  1. Nacos 自动保存每一次配置发布历史版本，后台可一键回滚到任意历史快照；
  2. 配置灰度：可以只推送新版本配置给指定 IP 的微服务实例，其他实例沿用旧配置，测试无误全量发布。

# 5. 为什么不推荐 Spring Cloud Config

  1. 依赖 Git 仓库存储配置，无可视化控制台；
  2. 配置刷新需要手动调用/actuator/refresh接口，无法自动推送；
  3. 无集群高可用，无环境隔离，架构单薄；
  4. Nacos 注册 + 配置二合一，减少中间件部署复杂度。

# 2. 第一步：资源埋点如何拦截请求（核心入口）

三种埋点方式，底层都是 AOP 动态代理拦截：

  1. 注解埋点：@SentinelResource(value = "orderCreate")，环绕通知进入 Sentinel 处理器；
  2. Web 全局过滤器：拦截所有 Controller 接口，自动把接口路径作为资源名；
  3. Dubbo/OpenFeign 适配器：拦截 RPC 远程调用方法，把远程调用作为受保护资源。

拦截本质：对每一段需要保护的代码块定义资源 Resource，所有请求先进入 Sentinel Slot 责任链执行校验。

# 3. Slot 责任链执行链路（Sentinel 内核）

请求进入后依次执行链式校验，任意一环拒绝直接抛出 BlockException：

  1. StatisticSlot 统计插槽（最核心） 记录所有请求的成功数、失败数、耗时、异常数，存入滑动窗口，为熔断、限流提供数据支撑；
  2. FlowSlot 限流插槽：校验 QPS / 并发线程数是否触发限流规则；
  3. DegradeSlot 熔断降级插槽：统计异常比例，判断是否打开熔断器；
  4. AuthoritySlot 黑白名单权限校验；
  5. SystemSlot 系统自适应保护（CPU、负载、总 QPS 全局防护）。

# 4. 核心 1：滑动窗口统计（限流、熔断的数据基础）

# 底层数据结构

  1. 采用环形滑动时间窗口，默认窗口总时长 1 秒，拆分为 2 个小窗口（每 500ms 一个桶）；
  2. 每个窗口桶内部维护原子计数器：
    • passQPS：通过的请求数
    • blockQPS：被限流拦截的请求数
    • exceptionQPS：异常请求数
    • rt：请求平均耗时
  3. 窗口滚动机制：时间每滑动 500ms，丢弃最旧的桶，新建空桶，只统计最近 1 秒内的实时指标；
  4. 优势：精准统计瞬时 QPS，解决固定窗口临界值双倍流量击穿漏洞。

# 5. 核心 2：熔断降级 CircuitBreaker 断路器状态流转原理（解决服务雪崩）

# 三种状态闭环流转：关闭 → 打开 → 半开 → 关闭

  1. Closed 关闭状态（正常通行） StatisticSlot 持续统计调用异常比例 / 慢调用比例； 例如规则：10 秒内 20 次调用，异常率超过 50% 触发熔断；
  2. Open 打开状态（熔断断路） 达到阈值，断路器开启，直接拒绝所有请求，快速失败，执行 Fallback 兜底方法； 同时启动休眠时间计时器（比如 5 秒）；
  3. Half-Open 半开探测状态 休眠时间结束，放行少量探测请求去调用下游故障服务；
    • 探测请求成功 → 断路器关闭，恢复正常调用；
    • 探测请求失败 → 立刻重回 Open 熔断状态。

# Sentinel 三种熔断规则

  1. 异常比例熔断（最常用）：异常请求占总请求百分比超限熔断；
  2. 异常数熔断：固定窗口内异常总次数超限熔断；
  3. 慢调用比例熔断：请求 RT 耗时超过阈值的占比过高熔断（应对下游超时卡死）。

# 6. 核心 3：两种隔离机制（线程池隔离 / 信号量隔离）

# （1）线程池隔离（推荐用于远程 RPC 调用）

  1. 为每一个下游依赖服务分配独立线程池；
  2. 调用 Dubbo/OpenFeign 远程接口时，提交到专属线程池执行；
  3. 下游服务卡死，只会耗尽该独立线程池，不会占用当前业务 Tomcat 主线程池，避免整个服务被拖垮；
  4. 缺点：线程上下文切换有轻微性能损耗。

# （2）信号量隔离（用于本地代码、Controller 接口）

不创建独立线程，直接使用 Tomcat 主线程，通过计数器限制最大并发请求数，超出直接限流，开销极小。

# 7. 核心 4：热点参数限流原理（Sentinel 独有能力）

对接口入参做精细化限流，例如：getProduct(Long productId) 限制商品 ID=100 的热点商品每秒只能访问 5 次，防止个别爆款商品被刷爆，Hystrix 无此功能。

# 8. Sentinel 控制台规则推送原理

  1. 微服务客户端启动后心跳连接 Sentinel Dashboard 控制台；
  2. 在页面配置限流、熔断规则后，控制台通过长连接推送 JSON 规则到客户端内存，实时生效；
  3. 规则默认存储在内存，服务重启丢失，生产可对接 Nacos 持久化规则到配置中心，实现规则持久化、集群统一管控。

# 9. Sentinel vs Hystrix 底层本质差异

  1. Hystrix 仅支持线程池隔离，滑动窗口设计老旧，无热点限流、无系统自适应保护；
  2. Sentinel 基于责任链架构扩展性极强，控制台可视化、规则动态推送、轻量级零侵入，Spring Cloud Alibaba 官方主推。

# 3. 阶段 2：一次接口调用完整执行流水线

# Step1：拦截方法，解析方法元数据

InvocationHandler 拦截getById调用，反射获取：

  • 参数位置、路径变量 id 的值

# Step2：构建 Feign 请求模板 RequestTemplate

把路径、参数、请求头、Cookie、Body 封装成模板对象，替换占位符{id}为实际传入 1。

# Step3：负载均衡选取目标服务实例（整合 Ribbon）

  1. 提取@FeignClient中的服务名order-service；
  2. 调用 Spring Cloud 的LoadBalancerClient负载均衡器；
  3. 负载均衡器从 Nacos 注册中心拉取的本地缓存实例列表中，按规则选出一个 IP + 端口（如 192.168.1.10:8080）；
  4. 拼接完整请求地址：http://192.168.1.10:8080/order/get/1。

补充：Spring Cloud LoadBalancer 是新版默认负载均衡组件，替代老旧 Ribbon，Nacos 内置负载均衡策略可以直接替换。

# Step4：底层 HTTP 客户端发送网络请求

Feign 顶层抽象了Client接口，三种可替换实现：

  1. 默认：JDK 原生 HttpURLConnection，无依赖，性能一般；
  2. Apache HttpClient：支持连接池、超时配置、重试，生产常用；
  3. OkHttp：高性能异步连接池，高并发场景优选。

# Step5：响应解析、反序列化

  1. 获取 HTTP 返回的 JSON 字符串；
  2. Feign 内置Decoder解码器（默认 SpringMvcDecoder），用 Jackson 自动反序列化为OrderResp对象；
  3. 向上层业务代码返回结果。

# Step6：异常处理 & Fallback 降级（对接 Sentinel）

  1. 如果远程调用超时、连接拒绝、下游返回 500，抛出 FeignException；
  2. 开启 Sentinel 适配后，异常进入 Sentinel 熔断规则，触发断路器；
  3. 执行fallback = OrderFeignFallback.class兜底实现类的方法，返回预设默认数据。

# 4. OpenFeign 核心内置能力

  1. 请求重试机制：默认重试策略，网络抖动自动重试几次，可自定义重试次数、间隔；
  2. 超时时间双配置：
    • connectTimeout 建立连接超时
    • readTimeout 接口读取响应超时
  3. 日志级别：NONE/BASIC/HEADERS/FULL，打印请求 URL、参数、响应体，排查远程调用问题；
  4. 请求拦截器 RequestInterceptor：全局统一透传 Token、TraceId、链路追踪上下文（SkyWalking 核心依赖）。

# 5. OpenFeign 与 Dubbo RPC 底层本质对比

  1. OpenFeign：应用层 HTTP 协议，基于文本 JSON 序列化，通用性强，调试方便，适合跨系统调用；
  2. Dubbo：TCP 私有二进制协议，Hessian/Protobuf 序列化，长连接、IO 多路复用，内部高频调用吞吐量远高于 HTTP；
  3. Spring Cloud Alibaba 最佳搭配：内部微服务用 Dubbo，对外开放 API 网关用 OpenFeign。

# 6. 高频踩坑原理说明

  1. Feign 接口参数丢失：@PathVariable 必须指定参数名@PathVariable("id")，JDK8 之前反射无法获取参数名；
  2. GET 请求传 POJO 对象报错：Feign GET 无法自动序列化对象为拼接参数，必须改用 @RequestParam 逐个接收；
  3. 超时雪崩：必须配合 Sentinel 做熔断隔离，大量 Feign 超时调用会打满 Tomcat 线程池；
  4. 上下文丢失：通过 RequestInterceptor 拦截器把 Header 里的 TraceId、用户 Token 往下游传递，保证 SkyWalking 链路连贯。

# 附加：四个组件联动完整调用链路（串联整体微服务流程）

  1. 订单服务启动 → Nacos 注册中心注册自身实例，同时拉取库存服务实例列表缓存本地；
  2. 订单服务通过 OpenFeign 调用库存微服务扣减库存；
  3. OpenFeign 通过 Nacos 负载均衡选中一台库存实例发起 HTTP 请求；
  4. OpenFeign 调用被 Sentinel 切面拦截，进入 Slot 责任链：统计 QPS、判断限流规则、线程池隔离；
  5. 如果库存服务频繁超时异常，Sentinel 触发熔断，执行 Fallback 兜底；
  6. 库存服务数据库配置从 Nacos 配置中心长连接动态拉取，修改数据库连接无需重启服务；
  7. SkyWalking 在 OpenFeign 拦截器透传 TraceId，串联整个调用链路耗时与异常。

# 极简面试背诵版（精简总结）

  1. Nacos 注册中心：客户端心跳保活 + 服务端 Raft 集群同步，消费者长连接增量推送实例，AP 架构保证高可用，内置权重实现灰度；
  2. Nacos 配置中心：Bootstrap 上下文优先加载，长轮询订阅配置变更，收到推送后刷新 Spring Environment 上下文，三维命名空间隔离多环境；
  3. Sentinel：AOP 埋点 + Slot 责任链执行校验，环形滑动窗口统计 QPS 与异常，断路器三状态流转实现熔断，线程 / 信号量隔离防止服务雪崩，控制台规则可持久化到 Nacos；
  4. OpenFeign：启动扫描 Feign 接口通过 JDK 动态代理生成实现类，拦截方法封装 HTTP 请求，负载均衡选取注册中心实例，可替换 HttpClient 连接池，天然对接 Sentinel 做远程调用降级。

  2. Seata AT 模式核心：TC、TM、RM 三大角色、二阶段提交、UndoLog、全局锁、脏写隔离

# 一、Seata 分布式事务（重中之重，面试必考）

# 1. 基础概念：什么是分布式事务

跨多个微服务、多个数据库的事务，比如下单同时扣库存、扣余额、生成订单，任意一个微服务失败需要全部回滚，保证最终数据一致性。 本地事务ACID失效，需要分布式事务解决方案。

# Seata 三大核心角色（所有模式通用）

  1. TC Transaction Coordinator 事务协调器（Seata Server） 独立部署的中间件，全局事务的大脑：
  • 生成全局唯一XID全局事务ID
  • 记录全局事务状态（开启、提交、回滚、完成）
  • 通知所有RM执行二阶段提交/回滚
  • 维护全局锁、分支事务注册与上报
  1. TM Transaction Manager 事务管理器（发起方微服务） 加注解 @GlobalTransactional 的入口服务，比如订单服务：
  • 向TC申请创建全局事务，拿到全局XID
  • 调用各个下游RM分支服务
  • 所有分支执行完毕，通知TC全局提交；异常通知TC全局回滚
  1. RM Resource Manager 资源管理器（各个参与分支微服务） 每个操作数据库的微服务（库存、账户、订单）都是RM：
  • 向TC注册分支事务
  • 执行本地业务SQL，记录undo_log回滚日志
  • 一阶段提交释放本地锁，持有TC全局锁
  • 接收TC二阶段指令：删除undo_log（提交）/执行undo_log补偿SQL（回滚）

全局事务链路传递：XID 通过 Feign 请求头透传给所有下游微服务，整个调用链共用同一个全局事务ID。

# 2. Seata 四种事务模式底层原理、适用场景对比

# 模式1：AT 自动事务模式（95%企业生产首选，无侵入）

# 核心原理：基于本地事务 + 全局锁 + UndoLog 逆向补偿（柔性事务，最终一致性）

# 前置准备
  1. 每个参与分布式事务的数据库必须创建 undo_log 表；
  2. RM 数据源通过 Seata 代理 DataSourceProxy 包装，拦截所有DML（INSERT/UPDATE/DELETE）SQL。
# 第一阶段：执行业务SQL，记录UndoLog，提交本地事务，释放行锁，申请全局锁
  1. TM 开启全局事务，获取全局XID；
  2. RM 执行业务SQL（比如扣减库存 update stock）；
  3. 记录UndoLog：记录更新前数据镜像（before image）和更新后镜像（after image），写入undo_log表；
  4. 提交本地数据库事务，释放InnoDB本地行锁，大幅提升并发性能；
  5. RM 向TC注册分支事务，占用该行数据对应的全局锁；
  6. 本地事务完成，业务暂时可以提交，客户端不用阻塞。
# 第二阶段：TC统一下发提交或回滚指令

# 情况A：全局正常提交（所有分支无异常）

  1. TC 通知所有RM 二阶段提交；
  2. RM 直接删除自身undo_log日志，无需执行任何SQL；
  3. 释放TC上的全局锁，全局事务结束。

# 情况B：任意分支异常，全局回滚

  1. TC下发回滚指令给所有RM；
  2. RM 读取当前分支undo_log里的before image原始数据；
  3. 自动生成补偿SQL反向执行（把库存加回去、余额恢复）；
  4. 删除undo_log，释放全局锁，分布式事务整体回滚完成。
# AT模式两大核心锁机制（解决脏写问题）
  1. 本地行锁（InnoDB行锁）：一阶段执行业务SQL时加，本地事务提交立刻释放；
  2. TC全局锁：一阶段占用，二阶段完成才释放。

场景：事务A扣了库存持有全局锁，事务B再修改同一条库存数据，会被阻塞等待全局锁释放，避免中间数据被其他事务篡改。

# AT模式优点&缺点

✅ 优点：代码零侵入，只需要加 @GlobalTransactional 注解，性能好，对业务无感知； ❌ 缺点：只支持MySQL等支持事务的关系型数据库；属于最终一致性，中间过程数据不一致；无法适配非事务中间件（Redis、MQ）。

# 模式2：TCC 手动补偿模式（侵入最高，强一致性）

# 三层接口定义（需要程序员手写代码）

  1. Try 阶段：资源检查、预留锁定（冻结库存、冻结余额），无真实扣减；
  2. Confirm 确认阶段：全部Try成功，执行真实业务扣减；
  3. Cancel 取消阶段：任意Try失败，释放冻结资源回滚。

# 执行流程

TM调用所有分支Try → 全部成功执行Confirm → 任一失败全部执行Cancel。

# 优缺点

✅ 可以对接Redis、MQ、第三方支付等无事务组件；数据一致性更强； ❌ 业务侵入极大，每个接口都要写三套代码，维护成本极高；仅复杂异构系统使用。

# 模式3：SAGA 长事务模式（超长流程、异步流程）

把长事务拆分成多个本地子事务，每个事务对应一个正向操作和逆向补偿操作。

  • 正向：下单→扣库存→扣余额→物流创建
  • 逆向补偿：物流撤销→余额退回→库存退回→订单关闭 Seata Saga 支持状态机编排，适合：
  1. 跨很长时间的业务（订单超时自动取消）
  2. 对接老旧遗留系统、无事务的第三方接口
  3. 微服务链路极长的场景

# 模式4：XA 强一致性模式（几乎不用）

XA是数据库原生二阶段提交协议，数据库本身参与事务协调。

  • 一阶段：所有数据库预提交锁定资源
  • 二阶段：协调器统一提交/回滚 致命缺点：一阶段占用本地行锁直到二阶段结束，并发极差，数据库资源锁定太久，生产直接淘汰。

# 3. Seata AT 模式三大经典问题及解决方案（面试高频追问）

# （1）空回滚

分支收到TC回滚指令，但该分支一阶段根本没有执行业务SQL，undo_log为空。 解决：插入一条 branch_id 记录到undo_log做标记，二阶段判断标记直接结束，避免报错。

# （2）悬挂

二阶段回滚请求先到达RM，一阶段业务SQL后到达，导致补偿SQL先执行，业务SQL再执行造成数据错乱。 解决：undo_log插入分支防悬挂记录，一阶段执行前先判断是否已被回滚，已回滚直接终止本地业务。

# （3）幂等性保证

TC重复下发二阶段提交/回滚指令（网络重试），防止重复执行补偿SQL。 解决：RM执行二阶段前查询undo_log状态，已经处理过直接返回，保证幂等。

# 4. Seata 生产部署架构

  1. TC（Seata Server）集群部署，注册到Nacos；
  2. 事务会话存储：生产不用内存，改为MySQL持久化全局事务会话；
  3. 规则与配置持久化到Nacos配置中心；
  4. 微服务通过Nacos发现TC地址，所有RM自动接入。

# 二、补充微服务其他核心组件原理（面试高频）

# 1. Spring Cloud Gateway 网关底层原理（替代Zuul）

# 1.1 核心架构：基于WebFlux 响应式编程（Netty非阻塞）

Zuul1.x 是Servlet阻塞模型，性能差，Gateway底层Reactor+Netty异步非阻塞，高并发吞吐更高。

# 1.2 三大核心组件

  1. Route 路由：定义请求匹配规则（路径、Cookie、Header），转发到对应微服务；
  2. Predicate 断言：条件判断，满足条件才路由；
  3. Filter 过滤器：分为全局过滤器GlobalFilter、路由过滤器。

# 1.3 过滤器执行链路（责任链）

PRE前置过滤器 → 路由转发 → POST后置过滤器 常用落地功能全部在Filter实现：

  • 跨域CORS统一处理
  • 全局Token鉴权、权限校验
  • 请求参数脱敏、请求日志打印
  • 灰度发布（根据Header/IP路由不同版本实例）
  • 限流（集成Sentinel网关限流）
  • 重写路径、SSL证书卸载
  • 全局异常统一返回格式

# 1.4 负载均衡

内置整合Spring Cloud LoadBalancer，从Nacos拉取服务实例做负载转发。

# 2. SkyWalking 分布式链路追踪底层原理

# 2.1 核心三要素：Trace、Span、Segment

  1. Trace：一次完整的分布式请求全局唯一ID，贯穿所有微服务；
  2. Span：单个方法/接口调用单元，记录耗时、状态、异常；
  3. Segment：单个微服务内部的调用片段。

# 2.2 探针Agent无侵入挂载（Javaagent）

启动JVM时挂载skywalking-agent.jar，通过字节码增强技术修改类：

  • 自动拦截OpenFeign、Dubbo、MySQL、Redis、Gateway、SpringMVC、Sentinel所有组件；
  • 不用改一行业务代码，自动埋点采集调用信息。

# 2.3 数据流转流程

  1. Agent 采集链路数据，异步批量通过gRPC上报到OAP服务端；
  2. OAP做聚合、计算、统计；
  3. 存储到Elasticsearch；
  4. UI可视化展示调用拓扑、接口耗时、慢SQL、异常堆栈、依赖服务QPS。

# 2.4 核心落地点

在OpenFeign的RequestInterceptor自动透传TraceId，保证跨服务链路串联；配合Sentinel定位是代码慢、下游慢还是限流熔断导致报错。

# 3. Spring Cloud LoadBalancer 负载均衡（替代Ribbon）

  1. Spring Cloud官方自带，无需额外依赖，Ribbon已停止维护；
  2. 内置2种策略：轮询RoundRobin、随机Random；可自定义权重、最小连接数、就近机房策略；
  3. 从Nacos注册中心订阅服务实例列表，本地内存缓存，增量更新；
  4. 无缝适配OpenFeign、Gateway网关、RestTemplate。

# 4. 分布式ID 四种生成方案原理（微服务分库分表必备）

# （1）雪花算法 SnowFlake（最常用）

64位Long结构：时间戳+机器ID+数据中心ID+序列号 优点：有序、高性能、本地生成无第三方依赖； 缺点：依赖服务器时钟，时钟回拨会产生重复ID，需要代码做时钟回拨校验。

# （2）Redis自增

INCR命令原子自增，每日重置Key；适合简单场景，Redis宕机有风险。

# （3）数据库号段模式

一张专门的ID生成表，每次批量获取一段ID缓存到内存，减少DB访问；性能稳定，可落地高可用。

# （4）百度UidGenerator、美团Leaf 开源框架

对雪花算法、号段模式封装，解决时钟回拨、集群机器分配问题，生产成熟方案。

# 5. 分布式锁三种实现原理（微服务并发超卖）

# （1）Redis分布式锁（Redisson框架）

基于SETNX + EXPIRE原子命令加锁；Lua脚本释放锁防止死锁；看门狗自动续期；支持可重入锁、公平锁、红锁集群模式。 适用：绝大多数高并发业务（库存扣减、订单防重复提交）。

# （2）Zookeeper 临时有序节点

创建临时节点，断开连接自动释放，可靠性最高；性能较差，并发量不大场景使用。

# （3）数据库乐观锁（version版本号）

update stock set num=num-1,version=version+1 where id=? and version=?；无中间件，并发冲突会重试，适合低并发。

# 6. RabbitMQ/RocketMQ 消息队列在微服务中的作用（补充）

  1. 异步解耦：下单后异步发送短信、物流通知，提升主接口响应速度；
  2. 削峰填谷：秒杀流量积压到MQ，后端消费慢慢处理，避免压垮数据库；
  3. 最终一致性事务（RocketMQ事务消息）：替代Seata AT模式做分布式事务，可靠消息最终一致性；
  4. 死信队列、延迟队列处理订单超时关闭等业务。

# 三、全套微服务组件完整串联业务流程（可直接背）

以下单微服务完整链路为例：

  1. 用户请求先到达 Spring Cloud Gateway网关：网关做鉴权、跨域、Sentinel网关限流、灰度路由；
  2. Gateway通过LoadBalancer负载均衡转发到订单服务；
  3. 订单服务 @GlobalTransactional 开启 Seata AT分布式事务，生成全局XID；
  4. 订单服务通过 OpenFeign 远程调用库存服务、账户支付服务；
  5. OpenFeign 请求被 Sentinel AOP拦截：进入Slot责任链，做QPS限流、异常比例熔断、线程池隔离，防止下游雪崩；
  6. 库存/账户RM执行本地SQL，Seata代理数据源记录undo_log，一阶段提交本地事务占用全局锁；
  7. 整个调用链路被 SkyWalking Java Agent 字节码无侵入埋点，自动上报Trace链路耗时、异常；
  8. 所有微服务地址、权重、配置文件全部统一注册/配置在 Nacos：服务注册发现、配置动态推送、Seata TC地址发现、Sentinel规则持久化；
  9. 事务执行成功Seata TC二阶段删除undo_log；任意服务异常Seata自动反向回滚所有分支数据；
  10. 下单成功发送 RocketMQ消息 异步创建物流、发送短信，完成最终业务闭环；
  11. 库存扣减使用 Redisson Redis分布式锁 防止超卖，订单ID使用雪花算法生成全局唯一分布式ID。

# 四、极简面试背诵精简版

  1. Seata AT模式：TM发起全局事务，TC作为协调器，RM通过代理数据源记录undo_log，一阶段提交本地事务释放行锁占用全局锁，二阶段由TC统一指令删除日志或执行回滚补偿，零侵入适配MySQL；TCC手动写三段代码侵入高，SAGA用于长流程异步事务。
  2. Gateway网关：基于WebFlux异步非阻塞，路由+断言+过滤器实现鉴权、限流、灰度、跨域，性能优于Zuul。
  3. SkyWalking：Javaagent字节码增强无侵入埋点，采集Trace调用链，定位接口瓶颈与异常。
  4. 整套微服务核心闭环：Gateway入口 → Nacos注册配置中心 → OpenFeign远程调用 → Sentinel流量防护 → Seata分布式事务保证数据一致 → SkyWalking链路排查 → MQ异步解耦。
