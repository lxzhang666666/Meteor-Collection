## 1. Redis 是什么？为什么要用Redis？典型业务场景
### 答案原理
Redis 是基于C语言开发的**高性能内存型NoSQL数据库**，数据主要存储在内存，支持多种数据结构、持久化、集群、事务、分布式锁等能力，属于后端最核心的中间件。

### 核心优势
1. 纯内存操作，读写性能极高，单机QPS可达10万+；
2. 丰富的数据结构：String、List、Set、Hash、ZSet、Bitmap、HyperLogLog、Geo、Stream；
3. 支持RDB/AOF双重持久化，宕机不丢失数据；
4. 主从、哨兵、Cluster集群高可用架构；
5. 原子操作，天然适合实现分布式锁、计数器。

### 落地使用场景
1. **热点数据缓存**：商品详情、首页Banner、字典数据，减轻DB压力；
2. **分布式锁**：库存扣减、幂等控制、防重复提交；
3. **计数器**：文章阅读量、接口限流、IP访问频次统计；
4. **排行榜**：ZSet做销量、积分、粉丝排行；
5. **分布式Session共享**；
6. **延时队列、异步任务**（ZSet有序集合）；
7. **位图Bitmap**：用户签到、日活统计、布隆过滤器；
8. **限流组件**：滑动窗口限流、令牌桶限流；
9. **消息队列**：List阻塞队列、Stream持久化消息队列。

## 2. Redis 单线程为什么速度这么快？底层核心原理
### 标准答案原理
Redis 核心执行命令的主线程是单线程，高性能来自4点：
1. **全部数据放在内存**
   内存读写速度远高于磁盘，没有磁盘IO瓶颈，这是最核心原因。

2. **IO多路复用模型（epoll）**
   使用Linux epoll实现IO多路复用，单个线程可以监听上万条Socket连接，不用频繁创建销毁线程，减少上下文切换开销。

3. **避免线程上下文切换与锁竞争**
   单线程执行命令，不存在多线程竞争资源、加锁、解锁、CPU上下文切换的损耗。

4. **底层数据结构高效**
   底层封装了动态字符串SDS、压缩链表、跳表skiplist、哈希表等时间复杂度极低的数据结构，算法效率拉满。

### 补充
Redis 6.0之后引入**多线程处理网络IO**，命令执行依旧是单线程，只是把解析协议、读写socket交给多线程，核心逻辑没变。

## 3. Redis 5种基础数据结构、底层编码、使用场景
### 1）String 字符串
底层：SDS动态字符串
场景：缓存、计数器、分布式锁、序列号、简单KV存储。

### 2）Hash 哈希
底层：ziplist（压缩列表，数据少时）、hashtable（哈希表）
场景：存储对象（用户信息、订单信息），部分字段更新，比序列化String更灵活。

### 3）List 列表
底层：quicklist（压缩双向链表）
场景：阻塞消息队列、栈、队列、分页数据。

### 4）Set 无序集合
底层：hashtable
特点：自动去重、交集/并集/差集运算
场景：好友共同关注、抽奖去重、黑名单。

### 5）ZSet 有序集合（Sorted Set）
底层：跳表 skiplist + 哈希表
特点：根据score分值自动排序，可范围查询
场景：排行榜、延时任务、权重队列、延迟队列。

### 扩展高级结构（面试官延伸提问）
1. Bitmap 位图：签到统计、布隆过滤器；
2. HyperLogLog：海量数据去重统计（UV独立访客）；
3. Geo：地理位置距离计算（附近门店）；
4. Stream：可靠消息队列，支持消费组、ACK、持久化。

## 4. Redis 过期键删除策略（三大策略）
### 原理总述
Redis 给key设置expire过期时间，不会实时主动删除所有过期key，采用三种策略组合。

### 1. 定时删除
创建定时器，key到期立刻删除。
优点：内存最及时释放；
缺点：大量过期key会占用CPU，性能损耗极大，Redis不采用。

### 2. 惰性删除（被动删除，主力）
key被客户端访问查询时，才判断是否过期，过期直接删除返回nil。
优点：CPU开销极小；
缺点：大量过期key长期不被访问，会一直占用内存，导致内存泄漏。

### 3. 定期删除（主动兜底）
Redis后台每隔一段时间（默认100ms），随机抽取一部分设置了过期的key检查，删除过期数据。
规则：遍历多个expire字典，每次随机取20个key，删除过期的，如果过期比例超过25%继续循环。

### 最终组合方案
**惰性删除 + 定期删除** 共同配合。
惰性删除保证平时CPU压力小，定期删除兜底清理冷数据过期key。

## 5. Redis 8种内存淘汰策略（Maxmemory-policy 重中之重）
### 触发条件
Redis内存达到 `maxmemory` 设定上限时，自动执行淘汰策略释放内存。

#### 分类：4类LRU、2类LFU、2类随机、1类TTL
1. **volatile-lru**：只在设置了过期时间的key中，淘汰最近最少使用（LRU）
2. **allkeys-lru**：所有key范围内淘汰LRU（生产最常用默认推荐）
3. **volatile-lfu**：过期key里淘汰访问频次最低LFU
4. **allkeys-lfu**：全量key淘汰LFU（Redis4.0+，比LRU更精准）
5. **volatile-random**：过期key随机删除
6. **allkeys-random**：所有key随机删除
7. **volatile-ttl**：过期key中删除剩余存活时间最短的
8. **noeviction**：不删除任何key，直接返回OOM错误（默认配置，不推荐）

### LRU vs LFU 原理
- LRU：淘汰**最久没被访问**的数据；
- LFU：淘汰**访问次数最少**的数据，能规避冷数据偶尔访问一直驻留内存问题，4.0以上优先allkeys-lfu。

### 生产配置建议
Redis 4.0及以上版本配置：`maxmemory-policy allkeys-lfu`
3.x版本：`allkeys-lru`

## 6. Redis 持久化 RDB、AOF、混合持久化
### 一、RDB（快照持久化）
#### 原理
Redis在某个时间点fork子进程，把全量内存数据二进制写入dump.rdb文件。
触发方式：手动SAVE/BGSAVE、配置定时规则、主从同步、关闭服务。

#### 优点
1. 二进制压缩文件，体积小，适合冷备份、全量迁移；
2. 恢复速度极快；
3. fork子进程，主线程几乎阻塞。

#### 缺点
1. 会丢失两次快照之间的增量数据，故障丢失数据风险大；
2. 海量数据fork子进程会短暂阻塞主线程。

### 二、AOF（追加日志持久化）
#### 原理
记录每一条修改数据的命令，追加写入aof日志文件，重启时重放命令恢复数据。
三种刷盘策略：
1. appendfsync always：每条命令都刷盘，最安全，性能最差；
2. appendfsync everysec：每秒刷一次（生产默认），最多丢1秒数据；
3. appendfsync no：交给操作系统自动刷盘，性能最高，丢失不可控。

#### AOF重写机制
AOF文件会无限膨胀，后台子进程触发rewrite，合并冗余命令，压缩文件体积。

#### AOF优缺点
优点：数据安全性高，最多丢失1秒数据；
缺点：文件体积大，重启恢复重放命令速度慢。

### 三、Redis 4.0+ RDB-AOF 混合持久化（生产标配）
#### 原理
AOF重写时，先把当前全量数据以RDB格式写入AOF头部，后续增量命令继续追加AOF日志。
#### 优势
兼顾RDB恢复快 + AOF丢失少两大优点，线上必须开启。

### 面试一句话总结
RDB做全量冷备份，AOF保证增量数据不丢失，生产环境开启混合持久化。

## 7. Redis 主从复制原理、PSYNC、全量/增量同步
### 作用
主节点写，从节点读，读写分离、数据备份、哨兵高可用基础。

### 完整流程
1. 从节点执行 `slaveof master ip port` 建立连接；
2. 主从握手协商复制ID、偏移量offset；
3. 判断是否可以增量同步：
    - 从未同步/偏移量不在主节点积压缓冲区：执行**全量同步（PSYNC）**
      master fork子进程生成RDB文件发送给slave，slave清空自身数据加载RDB，同时补发缓冲区期间新写入的命令。
    - 偏移量还在积压缓冲区：执行**增量同步**，只补发缺失的命令日志。
4. 后续主节点每写一条命令，异步发送给所有从节点执行，保持数据一致。

### 核心问题
1. 主从复制是异步的，存在短暂数据不一致；
2. 主节点积压缓冲区`repl_backlog_buffer`过小会频繁触发全量同步，线上调大缓冲区。

## 8. Redis Sentinel 哨兵架构原理（高可用）
### 三大核心作用
1. **监控**：哨兵集群持续监测主、从节点是否存活；
2. **自动故障转移**：主节点宕机，哨兵自动投票选出新的主节点，剩余从节点自动切换挂载新master；
3. **客户端通知**：告知业务代码新主节点地址，无需改配置。

### 故障选举完整流程
1. 单个哨兵主观下线（SDOWN）怀疑master宕机；
2. 超过半数哨兵判定客观下线（ODOWN），开启选举；
3. 哨兵之间投票选出领头哨兵；
4. 领头哨兵在所有从库中挑选最优从节点升级为主库（优先级最高、复制偏移量最大）；
5. 执行slaveof no one升格为主库，其他从节点指向新master；
6. 修改旧主库为新主库的从节点。

### 部署规范
哨兵至少部署**奇数个（3个）**，防止脑裂投票无法过半。

## 9. Redis Cluster 集群架构（分片集群 面试重点）
### 1. 哈希槽机制（核心）
Redis Cluster总共分配 **16384个哈希槽（0~16383）**，均匀分配给集群所有主节点。
计算规则：`CRC16(key) % 16384` 得到槽位，找到对应节点存储数据。

### 2. 集群组成
一般3主3从架构：3台主节点分摊16384槽，每台主配1台从节点做备份，某主宕机自动切从顶上。

### 3. 槽迁移原理
集群扩容缩容时，手动迁移部分哈希槽到新节点，数据逐步搬迁，集群不停机。

### 4. 哈希槽为什么是16384？面试官追问答案
1. 16384=2^14，CRC16算法输出16位，取低14位足够映射；
2. 集群心跳消息需要携带槽位图，16384只占用2KB，网络传输压力小；
3. 节点数量不会太多，16384分片粒度足够均衡。

### 5. Cluster 缺陷
不支持跨节点多Key操作（mget、事务、Hash多字段批量），会报`CROSSSLOT`错误。

## 10. 缓存三大经典问题：穿透、击穿、雪崩 原理+完整解决方案
### （1）缓存穿透
#### 原理
查询数据库不存在的数据（比如恶意传-1、随机ID），Redis查不到，大量请求直接打穿到MySQL，压垮数据库。

#### 解决方案
1. 缓存空值/默认值，设置短期过期；
2. 使用**布隆过滤器**，将所有合法主键存入过滤器，非法ID直接拦截；
3. 接口参数校验、网关层限流。

### （2）缓存击穿（热点Key过期）
#### 原理
某个热点商品Key（比如秒杀爆款）设置了过期时间，过期瞬间大量并发请求全部涌向DB。

#### 解决方案
1. 热点Key永不过期（代码逻辑手动控制失效，不用expire）；
2. 使用Redis分布式锁，过期瞬间只放行一个请求更新缓存；
3. 互斥锁方案（Redisson）。

### （3）缓存雪崩
#### 原理
大量Key在**同一时间集体过期**，或者Redis集群整体宕机，所有流量瞬间冲击数据库，导致数据库宕机，系统雪崩。

#### 解决方案
1. 过期时间加随机值，打散失效时间：`expireTime = 3600 + Random(0,300)`；
2. 搭建Redis高可用集群（哨兵/Cluster），防止整体宕机；
3. 服务层做多级降级、限流、熔断（Sentinel组件）；
4. 主从架构，持久化做好数据备份。

### 一句话区分背诵
穿透：查不存在的数据；击穿：单个热点Key过期；雪崩：大量Key同时过期/Redis挂了。

## 11. Redis 分布式锁四种实现方式（原理+优缺点）
### 方案1：SETNX + EXPIRE（存在死锁漏洞，淘汰）
问题：SETNX加锁成功后，程序突然宕机，EXPIRE没有执行，锁永久死锁。

### 方案2：SET 原子命令（基础可用）
命令：`SET lock_key uuid NX EX 30`
NX：不存在才设置；EX：过期时间，**单条命令原子执行**，解决死锁。
缺陷：
1. 锁过期但业务没执行完，会被提前释放；
2. 不支持可重入；
3. 集群主从切换可能锁丢失。

### 方案3：RedLock 红锁算法（Redis官方）
向多个独立Redis实例同时申请锁，半数以上成功才算获取锁。
缺点：复杂度极高，生产极少落地，Redis作者后来也不推荐。

### 方案4：Redisson 框架封装（生产最终方案）
#### 底层原理
1. 基于Lua脚本保证加锁、释放锁原子性；
2. **自动锁续期（看门狗WatchDog）**：业务未执行完，后台定时延长过期时间，避免业务超时锁释放；
3. 支持**可重入锁**，同一个线程多次加锁计数；
4. 支持公平锁、读写锁、联锁；
5. 自动处理集群主从切换风险。

### 面试标准答案
简单场景用SET原子指令，企业级项目直接使用Redisson框架实现分布式锁。

## 12. Redis 事务原理、WATCH乐观锁、为什么不支持回滚
### 1. 事务四大命令
MULTI开启事务 → 多条命令入队 → EXEC批量执行；DISCARD放弃；WATCH监控。

### 2. 执行原理
Redis事务只是**批量命令串行执行**，执行期间不会被其他客户端插入命令，保证隔离性。

### 3. 两种失败情况
1. **入队报错（语法错误）**：整个事务全部放弃执行；
2. **执行时报错（逻辑错误，比如字符串执行自增）**：错误命令跳过，其他正常命令继续执行，**不会回滚**。

### 4. 为什么Redis事务不支持回滚？
1. Redis追求高性能，回滚会增加复杂度与性能开销；
2. Redis业务场景大多简单，开发者自行规避逻辑错误即可；
3. 生产复杂原子操作用Lua脚本替代事务。

### 5. WATCH 乐观锁
WATCH key 监控键，如果事务执行前key被其他客户端修改，EXEC直接返回失败，用于防止超卖等并发场景。

### 替代方案
Lua脚本：多条命令打包原子执行，性能比事务更好，生产大量使用。

## 13. Pipeline 管道原理与使用场景
### 原理
普通模式：客户端发一条命令，Redis返回一次结果，多次网络往返RTT耗时；
Pipeline：客户端一次性打包多条命令发送，Redis批量执行后一次性返回所有结果，**减少网络IO次数**。

### 适用场景
批量插入大量数据、循环多次Redis操作优化。

### 限制
不具备原子性，中间某条命令失败，前面已经执行的不会回滚；需要原子批量操作用Lua脚本。

## 14. Redis 发布订阅 Pub/Sub 原理与缺陷
### 原理
PUBLISH发布消息到频道，SUBSCRIBE客户端订阅频道接收消息，一对多广播。

### 致命缺陷（面试必问）
1. 消息无持久化，客户端离线期间消息直接丢失；
2. 没有ACK确认机制，无法保证消费成功；
3. 不支持消息回溯、死信、堆积能力。

### 替代方案
Redis Stream（持久化、消费组、ACK）、RabbitMQ/RocketMQ专业MQ。

## 15. Redis 实现延时队列两种方案
### 方案1：ZSet 有序集合（最常用）
1. member存消息内容，score存入**未来执行时间戳**；
2. 后台轮询ZRangeByScore，取出score ≤ 当前时间的任务；
3. Lua脚本原子删除并执行业务。
   优点：简单易实现；缺点：轮询有少量CPU空转。

### 方案2：Redis Stream + 定时任务
持久化消息，可靠性更高，适合对丢失零容忍的延时任务。

### 业务场景
订单超时关闭、自动退款、定时提醒。

## 16. Redis 大Key、热Key 问题与优化方案
### 一、大Key问题
#### 定义
单个key value体积过大（比如Hash几万条、String几十MB、List上百万元素）。
#### 危害
1. 网络传输卡顿，Redis阻塞；
2. RDB持久化、主从同步卡顿；
3. 删除大Key主线程阻塞。
#### 优化
1. Hash拆分，拆成多个小Hash；
2. 使用hscan、lscan分段迭代删除；
3. 异步线程分片清理大Key。

### 二、热Key问题
#### 定义
某个Key每秒几万QPS并发访问（秒杀商品）。
#### 危害
单个节点CPU打满，集群分片压力不均衡。
#### 优化
1. 本地JVM缓存做二级缓存；
2. 集群内多副本复制热点Key；
3. 前端限流、网关层拦截。

## 17. IO多路复用 epoll 底层原理（Redis高性能根基）
### 通俗解释
Redis是单线程，要同时监听成千上万个客户端TCP连接，不能阻塞等待单个连接。
epoll可以告诉操作系统：只返回**有数据到来**的socket连接，没有数据的直接跳过，避免无效轮询。
三种IO模型对比：
1. select：文件描述符有上限，轮询遍历；
2. poll：无上限，但依旧全部遍历；
3. epoll：事件驱动，只返回就绪fd，Redis采用。

---

## 18. Redis 6.0 多线程改动点（面试加分）
1. **网络IO多线程**：接收连接、解析协议、读写socket分给多线程；
2. **命令执行依然单线程**：set/get/del等核心命令还是主线程串行执行，保证原子性；
3. 主要提升高并发网络IO场景下的吞吐量，单机上限更高。

## 19. ZSet底层跳表 SkipList 原理（面试官深挖）
### 原理
多层有序链表，底层是完整链表，上层建立稀疏索引，类似二分查找，查询时间复杂度O(logn)。
### 为什么不用平衡二叉树（红黑树）？
1. 跳表插入删除仅修改相邻节点，红黑树需要频繁旋转，CPU开销大；
2. 跳表更容易做范围区间查询（ZSet的zrange）；
3. 实现简单，内存可控。

## 20. Redis 生产环境落地规范（架构师收尾题）
1. 架构：核心业务用3主3从Cluster集群，读写分离；
2. 持久化：开启RDB+AOF混合持久化，AOF每秒刷盘；
3. 内存：设置maxmemory，淘汰策略allkeys-lfu；
4. 禁用危险命令：keys、flushall、flushdb、config；
5. 监控：接入监控系统，告警内存、连接数、大Key、命中率；
6. 定期备份RDB文件到异地服务器；
7. 分布式锁统一封装Redisson，避免手写SET命令漏洞；
8. 海量批量操作用Pipeline/Lua脚本优化网络耗时。

# 面试极简背诵总结（口述版）
1. Redis快核心三点：内存操作 + epoll IO多路复用 + 单线程无锁竞争；
2. 过期策略：惰性删除+定期删除；内存淘汰优先allkeys-lfu；
3. 持久化混合RDB+AOF兼顾速度与安全性；
4. 高可用演进：主从→哨兵（主从高可用）→Cluster（分片水平扩容）；
5. 缓存三大问题：穿透布隆过滤器、击穿热点永不过期/分布式锁、雪崩随机过期+集群降级；
6. 分布式锁生产直接上Redisson，解决死锁、续期、可重入、集群风险。
