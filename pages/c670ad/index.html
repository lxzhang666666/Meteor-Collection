分布式限流组件设计

# 自研分布式限流组件完整深度架构设计

沿用前面RPC、MQ、秒杀系统统一交付范式：

  1. 业务背景、痛点、设计目标、核心技术难点
  2. 整体分层架构 + 模块拆解+核心伪代码
  3. 单机限流算法底层实现（计数器、滑动窗口、漏桶、令牌桶）
  4. 分布式限流Redis落地方案、Lua脚本原子性保障
  5. 全维度限流粒度设计（接口、IP、用户、应用、集群）
  6. 熔断降级、流量预热、排队等待、热点参数限流
  7. 规则动态推送、配置中心热更新
  8. 监控告警、埋点统计、可观测体系
  9. 生产级踩坑点与解决方案
  10. 30道深度面试题+标准答案
  11. 三段背诵版面试总结话术

# 一、业务背景与整体设计约束

# 1. 应用场景

  1. 大促秒杀、优惠券抢购、高并发活动入口防雪崩；
  2. 外部调用方恶意刷接口、爬虫高频请求保护后端服务；
  3. 微服务之间调用流量管控，防止下游被上游打垮；
  4. 多租户SaaS系统按账号分配调用配额；
  5. 网关层全局流量削峰，保护数据库、Redis等核心资源。

# 2. 现有开源方案优缺点对标

  • Sentinel：功能最全、轻量级Java嵌入、本地限流性能强，分布式依赖Redis，热点限流、系统自适应负载优秀；缺点：跨语言支持弱。
  • Guava RateLimiter：仅单机令牌桶，无法集群共享阈值，无规则动态配置。
  • Gateway+Redis手写：分布式简单粗暴，缺少滑动窗口、热点限流、熔断联动。

自研组件定位 以Sentinel核心能力为蓝本自研，分为单机本地限流层 + Redis分布式集群限流层，支持多算法切换、多粒度规则、动态配置推送、热点参数限流、系统保护、熔断降级联动，可嵌入SpringBoot项目、网关层统一拦截。

# 3. 硬性非功能需求

  1. 高性能：单机限流内存计算无网络开销；分布式限流Lua脚本Redis原子执行，减少网络往返；
  2. 多算法可插拔：固定窗口、滑动窗口、漏桶、令牌桶自由切换；
  3. 多维度限流粒度：全局、接口、客户端IP、用户ID、租户ID、请求参数热点限流；
  4. 规则热生效：Nacos/Apollo配置中心推送规则，无需重启服务；
  5. 完整流量防护闭环：限流直接拒绝、排队等待、预热冷启动、关联熔断降级；
  6. 高可用容错：Redis宕机自动降级为单机本地限流，不影响服务可用性；
  7. 完整可观测：限流命中次数、QPS、拒绝率、等待队列长度实时监控+告警。

# 4. 核心技术难点

  1. 分布式场景下Redis计数并发超阈值，如何保证原子性避免超发；
  2. 滑动窗口在Redis中如何高效存储时间分片，减少Key数量与内存占用；
  3. 热点参数海量Key打散，避免Redis热Key缓存击穿；
  4. 规则动态推送后所有实例实时感知并加载，无一致性问题；
  5. 限流与熔断降级联动，防止限流后大量请求直接打垮下游；
  6. Redis集群模式下分布式限流数据一致性与性能平衡。

# 两种接入方式

  1. 应用内拦截：SpringMVC Interceptor / GlobalFilter，拦截Controller接口请求；

# 模块4：核心限流算法引擎（可插拔策略模式）

# 第一大类：单机内存限流（4种算法完整实现）

# 1. 固定时间窗口计数器 FixedWindow

原理：按时间分片（1s、1min），每个窗口独立计数，超过阈值直接拦截。 优点：实现最简单、内存开销极小； 缺点：窗口临界点临界流量突刺（上窗口末尾+下窗口开头瞬间双倍请求击穿系统）。

伪代码核心逻辑

public class FixedWindowRateLimiter implements RateLimiter {
    private long windowStart;
    private final long windowSizeMs;
    private int count;
    private final int threshold;

    @Override
    public synchronized boolean tryAcquire() {
        long now = System.currentTimeMillis();
        // 判断是否跨窗口
        if (now - windowStart >= windowSizeMs) {
            windowStart = now;
            count = 0;
        }
        if (count >= threshold) {
            return false;
        }
        count++;
        return true;
    }
}

# 2. 滑动时间窗口 SlidingWindow（自研重点）

解决固定窗口临界突刺问题。 实现：将1秒窗口拆分为N个小格子（默认10个，每100ms一格），用环形数组存储每个格子的请求计数。 每次请求删除已过期格子，统计所有有效格子总数量判断阈值。 优点：流量曲线平滑，无临界瞬间击穿； 缺点：内存略高于固定窗口。

# 3. 漏桶算法 LeakyBucket

核心：请求匀速流出，超出桶容量直接丢弃，控制下游处理速率恒定。 适用：保护DB、慢接口，强制匀速消费，削峰不控总量。

# 4. 令牌桶算法 TokenBucket（最通用）

系统以固定速率往桶内放令牌，请求拿到令牌才放行，桶满则丢弃令牌。 支持冷启动预热：系统刚启动缓慢递增放令牌速率，避免瞬间大流量打垮冷服务。 适用：秒杀、突发流量、允许短时脉冲流量场景，Guava RateLimiter底层原理。

# 第二大类：Redis分布式限流（集群共享阈值）

# 核心设计原则

所有计数逻辑全部在Redis Lua脚本中执行，保证原子性，避免多命令并发导致超阈值。

local limit = tonumber(ARGV[2])
local current = redis.call('incr', key)
if current == 1 then
    redis.call('expire', key, expire)
end
return current <= limit

  • 第二步：ZCARD 统计窗口内有效请求总数；
  • 第三步：未超限则ZADD写入一条记录；
  • 第四步：设置ZSet过期自动清理。 整条逻辑封装一个Lua脚本，原子执行，防止并发超量。
# Redis性能优化点
  1. 滑动窗口ZSet设置全局过期，避免大量冷Key堆积占用内存；
  2. 热点参数限流做Key打散（如商品ID做hash分片），防止单一Key热点击穿Redis；
  3. Redis连接池复用，减少频繁创建连接开销；
  4. Redis超时/宕机熔断自动降级切为单机本地限流，保障服务不挂。

# 模块5：多维度限流粒度设计（生产全覆盖）

  1. 全局限流：整个服务集群总QPS上限，兜底保护；
  2. 接口级限流：单个URL独立阈值，防止某一个高频接口拖垮整体；
  3. IP维度限流：防止单IP爬虫、恶意刷接口；
  4. 用户/账号维度：限制单个账号调用频次，SaaS多租户场景；
  5. 热点参数限流（Sentinel核心能力复刻） 例如秒杀接口 /seckill?productId=10001，对productId做独立限流，防止爆款商品被疯狂请求挤占其他商品资源。 底层：参数值作为Redis Key，独立计数，支持热点规则快速扫描并自动降级。

# 模块6：流量后置策略 & 熔断降级联动模块

# 1. 四种限流触发后的处理策略

  1. 直接快速拒绝（默认）：返回自定义提示码，如429 Too Many Requests；
  2. 排队等待：超出阈值进入阻塞队列，设置最大等待时长，超时释放，平滑削峰；
  3. 冷启动预热：令牌桶缓慢释放令牌，服务刚启动时逐步放开流量；
  4. 降级熔断：限流触发后直接执行本地Mock兜底逻辑，不再调用下游依赖。

# 2. 与熔断组件联动闭环

  • 同一资源短时间内大量限流拒绝 → 触发熔断器打开；
  • 熔断期间直接走降级逻辑，减少Redis和业务线程消耗；
  • 半开状态试探恢复流量，闭环防止级联故障。

# 模块7：监控埋点与告警运维模块

# 1. 核心采集指标（接入Prometheus）

  • 各资源总请求量、通过量、拒绝量；
  • 单机/分布式限流命中次数；
  • Redis Lua执行耗时、Redis异常降级次数；
  • 热点参数Top N高频Key；
  • 排队队列积压长度、熔断触发次数。

# 2. 告警规则

  1. 单接口限流拒绝率持续超过5%告警；
  2. Redis集群不可用、自动降级为单机限流告警；
  3. 热点参数突增、疑似爬虫攻击告警；
  4. 熔断器频繁打开关闭告警。

# 3. 可视化控制台

后端提供管理接口：规则新增/编辑/禁用、实时QPS查看、限流命中日志查询、热点参数排行榜。

# 三、一次完整限流校验全流程时序

  1. HTTP请求进入拦截器，拦截器开始执行限流校验；
  2. 上下文解析器提取请求URL、IP、用户ID、热点参数；
  3. 从本地内存读取已加载的对应资源限流规则；
  4. 判断规则为单机模式还是Redis分布式模式：
    • 单机：调用内存算法直接判断是否放行；
    • 分布式：拼装Redis Key，发送Lua脚本至Redis原子执行计数；
  5. 返回校验结果：放行 / 触发限流；
  6. 触发限流则执行预设策略（拒绝/排队/降级），记录埋点指标；
  7. 放行则进入后续SpringMVC业务逻辑；
  8. 异步线程上报本次限流统计数据至监控系统。

# 四、整套组件高可用设计汇总

  1. 规则高可用：配置中心集群持久化，本地内存缓存兜底，配置变更热更新；
  2. 分布式Redis高可用：Redis主从+哨兵/集群部署，Lua原子脚本防并发超量；
  3. 故障降级高可用：Redis失联自动切单机限流，组件异常不阻断正常业务；
  4. 流量防护高可用：多算法、多粒度层层防护，限流+熔断双重闭环；
  5. 资源保护高可用：热点Key打散防Redis击穿，过期Key自动清理释放内存。

# 五、生产落地高频坑点 + 根治方案

# 坑1：固定窗口算法临界点流量翻倍击穿系统

解决方案：生产环境默认使用滑动时间窗口算法，平滑流量，杜绝临界突刺。

# 坑2：分布式多节点并发执行多条Redis命令，计数超阈值

解决方案：全部逻辑封装到单条Lua脚本，Redis单线程原子执行，避免分布式并发误差。

# 坑3：热点参数导致单个Redis Key超大并发，产生热Key

解决方案：对热点参数做Hash分片，拆分多个子Key分摊压力；后台自动扫描Top热点Key做独立限流。

# 坑4：Redis宕机后整个分布式限流失效，流量直接压垮服务

解决方案：增加断路器，Redis调用超时/异常自动降级为单机内存限流，保障基础防护。

# 坑5：规则推送更新过程中出现瞬时不一致

解决方案：内存规则采用原子引用AtomicReference整体替换，旧规则被GC回收，无中间状态脏数据。

# 坑6：滑动窗口ZSet长期堆积大量过期数据，Redis内存暴涨

解决方案：Lua脚本每次执行先清理过期score，同时给ZSet设置统一过期时间自动删除。

# 坑7：Tomcat线程池被排队等待的请求占满导致服务卡死

解决方案：排队策略设置最大等待队列长度与超时时间，超限直接拒绝，保护核心线程池。

# 坑8：集群模式下多台实例单机限流叠加，总阈值不可控

解决方案：核心业务强制开启Redis分布式全局计数，单机限流仅作为降级兜底方案。

# 六、30道深度面试追问 + 标准答案

# 一、基础算法原理（1-10）

# 1. 四种限流算法各自优缺点和适用场景？

  1. 固定窗口：实现简单，存在临界流量突刺，仅内部低风险接口使用；
  2. 滑动窗口：流量平滑无突刺，生产最推荐，消耗少量内存；
  3. 漏桶：匀速流出，适合保护DB等慢下游，无法应对突发脉冲流量；
  4. 令牌桶：支持冷启动预热，允许短时突发流量，秒杀、活动场景首选。

# 2. 固定窗口临界突刺的底层原因是什么？

时间窗口切割点，上一个窗口最后一刻大量请求未超限，新窗口第一秒又涌入大量请求，两段叠加瞬间QPS达到2倍阈值直接击穿系统。

# 3. Guava RateLimiter底层是令牌桶还是漏桶？冷启动预热怎么实现？

底层令牌桶，通过平滑加权算法逐步提升令牌发放速率，避免服务冷启动瞬间流量打满。

# 4. 滑动窗口单机用环形数组，Redis分布式为什么用ZSet？

单机内存用数组分片效率最高；分布式需要Redis存储跨节点共享时间戳，ZSet可按score时间范围快速删除过期数据、统计有效条数，天然适配滑动窗口时间维度筛选。

# 5. Redis分布式限流为什么必须用Lua脚本？

Redis执行单条命令是原子的，多条命令中间会被其他线程插队，导致计数超出阈值；Lua脚本在Redis服务端一次性执行所有逻辑，保证原子性，消除并发误差。

# 6. ZSet实现分布式滑动窗口完整Lua执行步骤？

  1. 根据当前时间戳删除窗口外所有过期数据；
  2. ZCARD统计集合内剩余有效请求数量；
  3. 判断是否小于阈值，是则写入一条随机value；
  4. 设置ZSet过期时间自动清理。

# 7. 令牌桶和漏桶核心区别一句话概括？

漏桶控制流出速率恒定，削峰不允许突发；令牌桶控制流入速率，桶内可积攒令牌支持短时突发流量。

# 8. 单机限流和分布式限流分别在什么场景下选择？

单机：单实例部署、Redis不可用降级兜底、非核心接口轻量化防护； 分布式：集群多实例部署、需要全局统一QPS阈值、网关层全局流量管控。

# 9. 滑动窗口拆分多少个格子性能最优？

一般1秒窗口拆10个100ms子窗口，精度足够，内存开销可控，过多分片收益边际递减。

# 10. 限流429状态码含义？

HTTP 429 Too Many Requests，代表客户端请求频率超限，标准限流返回状态码。

# 二、分布式、热点、规则治理（11-20）

# 11. 热点参数限流解决什么问题，底层如何打散热Key？

防止某一个超高热度商品/活动ID占用全部配额，其他正常参数无法访问；通过参数Hash取模分片为多个Redis子Key，分散并发压力。

# 12. Redis集群模式下分布式Lua脚本执行有什么限制？

Lua脚本操作的所有Key必须落在同一个Redis槽位，否则执行报错；解决方案：Key统一使用相同HashTag强制路由到同一个slot。

# 13. 规则热更新如何保证线程安全？

使用AtomicReference<LimitRule>原子引用存储全量规则，配置变更直接替换引用地址，业务线程读取旧引用不受影响，无并发修改异常。

# 14. 限流之后三种降级策略优缺点？

直接拒绝：性能最高，用户体验差；排队等待：削峰平滑，但有线程池耗尽风险；本地Mock降级：保护下游依赖，适合非强一致性查询接口。

# 15. Redis宕机自动降级逻辑怎么设计？

封装Redis操作模板，捕获连接超时、集群不可用异常，捕获后自动切换为单机内存限流策略，并触发告警通知运维修复Redis。

# 16. 全局限流和接口粒度限流优先级怎么设计？

先校验全局总阈值，全局超限直接拦截；全局通过再校验当前接口独立阈值，双层兜底防护。

# 17. IP限流如何获取真实客户端IP，避免Nginx反向代理丢失？

解析X-Forwarded-For请求头，逐级剥离代理IP，取最原始客户端公网IP作为限流Key。

# 18. 滑动窗口Redis ZSet会产生大量垃圾数据吗，怎么清理？

每次Lua执行先清理过期score，同时给整个ZSet设置TTL过期时间，Redis自动回收，不会内存泄漏。

# 19. 冷启动预热基于哪种算法实现，解决什么痛点？

令牌桶算法，解决服务重启、发布上线后大量流量瞬间涌入，JVM未预热、缓存未加载导致系统雪崩问题。

# 20. 同一个接口既做IP限流又做用户限流，执行顺序怎么排？

先IP粗粒度拦截，再用户细粒度拦截，尽早拦截无效请求，减少后续计算开销。

# 三、架构拔高、生产优化（21-30）

# 21. 网关层限流和应用层限流区别，推荐在哪一层做？

网关层：入口统一拦截，所有微服务一套规则，集中管控，推荐生产首选； 应用层：细粒度接口、热点参数、内部调用管控，作为第二层防护。

# 22. 大量请求进入排队策略，如何防止Tomcat线程池打满？

设置最大排队长度、最大等待超时时间，超出直接拒绝；排队使用独立阻塞队列，不占用Web容器核心线程。

# 23. 如何统计限流命中率，评估阈值是否设置合理？

通过监控指标计算：拒绝次数 / 总请求次数 = 限流命中率，命中率过高调大阈值，过低调小阈值。

# 24. 分布式限流Redis Key命名规范怎么设计？

limit:{算法}:{粒度}:{标识}:{资源路径}，分层清晰，方便过期清理和后台统计。

# 25. 如果Lua脚本执行耗时过长阻塞Redis主线程怎么优化？

  1. 精简Lua内部逻辑，只保留核心计数；
  2. 拆分超大窗口为小时间粒度；
  3. Redis集群分片分摊脚本执行压力。

# 26. 多租户系统如何做租户隔离限流？

限流粒度增加TENANT_ID维度，每个租户独立Redis Key计数，配额互不干扰，按套餐分配阈值。

# 27. 限流组件如何与之前自研熔断框架联动？

同一资源短时间内连续触发限流次数达到阈值，调用熔断器打开开关，熔断期间直接返回降级结果，降低Redis压力。

# 28. 磁盘持久化规则什么时候需要？

配置中心已做持久化，组件本地无需落盘；仅配置中心不可用时可加载本地JSON备份规则应急。

# 29. 大促前如何压测验证限流组件准确性？

JMeter/压测工具并发施压，观测监控面板QPS是否严格卡在设定阈值，查看Redis计数是否准确、降级是否自动触发。

# 30. 一句话总结自研分布式限流组件整体设计思想

整套限流组件基于策略模式插拔式实现四大经典限流算法，分层构建单机内存轻量化限流与Redis Lua原子脚本分布式集群限流双底座；支持IP/用户/接口/热点参数多维度粒度管控，依托配置中心完成规则无感知热更新；增加Redis故障自动降级、冷启动流量预热、限流熔断联动闭环保障高可用，最后辅以全维度指标埋点与告警体系，构建从流量拦截、规则管控、故障自愈到可视化运维的完整服务流量防护体系。

# 架构师拔高版

整体围绕算法可扩展、计数强准确、集群高可用、运维自动化四大目标搭建架构。算法层以策略工厂实现四种限流算法自由切换，生产优先滑动窗口规避流量突刺；分布式层依托Redis+Lua原子脚本解决集群并发计数偏差问题，通过HashTag、热点Key分片解决Redis槽位与热Key击穿风险；管控层打通配置中心完成规则热生效，多层级限流粒度覆盖网关全局到接口参数精细化防护；可靠性上构建Redis失联自动降级、冷启动预热、限流熔断联动三重故障闭环；最终以全链路指标埋点、热点自动扫描、异常告警完成可观测运维闭环，在并发准确性、系统容错性、运维便捷性上达成平衡。
